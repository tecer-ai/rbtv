# Documentation decisions

The standing choices and comparisons behind the 0.2.1 reader pages. The [overview](capabilities/rbtv.md), `glossary/`, [Building guides](capabilities/guides/choosing-what-to-build.md), and `principles/` state the chosen design directly.

## Editorial decisions

- Write in English, call the product **rbtv** in lowercase, and make the overview short enough for a human to review end to end. Describe the intended 0.2.1 design as the design itself; keep migration notes here.
- Define rbtv once, in `rbtv.md`. Keep one glossary file per surviving rbtv concept or named structure. Explain general terms and the harness names Claude Code, Codex, and OpenCode inline rather than creating glossary pages for them. The one exception is `context window`: rbtv exists to shape it, so it has an entry, and that entry also holds hallucination, drift, and their four causes (context load, context gap, cognitive load, context poisoning) rather than giving each its own page.
- "Part" is not a term. Do not add a glossary entry for it, for "prompt part", or for "task part". A glossary entry would freeze several meanings under one name. Where a sentence means what a component contains, name the cognitive unit, capability, or tool. Where it means what a folder exposes, name skill, rule, command, or agent. Where it means the units listed in `glossary/prompt.md`, write "cognitive units of a prompt". Where it means scope and done contract, write "cognitive units a task carries". Plain English may say "piece". Do not use "part" for either.
- Link terms from the overview. Use ASCII diagrams for its two folder layouts and lists where they make the glossary easier to scan. Keep the settled principles in separate, self-contained files under `principles/`.
- Consolidate the user-facing agent, source agent definition, installed agent, and agent exposure in `glossary/agent.md`; do not create parallel entries for these views. Keep the installed `.rbtv/` folder distinct from the product rbtv.
- Say "folder", never "directory", matching the term folder artifact.
- This project's folders keep one hand-written folder instructions file each, `CLAUDE.md`; the installer generates `AGENTS.md` from it. The owner dropped the earlier hand-kept `AGENTS.md` copies (never tracked: git ignores every `AGENTS.md` in the vault) because the installer refuses to overwrite a file it did not write, which blocked every install in the vault, and because the 0.2.1 design has the author write one basis file.
- The release is called **rbtv 0.2.1**. "Ignite" names only the `core` component that connects installed agents to Slack and wakes them; the owner chose to keep the name for the component and drop it for the release, so one name has one meaning.
- Respect the owner's deletions. Do not recreate glossary entries for `agent type`, `reference`, `permissions`, `restrictions`, `resources`, `input`, `output`, `outcome`, `i/o spec`, or `task goal`. Those are 0.1 names, not cognitive units of a prompt. A task can still state its goal in ordinary language.
- `guides/` has a guide for every standard file, folder, cognitive unit of a prompt, and cognitive unit a task carries, as rule 2 of [`CLAUDE.md`](CLAUDE.md) requires, plus a guide for choosing what to build. It has no guides for deleted entries. A guide has no building guide of its own: it has a glossary entry and a template, and the template is the shape, so a second guide would restate it.
- Every guide uses one shape: one sentence saying what the unit is and linking its glossary entry; then Purpose, What good looks like, Making it good, and Traps. Purpose says what the unit is for and what fails without it, in a few lines. What good looks like holds tests a reviewer can pass or fail. Where a test comes from a principle, the bullet links the principle and states the test for that unit; it does not restate the principle. Making it good says how to reach those qualities; it is step-by-step only where writing a section needs it. Traps records only a trap a named source has shown; omit the section when none remain. Hand-authored units use that full shape. A file the installer creates stays a few lines: what it is for, that it is not hand-written, and what a good one shows. Those files are the thin loader, `config/`, `runtime/`, `.rbtv/` itself, `launch.json`, `install.json`, and Ignite's `config/ignite/config.json`. `mirror/` is hand-authored source inside the installer-created folder, so its guide is full.
- Choosing between kinds of unit lives only in `guides/choosing-what-to-build.md`. Each other guide's Purpose links that file and does not compare kinds. That choosing guide routes between builds rather than building one unit, so it does not use the fixed shape. It is the one exception.
- Guides do not state file mechanics: where a file goes, what the installer generates, frontmatter fields, or a template link. Those live in `rbtv.md`, one line each with a link. `rbtv.md` stays a concise navigation index, short enough for a human to review end to end.
- `guides/`, `principles/`, `glossary/`, and `templates/` each have an index file, `<folder>.md`, listing every item in that folder with the moment to open it. The index does not list itself.
- The building guides live in `guides/`, not `build/`, because `build` is the name of the `core/build/` component that holds them; one name, one meaning. The component is staged at the project's `core/build/`, mirroring its rbtv path, so it does not collide with the project's `build/` records folder.
- `templates/` holds both kinds of shape, listed in its index file: **templates**, the agent-readable shape of a file (a cognitive unit), and **schemas**, the code-readable shape (a JSON Schema, `<name>.schema.json`). The owner kept one folder because one file can follow both: an agent, skill, rule, or command file's body follows its template and its frontmatter its schema, and a folder instructions file holds the installer's marked sections, which follow a template, beside the author's own text. For those files the template keeps a filled frontmatter example and the schema is the authority for the fields: the installer validates every file's frontmatter against its schema and refuses a mismatch, and the template guide tests that the template's frontmatter keys equal the schema's, so drift fails loudly. Every exposed cognitive unit, and every tool, carries its own name and description, so the installer can present it without a separate list: skills, commands, rules, and agents in frontmatter, and tools in `<tool>.json`. A skill or command description is short: its first sentence is enough to decide whether to open or invoke it, and the rest names the situations and one similar case that must not. A rule description states what every agent that receives the rule does on every task; it names no case to skip. The [`<tool>.json` schema](capabilities/templates/tool-json.schema.json) holds a tool's name and one-line description, because a program has no frontmatter; `<tool>.json` is used, not `<tool>.md`, because `<folder>.md` already names the index file. Every file the system needs in order to work that has a fixed shape gets a schema here, including files only programs read: [`launch.json`](capabilities/templates/launch-json.schema.json), [`install.json`](capabilities/templates/install-json.schema.json), and Ignite's [`config/ignite/config.json`](capabilities/templates/ignite-config.schema.json). The owner's reason: the documentation defines what the system needs to work, and defining those shapes here is what keeps it consistent, even for formats only a program writes. They stay in this folder until their components (Ignite, the installer) are staged. The `install.json` schema is transcribed from the 0.2 installer's record (`meta/installer/lib/state.py`, `operations.py` in rbtv); its descriptions of `tree`, `claims`, `links`, and `path_links` are inferred from names and code, not confirmed, and the live key `path_bootstrap`, which current installer code does not write, is left out. `ignite/config.json` drops two 0.2 `ignite.json` fields: `defaultLaunch`, because whoever installs an agent must choose its harness, model, and effort, and `workspace`, because the file's own place under the installation root already gives it. Files the installer generates that agents read have templates too, because their shape is rbtv's decision: the [thin loader](capabilities/templates/thin-loader.md) and the installer's parts of a [folder instructions](capabilities/templates/folder-instructions.md) file (a component's marked section, the agent section, and the header of a generated copy). The installer's own section at the top of a target has no template yet: its only content, the rule list for harnesses that cannot present rules directly, waits on that open harness mapping. The guide template also holds the short shape for files a program creates. There is no template or schema for a tool's program (it is code), `runtime/` data or an agent's live data (written only by programs while they run), `settings.json` (its content depends on the agent), `memory/` (undefined), a capability, or the author's own text in folder instructions (no fixed shape).

The owner kept hooks and MCP servers (one MCP server, Chrome DevTools, is in use), moved them into their own folders with an rbtv format, and kept a whole-folder skill only in the mirror (next row). |

Edit the basis file and run the installer again; never edit a generated copy by hand. Folders the installer does not walk — a nested git repository, an excluded path — get no copy by design. | The harnesses already load those file names. One authored file plus generated copies keeps one source without a third filename. Both copies exist on purpose; the generated copy is not a second source. Skipping non-walked folders is the user's choice of what to ignore, not a gap. |
| A component can ship folder instructions from a `folder-instructions/` source folder, sixth beside `skills/`, `rules/`, `commands/`, `capabilities/`, and `agents/`. Its files are flat; each names its target folder, relative to the installation root, in its frontmatter `target`, which the installer removes before writing the text. In the target, the component owns only a marked section inside that folder's folder instructions file, labeled with its module and component; two components targeting one folder each own their own section. Text outside the markers is never touched, and missing markers stop the install. | Proven precedent: sb-os's marker-section model, where the installer rewrites only inside a marker pair and aborts rather than overwrite when a marker is missing ([i4](../../build/guides-rework/out/i4-sbos-managed-blocks.md)). The owner chose flat files with the target in each file's own frontmatter over a mirrored folder tree and over a separate mapping file, so each file is its own single source. In 0.2, `agents.md` rows were listed as "guidance parts" inside the root section instead. |
| An installation has `.rbtv/mirror/`, `.rbtv/config/`, `.rbtv/agents/`, `.rbtv/runtime/`, and `.rbtv/memory/`. | Agent homes and runtime data are part of the installation alongside mirror, config, and memory, by owner choice. Memory's behavior is still undefined. Glossary entries name full paths, including `.rbtv/config/` and `.rbtv/mirror/`. |

The owner chose the simpler 0.2 whole-component substitution over it. Files from the two components are not merged. The `_skills/` exception is deliberate, per the owner: it is the user's way to import an outside skill and track it without changing rbtv's source. In 0.2, `_skills/` was the older name of `_hub/skills/`, and `_hub/` also held commands, rules, hooks, and other kinds; 0.2.1 keeps only `_skills/`. |

The owner removed them from the file so the live value has one home. |

The installer recognises an agent folder by its install record, and `rbtv install update` refreshes the agent from its `agent.md`. | In 0.2, `ignite-agent create` built the folder from a purpose file, reference paths, and a skill list, wrote `CLAUDE.md`/`AGENTS.md` from a template, `launch.json`, `settings.json`, `board.md`, and a create-progress `setup.json`, and installed skills with `rbtv install add --target <agent folder>`, so each agent folder already had its own install record. Files the installer generates are rebuilt in each installation, never shared. ## Agents and cognitive units

- **Agent:** a prompt (instruction text composed of cognitive units) given to a model through a harness. This replaces 0.1's agent-type distinction and the proposal to make a fixed task inside the reusable agent. A user can supply the task interactively; another agent can supply it when invoking the agent. The task supplies the goal, [scope](capabilities/glossary/scope.md), and [done contract](capabilities/glossary/done-contract.md). An agent launched by another agent is a sub-agent: any agent an agent launches through `cast` is one. The word "role" is not used for this, because role is a cognitive unit of a prompt. "Primary agent" is not a term; the owner dropped it (the 0.2 `create-primary-agent` skill still carries it).
- **Sub-agents and harnesses:** Claude Code and Codex launch sub-agents of their own, but only on their own harness and models; `cast` removes that limit. The installer's `sub-agent` exposure translates an agent file into a harness's own sub-agent definition; the owner ruled this a translation, not a contradiction. In 0.2 it writes `.claude/agents/<name>.md` for Claude Code and `.opencode/agents/<name>.md` for OpenCode, and nothing for Codex; the installer is adapted to agent files. A sub-agent is not a cognitive unit of its caller: like a tool, it shapes the caller's context window indirectly, through a fresh context window, other models' views, and specialized agents to distribute tasks to.
- **Agent files:** an agent file, `agent.md`, gives the prompt; its frontmatter selects skills, rules, commands, hooks, and MCP servers and lists the agent's key folders, written relative to the installation root so that one root can be shared across machines. The installer writes the key folders into the agent section of the agent folder's folder instructions, beside the pointer to `agent.md`. A component can ship agent files under `agents/`. The same file serves `rbtv install`, Ignite, and `cast`; how an agent is installed and run is in the System and installation table. `cast` is documented here because launching agents on any harness is part of rbtv's `core`.
- **Agent description.** The `description` field is a short description: the first sentence is enough to decide whether to invoke the agent; the rest names the triggers and one near-miss (a similar case that is not this agent). It does not hold steps.
- **Prompt:** only the surviving prompt-side units are described as its cognitive units: role, persona within role, procedure, and constraints. The deleted 0.1 prompt fields listed above must not creep back into its definition. Scope and done contract arrive with each task.
- **Where a prompt's cognitive units are written.** Role, procedure, and constraints are sections of the named agent file, under the headings in the agent template; the persona sits inside the role section. They are not separate files. When a second agent needs the same text, move that text to a capability and point both agent files at it. The agent file is the only home while one agent uses the text.
- **Standing completion conditions:** conditions that hold for every task are check steps in the skill, command, or procedure that does the work; a done contract carries only its own task's conditions. Chosen over a default done contract carried by the skill, which would change the done contract's definition and need a rule for combining it with the task's.
- **Cognitive unit:** text an agent reads that shapes its cognition, written in files (a whole file or a section of one) and organized in folders; the folders belong to it because they decide what reaches the context window through folder instructions and folder artifacts. A file only programs read is not a cognitive unit; one both read is. Folder instructions and folder artifacts are cognitive units. In 0.1, "scaffolding" named this collective, the reusable toolkit an agent works with ([0.1 scaffolding](../../recovered-0.1/system-definition/concepts/scaffolding.md)); in 0.2.1 that meaning belongs to cognitive units, and "scaffolding" names only what the installer creates in a target folder. The owner kept the installer meaning because an agent folder is one more target folder, and moved the toolkit meaning to cognitive units so that each name has one meaning.
- **Discovering cognitive units:** whoever creates an agent finds the available units through the installer's non-interactive commands (`rbtv install list`, `search`, `show`) and enters them in the agent file; a new unit is built only for what nothing listed covers. Those commands must carry everything needed for that.
- **Capability:** reusable content kept in a component's `capabilities/` folder and shared by its skills, rules, commands, and agents: instructions, knowledge, templates, or tools. It has no exposure method and no fixed shape, so it has no template; the cognitive units that use it point to it. A tool is a capability but not a cognitive unit: it shapes the context window only indirectly, by doing work outside it. This documentation is staged as the `core/build/` component, in the project's `core/build/` folder: its pages, templates, building guides, and principles are the component's capabilities in `capabilities/`; other cognitive units may move in later. The CLI work is the staged `meta/code/` component. The older `reference` name is not a 0.2.1 term.
- **Exposure:** rule means the full instruction is presented on every task of every agent that receives it, with no human activation and no agent choice; a rule is not admitted because it is installed. Skill means the agent always sees a short description and chooses when to read the full body. Command means a human chooses when to invoke it. This follows the intended Claude Code sense of the three methods. Codex and OpenCode require harness-specific treatment for rules. The 0.1 rule design also allowed a scoped command-result rider; that delivery is not carried into this definition. An agent is reached through Slack (Ignite), `rbtv spark`, `cast -ig`, or, when not installed, `cast -rg`.
- **Tool choice:** use executable software for exact, repeatable operations and model judgment for work that needs interpretation. A skill, rule, or command names the tool and the moment to use it. Placing the executable on `PATH` alone does not teach the agent when to use it. A tool reports success as status 0 and failure as any other status, so a caller checks the answer without reading prose.

## Module and component placement

- `core` is for rbtv's own operation, installation, configuration, and editing, and for the software that installs, runs, launches, and connects agents on any harness: the installer, Ignite with its Slack connection and configuration, `cast`, and `rbtv spark`. `meta` is for how agents behave, communicate, plan, and coordinate work, such as the `plan`, `swarm`, and `panel` skills. The owner placed `cast` in `core` because sub-agents and harness independence are central to rbtv, and Ignite there because it holds the Slack configuration. Other modules own their own subject areas; neither `core` nor `meta` is a catch-all. Only these two intrinsic modules receive module-specific glossary pages.
- This **reverses the 0.2 folder meanings**: in 0.2, `meta/` is about rbtv itself and `core/` is about general agents. The owner chose the inversion for 0.2.1 after considering both assignments. The reader pages use only the chosen meanings.
- Extend a component when its cognitive units and capabilities serve one coherent purpose; create a new one when the purpose is distinct. The owner chose this over grouping by shared audience, workflow, file type, or exposure method. 0.2 has exceptions, including `core/functions` (a pool of unlike conversational skills) and unrelated tool exposures under `meta/planning`; these are observations, not precedents for 0.2.1. This is a placement rule, not an authorization to reorganize existing components now.
- `core/build`'s capabilities exist so that a skill under `build/skills/`, still to be written, can teach agents to read and navigate them whenever they build skills, rules, commands, agents, tools, or other rbtv units. `meta/code` is the anticipated migration of the command-line work into a skill, `cli-creator`: an early test of how this documentation works in use; other cognitive units may follow.
- The navigation skill is named `build`, with no prefix; its source is in the `build` component's `skills/` folder in rbtv, and a harness receives only its thin loader. It replaces the 0.2 `build` skill (`meta/planning/references/build.md` in rbtv), which is deleted entirely. It triggers only on work on rbtv components: creating or reviewing a skill, rule, command, agent, hook, MCP server, tool, or other rbtv unit. It is written after the `core` migration. Its body is an entry point, not a second map: read `rbtv.md` to understand what rbtv is, the guides to build, the glossary for exact meanings, the templates and schemas for a file's shape, and always follow the principles. That routing already lives in `capabilities/capabilities.md`, so the skill points there instead of restating it, and it never repeats `rbtv.md`'s content. Owner's reason: an agent building on rbtv must land on the right page for its situation, and results must be installer-recognizable and follow the principles.
- `rbtv install`'s command-line experience is the reference for every rbtv command-line tool, and `cli-creator` was built from it. Every new or edited rbtv command-line tool follows `cli-creator`, and no edit lowers its standards. Until migration, hand-made loaders in the workspace's `.claude/skills/` and `.agents/skills/` point to the staged skill so it is followed now.
- Module and component names are nouns, never gerunds: `plan`, not `planning` (owner ruling). The 0.2 `meta/planning` component becomes `meta/plan`.
- Create a new module only when no existing module's purpose fits without stretching it. It may start with one component, but it must name a coherent area for future components. Decide the module, then the component, then whether any cognitive unit needs independent exposure.

## Principles

The principles act as rbtv's culture for agents: they guide how cognitive units, files, folders, and not-yet-designed structures such as memory and artifacts are built. They exist to shape the agent's context window, so the model hallucinates and drifts less and reasons better. No one reinforces them, so each must state its own practical consequence.

Working records behind these choices: the [principles audit](../../build/principles-audit.md) (terminology clashes, overlaps and tensions, where each principle applies, candidate implications), [earlier principle versions and formats](../../build/principles-provenance.md), and [external research on actionable principles](../../build/principles-external-research.md).

- Each principle file has a **Statement**, **Rationale**, and **Implications**, following the architecture-principle format. The implications are the practical consequence, and each is written so a reviewer can confirm or reject it. The owner chose this over pass/fail checks with red flags, MUST/NEVER rule tables, and do/don't examples. All principles use this format.
- Principles guide how structure is defined; they never define the structure themselves. An implication is a test the builder applies to its own design, not a piece every design must contain. Every implication was swept against this rule and ruled by the owner one at a time; the rulings are in [`../../build/principles-sweep.md`](../../build/principles-sweep.md).
- The Statement names the trade-off the principle makes, in the form "X, even over Y". A principle nobody would disagree with guides no decision.
- The Rationale names the context-window effects the principle reduces, hallucination or drift, and the causes it acts on: context load, context gap, cognitive load, or context poisoning. The owner asked for this so that every principle is checkably aimed at those effects.
- Implications are instructions to the builder ("Link to the owning file"), not descriptions of the system. Agents act on instructions most reliably.
- "Task" is the one term for a piece of work given to a human or an agent, and has its own glossary entry. It replaces request, job, assignment, unit of work, seat, session, run, and execution ([audit §1b](../../build/principles-audit.md#1b-cross-set-drift-one-concept-several-names)). The owner chose "task" because it is the same thing a task list holds, whether a human or an agent does it, which keeps human and agent work in one vocabulary (Agent parity). The deleted 0.1 task-goal cognitive unit stays deleted; a task states its goal in ordinary language.
- Micro agency gives each task and each cognitive unit one purpose whose result can be judged alone. An unrelated second purpose is a second unit. The principle owns the parallel-run limit: independent tasks run in parallel only when no two of them change the same file or record.
- Progressive disclosure has five loading moments: a rule, when the content applies to every task of every agent that receives it; a skill, when the agent judges it relevant; a command, when a human decides; folder instructions, when the agent reads or changes files in a folder; a file opened because a rule, skill, command, or folder instructions points to it, when it is needed only at that step. Folder structure and memory are designed around index files and pointers.
- Folder instructions route the agent to the right file at that moment. That routing is what sets them apart from a rule, which travels with the agent into any folder. The installer delivers them by writing a copy for each installed harness beside the basis file, as it does for every folder it walks; each harness then loads the copies by its own rules. rbtv accepts where a harness loads less and does not work around it: per the research, Codex reads folder files only from the root down to the folder it starts in, once per session, and stops at a 32 KB total ([investigation](../../build/guides-rework/out/i2-rules-folder-instructions.md)). A folder instructions file stays correct when read with its parent folders' files: it does not contradict them and does not rely on overriding them. The file in the highest folder of a tree stays small.
- What an agent sees before opening a unit, such as a skill description, is a name and a short description. The first sentence is enough to decide whether to open it. The rest names the triggers and one near-miss: a case that looks close but should not open it. An index line, and a record's description field, stay one line that names the moment or the decide sentence.
- A principle lists implications only for the areas it actually changes, not a fixed checklist of areas.
- Merges are allowed: if two principles produce the same implications, propose merging them for owner approval. The candidate overlaps and their proposed owners are in [audit §2](../../build/principles-audit.md#2-overlap-and-tension-map).
- Each shared implication has one owning principle, following [audit §2](../../build/principles-audit.md#2-overlap-and-tension-map). Single source of truth owns "one implementation behind every way to perform an action" and "move content to a shared home at the second user". Agent parity owns "an agent can reach every action". Deterministic first owns "exact steps go to tools" and making tools known to agents. Keep it simple breaks ties.
- The parity principle is named Agent parity. It covers any software that humans and agents both use, not only the state rbtv manages: both reach the same operations through their own interfaces. An agent reaches an rbtv action by editing the same file a human edits, or through a tool when the action is more than a file edit, so the principle is not about command-line tools alone.
- "Workflow" is defined in the glossary: a set of tasks arranged as a DAG, run by sub-agents through `cast`, running at the same time every task whose needs are met except tasks that change the same file or record. It is written in `workflow.md`, which replaces 0.2's `seats.md`; the coordinating agent reads it and launches the ready agents. The owner chose a file only agents read, because no program needs to read it; a machine-readable file with a `cast` command that launches and monitors every ready agent was considered and not adopted. The principles still use no term such as "handoff"; one task's result being used by another is described in plain words.
- Compound engineering is not a principle. Its content moved to the memory drafts, [`../../_backlog/_scaffolding/memory/compound-engineering.md`](../../_backlog/_scaffolding/memory/compound-engineering.md), to be designed together with `.rbtv/memory/`.
- Agent tooling is merged into Deterministic first. Both covered tools for agents, and one implication, naming the tool in the step that uses it, appeared in both.
- A principle shapes the system; an instruction about an agent's conduct during a task is a rule, never a principle ([glossary](capabilities/glossary/principle.md)). Always verify is therefore a rule, not a principle, and so are the former last implications of Deterministic first (check the installed tools before scripting) and Terminology is king (use glossary terms with humans). Their rule texts are drafted in [`../../build/doc-review-2026-09-29/rule-drafts.md`](../../build/doc-review-2026-09-29/rule-drafts.md) until the component that holds them is chosen.
- Agents as teammates, Capabilities first, and Harness and provider agnostic are deleted. Of their implications, only two are kept: the clean-boundary test (a capability relies on nothing beyond what its user passes to it) is in the [capability guide](capabilities/guides/capability.md), and the carry-over test is an input to the memory design (Open decisions). The rest, including the term "provider", are dropped.
- Principle texts use 0.2.1 terms only, such as no "seat" in Micro agency. The full list of clashes is in [audit §1](../../build/principles-audit.md#1-terminology-audit).

## Migration

- The migration is implemented in place: the installer, `cast`, and Ignite are changed directly and at the same time, in parallel. No copies or second files are kept so the 0.2 version goes on working. Before implementation starts, each affected repository (rbtv and second-brain) gets a cleanup commit that leaves nothing uncommitted; those commits are the restore point. Ignite on the VPS runs from a deploy worktree fixed at a commit, so its live agents keep the 0.2 code until the new commit is deployed. The owner chose this over keeping the old version working beside the new one.
- Who does what, and how they coordinate, is the [migration coordination contract](../../build/migration-contract.md): janice owns the documentation and answers from it, jamiro implements, laila tests on the VPS.
- The implementation happens on the branch `rbtv-0.2.1`, in a separate git worktree under `5-workbench/`, and is merged after laila's tests pass. The vault's own rbtv folder stays untouched until then, because every installed skill in the vault points at it: switching it to a half-migrated branch would break every session. A branch is not a copy kept working beside the new version, so it fits the in-place rule.
- The modules outside `core` and `meta` (`web`, `office`, `innovate`) are converted to the 0.2.1 layout mechanically, with a one-off script, in the same change as the installer's new reader, so the installer has one reader and no second format.
- The 0.2 `core/coding` component moves into the `meta/code` component.
- The installer checks frontmatter and JSON records against the schemas with a small validator in its own code, covering only the schema keywords the templates use; it adds no outside dependency.
- The 0.2 `build` skill leaves the plan component now, and the plan component's `references/` are retired: the `plan` skill points to the build documentation (glossary and guides) where it pointed to those references. The file-by-file review (`../../build/installer-schemas/r7-plan-references.md`) found two things the build documentation lacked, now carried into the agent and capability guides: no installation-specific value (channel id, path, account, host, credential) is typed into a prompt or capability, and an agent that runs without a person never waits for a result after its turn ends. The other nineteen files are covered, a deleted 0.1 concept, or an obsolete 0.2 mechanism.
- Components in this migration (owner rulings on jamiro's component table, `../../build/component-table.md`): `acct` (provider accounts) folds into `core/cast`; the Slack and Google tools (`stools` wrapper, `gtools`) and the `google-workspace` skill move to `meta/communication`, and Ignite installs them as standard units; `innovate/brand`, `innovate/conception`, `innovate/validation`, and `web/research`, which had no record in 0.2 but hold content other files point to, each get a `<component>.json` and become components with capabilities only.
- Retired in this migration: the 0.2 `create-cli` skill (it overlapped `cli-creator`), and the `component-lint` and `capability-cards` tools (they read `exposure.csv`, and `component-lint` checked 0.1 shapes). Checking that a component follows the format is the installer's job: its schema validation and `rbtv install doctor`.
- The mechanical conversion removed every frontmatter key no schema allows (the 0.1 names `inputs`, `outputs`, `outcome`, `id`, and the unread 0.2 hints `tags` and `exposes-cli`), moved each component's `component.md` into its `capabilities/`, and deleted `module.md`; the descriptions live in the JSON records, and the rest stays in git history. The owner accepted it.
- The 0.2 installer installs no dependencies. `package.json` stays in the four components that have it, untouched, because its `check` and `install` commands are the data a future dependency installer needs; that installer is not built in this migration (Open decisions).
- A tool's `entry` names its program inside its component. The one exception is `gtools`, whose program lives in its own repository in the workspace: its `entry` keeps 0.2's `ws:` form, a path from the installation root.
- Agent files are translated into each harness's own sub-agent definitions on all three harnesses: Claude Code and OpenCode get a thin loader in their agents folder, as in 0.2, and Codex gets `.codex/agents/<name>.toml` with the agent's name, description, and instructions pointing to its agent file. In 0.2 Codex got none; Codex now has native sub-agents.
- Kept from 0.2: thin loaders name their unit by an absolute path; the installer keeps listing the files it generates in `.git/info/exclude`, so each machine regenerates its own and the absolute paths stay right; Codex's rule list stays in the root `AGENTS.md` until the direct-rule mapping is decided.
- Installing an agent: `rbtv install agent add <agent file> --harness … --model … --effort …`, `rbtv install agent update <agent>`, and `rbtv install agent remove <agent>`, a sub-verb so agents never collide with unit selection; `rbtv spark <agent>` runs one interactively. The agent folder's ignore file is `.gitignore`, listing the database (`state.sqlite*`), `turns/`, and each conversation's harness session files (`conversations/*/session*`); conversation history stays shareable. The units an agent file selects are installed into the agent folder itself, which has its own install record, so its hooks and MCP servers land in the agent folder's own harness files. `update` regenerates everything from `agent.md`, removing units it no longer selects, and keeps `launch.json`, `settings.json`, and live data. `remove` takes back only what the installer wrote (its units, the agent section, `launch.json`, `.gitignore`) and keeps `agent.md`, `settings.json`, and everything the agent made, following the installer's rule that it deletes only its own files. An effort given as a number from 1 to 5 is stored as the model's own effort word, and `inert` for a model with no effort setting.
- Hooks use Claude Code's event names, which Codex shares, with the fields event, optional matcher, command, and optional timeout; OpenCode receives no hooks. OpenCode's equivalent is a plugin, a JavaScript program file loaded from `.opencode/plugins/`, not a settings entry; the owner translates a hook only where the harness takes a settings file, so none is generated for OpenCode.
- An MCP server's secrets reach each harness as the environment variable's name in that harness's own form: `${VAR}` for Claude Code, `{env:VAR}` for OpenCode, and Codex's forwarding list, which works only when the server's variable has the same name as the environment variable (otherwise the installer refuses it for Codex). rbtv never writes a secret: a server that logs in through the browser has its token stored by the harness, and an API key stays in an environment variable. One shared record serves all three harnesses.
- `cast` hands Codex its prompt as developer instructions on every platform. On Windows it starts Codex's program directly, not through the `.cmd` wrapper, whose command-shell quoting breaks on characters such as `&`, `|`, `<`, `>`, `^`, `%`, and quotes; the same launch fixes every harness on Windows. Owner's reason: both platforms work the same way. This holds for every `cast` launch that carries a system prompt, not only `cast turn`. Verified against the harness documentation: Codex forwards an environment variable by name through `env_vars`, and its `env` values are taken literally; OpenCode expands `{env:VAR}` in its configuration when it loads it, and an unset variable becomes empty.
- Programs move into their tool folders for the modules migrated now, `core` and `meta`. In `office`, `web`, and `innovate`, each tool's `entry` points to its program where it already is, inside its component, until those modules are migrated.
- `embed-search` and `control-panel` are not migrated now: their folders move, as they are, to the project's `_backlog/`, and their installed skill and commands are removed from the vault.
- Ignite's commands are verbs of `ignite-agent`: `install <agent file> --harness … --model … --effort …` (runs `rbtv install agent add` and adds Ignite's standard units; any machine, no Slack), `update <agent>`, `connect <agent> (--channel-name <name> | --dm) [--schedule-json <file>]` (on the machine that will run it: the Slack channel or direct messages, the route in that machine's `config/ignite/config.json`, an optional timer), and `disconnect <agent> [--archive-channel]`. They replace 0.2's `create` and `create --remove`; `settings`, `schedule`, `work`, and `history` stay.
- Ignite's standard units reach an agent folder as an ordinary install recorded under Ignite in the folder's install record; the agent file lists only the owner's choices. The install record's `agent_units` lists the units the agent file selected, so `rbtv install agent update` removes only those the file drops, and `ignite-agent update` re-runs Ignite's install. The owner chose this over writing Ignite's units into each agent file, which would mix the owner's choices with Ignite's and leave dropped standard units behind.
- The 0.2 `build` skill and all 21 files of the plan component's `references/` are deleted in the `plan` rework.
- Until the merge, the documentation's one hand-edited home is the vault's `1-projects/ignite-0.2.1/core/build/`; the rbtv branch holds a copy the installer reads, and jamiro re-copies the files each janice documentation commit changes, in his next commit. At the merge, the vault copy is deleted and the rbtv repository's `core/build/` becomes the one home; the project's `CLAUDE.md` and index then point there.
- laila may use the `meeting-summarizer` agent for tests. It has been paused since 2026-09-30 after a harness error; the owner keeps it paused until the changes are tested, and clearing that pause is the first test. The `gaming` and `master` agents are never tested.
- laila tests Ignite agents by sending Slack messages as the owner through `stools`, the Slack command-line tool Ignite agents already use; one waking program serves both the owner's agents and the test agent.
