# Listener

A listener is the inbound side of a [port](../../../rbtv/capabilities/glossary/port.md) in Ignite: one per port, it receives each [connector](../../../rbtv/capabilities/glossary/connector.md)'s events in the port's one inbound shape and hands them to Ignite's dispatch, which decides whom to wake. The messaging listener is the operation `message.receive`; its inbound event (who, group, thread, text, with optional parts) is the one the [messaging contract](../../../../connectors/messaging/capabilities/methods/messaging-contract.md) states, and every messaging connector's [adapter](../../../rbtv/capabilities/glossary/adapter.md) delivers that shape, whatever the service's own.

Ignite's listener is `listener.js`. Slack keeps Ignite's socket: `daemon.js` connects and `fromSocket` assigns identity from `slack.ownerUserId`, never from a field of the event. WhatsApp is a receiver on `127.0.0.1` only. Ignite starts `whatsapp sync --follow` on the installation store (`.rbtv/runtime/whatsapp`) after that receiver binds, and stops it with the listener. The webhook secret stays in the env file named by `secretEnv`; it is not typed into a shell. wacli signs the raw body with HMAC-SHA256 in `X-Wacli-Signature` (hex or `sha256=` plus hex). A missing or wrong signature is refused before dispatch. The body Ignite accepts is wacli's message: `Chat`, `ID`, `SenderJID`, `Text`, `Timestamp`, `FromMe`, `ReplyToID`. The linked phone comes from `whatsapp auth status --json --read-only` and must match `listeners.whatsapp.account`. Gmail is polled by the Google adapter only when `listeners.google.pollMs` is set; the module starts no timer of its own. The command is `google gmail read … --json`. Owner identity is `--verify-sender`, not the From header. The mailbox is the address Gmail's profile returns (`MAILBOX` on stderr, and `sender_verification.mailbox`); it must match `listeners.google.mailbox`. A poll reads each message for its full body, pages with `before`/`after` on Gmail's `internalDate` in milliseconds, and keeps one cursor per account. A held message is retried by id and does not move the watermark past it. Polls do not overlap; stop aborts the command in flight and waits for it.

## What the listener decides

Routing is Ignite's dispatch, never an adapter's. For each event, in this order: admission (only a verified owner; a [subscription](subscription.md) does not admit anyone else), thread affinity (a reply follows its thread's agent before any rule), the most specific matching subscription, a judged subscription (a TypeSafe judgment at entry, configured per subscription), then the port's default agent (a Slack DM and WhatsApp: the configured DM agent; mail: `listeners.google.agent`). Specificity is strict inclusion of constraints: contact and group together beat group alone. Equal or incomparable matches are a tie: no turn, the judge is not called, reason `tie`. A judgment error or timeout starts no turn, reason `judgment-error`, and the event is kept in the hold file and replayed through the same dispatch; it is not sent to another agent because the judge failed. The judge command is `typesafe yesno QUESTION --json`. An invalid subscription file is logged (`subscriptions` / `invalid`) and the event is held, or the last valid copy is kept; it does not become the default agent. An event already accepted is not queued again when the rules change or the process restarts (`.rbtv/runtime/ignite/ingress.json`). A reply follows the agent of that connector, account and conversation, including a thread an inbound message or `message send` started. Every decision is one JSON line in `.rbtv/runtime/ignite/decisions.jsonl`, with the connector, account, conversation and whether the sender is trusted or only claimed. No model judges anything at exit, and a judged route never grants a permission.

An adapter delivers events and keeps the session with its service; the listener receives, admits and routes; a subscription says who is woken. A schedule wakes an agent by time, not by an event.
