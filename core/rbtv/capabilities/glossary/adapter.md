# Adapter

An adapter is the half of a [port](port.md)'s mechanism that meets the port through one outside party's own operations, so that the inside of rbtv names the operation and never the party. `cast` runs an agent through a harness adapter per harness; a [connector](connector.md) delivers a port's [operations](operation.md) through an adapter per port it serves. Name the adapter when the question is which piece translates the port into the party's calls; name the [port command](port-command.md) when the question is which command agents call, and the [service](service.md) when the question is which outside system acts.

A connector's adapter is required, whatever the port: a Node module at `capabilities/tools/<name>/lib/<port>.js`, loaded in-process by Ignite by the connector's name, exporting the shape its port names. Ignite loads it in-process because it is a daemon that reacts to events, polls and ticks status, and a command started per call is not viable there; the connector's command, in any language, is the other half and knows nothing of Ignite. [Building a connector](../methods/building-a-connector.md) states what each port's adapter exports, when the two halves may hold two implementations of one service call and when they share one, and the shape check that confirms the exports.

Two exist. `connectors/asaas/capabilities/tools/asaas/lib/withdrawal-validation.js` is the payments adapter for the [payment gate](../../../ignite/capabilities/glossary/payment-gate.md)'s withdrawal validation: it exports `path` (where the bank calls), `header` and `tokenEnv` (the token's header and variable) and `read(body)` (the bank's body as an operation the gate can check); Ignite's `payment-webhook.js` loads it with `loadProvider(name)` and refuses a module of another shape. `connectors/slack/capabilities/tools/slack/lib/live-status.js` is the one piece of Slack's messaging adapter built today: the emoji for each state, their order rules and the legend, pure logic handed the reaction functions by Ignite's `status-ticker.js`.

## Write one

1. Take the shape from the port: the exported names and what each takes and returns are stated by the page that loads it (the payment gate for withdrawal validation; the [messaging contract](../../../../connectors/messaging/capabilities/methods/messaging-contract.md)'s Adapter section for a messaging adapter; Building a connector for a port with no contract page). Export exactly those names; the loader refuses another shape.
2. Make the module pure where it can be: translate shapes, map names, read a body. What must call the service receives Ignite's functions or clock as arguments, as `live-status.js` receives `addReaction` and `removeReaction`, so Ignite's tests run the adapter with a stand-in.
3. Read a token by its variable name only, from the process environment and then the installation's [environment file](environment-file.md); never print it and never log a payload that may hold one.
4. Test it with recorded bodies of the service: from Ignite's suite when Ignite loads it ([Testing Ignite](../../../ignite/capabilities/methods/testing-ignite.md); the asaas adapter's tests are in `test_payments.js`, the Slack live status in `test_live_status.js`), otherwise from a test program beside the connector's command.

The shape check of Building a connector confirms the exports from the command line.
