# Documentation decisions

The standing choices and comparisons on which the 0.2.1 reader pages are based. The [overview](skills/framework.md), `glossary/`, [Building guides](capabilities/choosing-what-to-build.md), and `principles/` state the chosen design directly.

## Editorial decisions

- Write in English, call the product **rbtv** in lowercase, and make the overview short enough for a human to review end to end. Describe the intended 0.2.1 design as the design itself; keep migration notes here.
- Define rbtv in the framework entry point and keep one glossary entry per shared rbtv term. The context-window entry also owns hallucination, drift, context load, context gap, cognitive load and context poisoning. Do not create separate pages for these causes. Harness has its existing entry for delivery differences.
- A prompt is one cognitive unit. Role, optional persona within Role, optional Navigation, Procedure and optional Constraints are its sections. Scope and Done contract are sections of a task, not independently authored cognitive units. “Part” remains ordinary language and gets no glossary entry.
- Generated skill and command copies are described in the rbtv CLI entry, not a separate term, guide or template. PATH is operating-system vocabulary; the rbtv home-folder entry explains its role without a separate glossary page.
- The framework entry point supplies the map and direct reading routes. Principles stay in separate files under `capabilities/principles/` and are mandatory readings before conditional guidance.
- Consolidate every view of an agent (the rbtv agent, the Ignite agent, the rogue agent, the sub-agent, and the agent file) in `glossary/agent.md`; do not create parallel entries for these views. Keep the installed `.rbtv/` folder distinct from the product rbtv.
- Say "folder", never "directory", matching the term folder artifact.
- The commands use the words **file** (not item, not unit) and **installation** (not workspace), in help, results, refusals, and JSON field names (`files`; Ignite's flag is `--installation`). The state words `installed` and `not installed` stay, and "workspace memory" keeps its name. A retired command name has no working alias and no message that it moved.
- This project's folders keep one hand-written folder instructions file each, `CLAUDE.md`; the installer generates `AGENTS.md` from it. The owner dropped the earlier hand-kept `AGENTS.md` copies (never tracked: git ignores every `AGENTS.md` in the vault) because the installer refuses to overwrite a file it did not write, which blocked every install in the vault, and because the 0.2.1 design has the author write one basis file.
- The release is called **rbtv 0.2.1**. "Ignite" names only the `core` component that connects rbtv agents to Slack and wakes them, and its command `ignite`; the owner chose to keep the name for the component and drop it for the release, so one name has one meaning.
- Respect the owner's deletions. Do not recreate glossary entries for `agent type`, `reference`, `permissions`, `restrictions`, `resources`, `input`, `output`, `outcome`, `i/o spec`, or `task goal`. Those are 0.1 names, not cognitive units of a prompt. A task can still state its goal in ordinary language.
- Each standard rbtv file or folder has one glossary entry that defines it and teaches its authoring. Sections not built independently stay in the containing entry. There are no separate glossary, guide and template pages for one converted term; its template belongs in the entry and a software-read schema remains separate.
- Entries open with definition and purpose, then teach the decisions in the author’s order and how to verify the result. Headings follow the subject; do not repeat one requirement in a failure list, procedure, example and checklist. The framework’s mandatory readings may be assumed, so concrete-kind entries add their own requirements rather than reteaching the shared ones.
- `capabilities/choosing-what-to-build.md` owns kind selection; `capabilities/choosing-where-to-build.md` owns placement. `building-from-a-conversation.md` extracts settled reusable instructions after a conversation; `tips-development.md` records distinctions during it. `documenting-a-change.md` remains the documentation-update route required by the root instructions and awaits its separate migration.
- Kind-specific facts needed to author a file stay with the kind’s instruction. The rbtv CLI entry owns recognition, generated paths, invocation syntax and refresh behavior. Schemas own validated field lists. Link that owner rather than copying its reference material.
- Converted rbtv source folders have no index files. The framework and other entry points route directly to capability pages. Workspace folder-artifact conventions are separate and must not be inferred from this source-folder rule.
- The program and building documentation live together in `core/rbtv`; its entry point is `skills/framework.md`. Capabilities, glossary entries, principles and schemas live under its `capabilities/` tree.
- A template is an inline layout with decision placeholders in its owning entry; a schema is a separate `<name>.schema.json` file used by software. Do not maintain a template index or a completed instance as the required layout. Fields are authoritative in schemas, whose actual enforcement is documented by the Schema entry. Generated records and runtime data are described where the responsible program is documented, without pretending the agent hand-writes them.

- Natural, simple and direct writing is the standard. Reasons remain when they supply a needed fact or prevent an evidenced mistake. Examples default to none; use one for a required output format and a contrasting pair for an evidenced confusion. Do not use a banned-word search or repeated example pattern as a substitute for reading the result.
- Cognitive load includes interpretation and decisions without criteria. The context-window entry defines it; Keep it stupidly simple owns the authoring rule. Authors settle task-independent choices. Remaining task-dependent choices specify defaults, observable exceptions, evidence and missing or conflicting-evidence behavior, without turning these authoring checks into a ritual for every reader.

- Every file the system needs in order to work that has a fixed shape gets a schema here, including files only CLIs read: [`install.json`](capabilities/templates/install-json.schema.json), [`agent.json`](capabilities/templates/agent-json.schema.json), and Ignite's [`config/ignite/config.json`](capabilities/templates/ignite-config.schema.json). The owner's reason: the documentation defines what the system needs to work, and defining those shapes here is what keeps it consistent, even for formats only a CLI writes. They stay in this folder until their components (Ignite and the rbtv CLI) are staged. The `install.json` schema describes the root's record, including component source `tree`, ownership claims, and PATH links; it omits `path_bootstrap`, which the rbtv CLI does not write. The `agent.json` schema describes an agent's file: the author's fields and the record of what was generated. The `ignite/config.json` file drops two 0.2 `ignite.json` fields: `defaultLaunch`, because whoever adds an agent must choose its harness, model, and effort, and `workspace`, because the file's own place under the installation root already gives it.

## Agents and cognitive units

- **Agent:** a model at an effort, a harness and scaffolding, launched with a task. Scaffolding is its prompt plus the files and packs it selects. The Agent entry owns the source folder and placements; the Prompt entry owns standing instructions, while the Task entry owns one launch’s result, scope and done contract.
- **Kinds of agent:** an **rbtv agent** is an agent that has a folder containing `agent.md` (its prompt) and `agent.json` (its description, harness, model, effort, voice, chosen units and packs, and the record of generated files). It replaces "installed agent". An **Ignite agent** is an rbtv agent connected to Ignite: the Ignite pack is on and a Slack channel wakes it. A **rogue agent** is an agent file launched with `cast --rogue`; it is not an rbtv agent and is never installed.
- **Sub-agent:** an agent launched by another agent. A component ships one `agents/<name>/` source with `agent.md` and `agent.json`, which can be placed as an rbtv agent or a harness-native sub-agent. The latter uses its target’s installed selections; its source record’s selections are not installed by native placement.
- **The root:** the installation root is an rbtv agent with no `agent.md` and no stored harness, model, or effort: the person chooses them when they open it. Its file is `.rbtv/config/install.json`. Both records share one shape, and the root's has the same fields without `name`, `description`, `harness`, `model`, and `effort`. Where a file is tells the root from an agent, never which fields are empty.
- **The `rbtv` CLI:** manages what an agent is exposed to, by managing which units it has, for the root and for agents, and creates agents.
- **Pack:** a named list of units a component declares in `packs/<name>.json`; the root or an agent turns it on or off, and an agent's `agent.json` lists the packs that are on. Packs are declared in data, so `rbtv` contains nothing specific to Ignite.
- **Launching:** `cast --agent <agent>` (an agent launching another), `spark <agent>` (a person, interactively), and Ignite (a Slack message or a timer) all run an rbtv agent with its own harness, model, and effort from `agent.json`; `rbtv agent configure` is the only command that changes them. `<agent>` is a name or a folder path. `cast --rogue FILE` launches a rogue agent file. Every launcher sets `RBTV_AGENT_HOME` to the agent's folder, so any agent, however launched, can manage itself. It replaces `IGNITE_AGENT_HOME`; `IGNITE_CONVERSATION` stays.
- **Shipped agents:** a component may ship an rbtv agent folder under `agents/<name>/`. `rbtv agent add <name>` places a copy of it in `.rbtv/agents/<name>/` and installs it there. The intended use is an agent that carries its skills through a pack, so it is easy to call and its work stays out of the caller's context window.
- **Flags and options:** a flag or an option is two dashes and a whole word, or one dash and one letter; a whole word after one dash is not used for a new or changed word. The rule is in the `cli-creator` skill's interface contract (`meta/code/capabilities/cli-ux/interface-contract.md`). Every command-line tool of the `core` module follows it: `cast models list`, `cast list --agents`, `cast list --agent <agent>`, and, for launching, `cast --agent <agent>` and `cast --rogue FILE`. A list that shortens a description takes `--full`, which shows it whole: `cast list --agents`, `spark list`, `rbtv agent list`, `rbtv list`, `rbtv search`, and `rbtv show` for a module or a component.
- **Finding models:** `cast models list` prints the harnesses, the models, and what each effort number means on each; `cast -h` names that command and prints no model, so the help page does not change when a model does. `cast models` owns every list of models: `cast list` lists the rbtv agents only, and `cast list --models` and `cast route --catalog` are refused with the command that replaces them (owner: one home per fact).
- **cast help:** `cast -h` leads with the rbtv-agent form, `cast --agent AGENT (-p TEXT | -f FILE)`; the raw `<harness> <model> <effort>` form comes second, as the form for a worker chosen by `cast route` or a throwaway. `-p` and `-f` are the task. `-s`, `-S` and `--rogue` sit under one heading, "Without an rbtv agent", for a launch that will not be repeated. The page tells a reader about to write an agent to make an rbtv agent in any folder, load the `framework` skill (its repository path and the absolute path of that copy), then run `rbtv agent add FOLDER --harness H --model M --effort E` and `cast --agent FOLDER`. `cast route -h` says a verdict for an agent launched more than once goes into `rbtv agent add` or `rbtv agent configure`. The owner asked for it after the page led an agent to a raw launch where an rbtv agent was wanted.
- **Selected models:** an installation's model catalog, `.rbtv/config/cast/models.csv`, holds the models that installation selects, each with its routing columns. A model with no row there is refused by `cast <harness> <model>`, `cast --agent`, an Ignite turn and `cast api`, the refusal naming `cast models add`, and `cast route` never names it. While an installation has no such file the model catalog shipped with cast is in force and every supported model is selected, so no installation is dead on arrival; the user prunes. The installation is the first folder upward holding `.rbtv/config/install.json`: from the agent's folder for an agent launch, from the current folder for any other. The file is committed with the installation, so both machines and the daemon share one choice (owner: cast sets which models can be launched). `cast models add` and `cast models remove` are the commands that change it, for the installation of the current folder; `remove` is refused while an agent under `.rbtv/agents/` or the Dreamer still names the model, and `--force` overrides (owner). `cast doctor` checks the logins of the selected models only.
- **One provider for the rules about an agent:** cast's `lib/agent.js` is the one place that says where an agent's folder is (`<installation>/.rbtv/agents/<name>`), whether a value is a name or a path (a slash or a backslash makes a path), and how `agent.json` is read. spark, the agent list and Ignite load it; none keeps a copy. rbtv is not a Node CLI and its `agent update` and `agent remove` work with no cast on PATH, so it states two of these rules in one line each (`agent_home` and `is_path` in `lib/agents.py`) in place of asking cast on every agent command (owner ruling); its self-test runs cast's code and fails when the two differ. A record must carry `harness`, `model` and `effort`, the effort as the model's own word; a record without one is not launched by cast, spark or Ignite. What an effort number means is cast's too: `rbtv agent add`, `rbtv agent configure` and `rbtv add --on` take a number or a word, and for a number rbtv asks cast for the model's word (`cast <harness> <model> <number> --dry-run`, the field `effort_word`), as it asks for the harness's own id of a model; a number cast refuses is refused. The list of harnesses rbtv accepts stays rbtv's own (`HARNESSES`): it is the harnesses rbtv knows where to write files for, which is a different fact from the harnesses cast can launch.
- **Finding rbtv agents:** one list, kept by cast. `cast list --agents` shows the agents that can be launched by name from the current folder, the agents of the nearest `.rbtv/agents/`, each with its name, harness, model, effort, whether it is an Ignite agent, and its description; `cast list --agent <agent>`, with a name or a path, shows that agent in full, with the packs, skills, rules, commands, MCP servers and hooks installed in it under the names `rbtv show` takes, which cast asks of the installer. An agent finds them there. `spark list` shows the same list to a person and `rbtv agent list` runs `cast list --agents`, so the three print the same text and no second listing exists. `--target FOLDER` on the three lists, and on `spark AGENT`, takes the agents from an installation, from a folder that holds agent folders, or from one agent folder; cast reads the option in one function, so an agent that lives outside `.rbtv/agents/`, such as a plan's, can be listed. A launch by `cast --agent` takes no `--target`: such an agent is launched by its path. No other file under an agent folder is named `agent.json`: the file an Ignite turn writes its result to is `agent-result.json`, because two files with different purposes never share a name. `rbtv agent add <name>` looks first under `.rbtv/agents/`, then among the agents components ship. Ignite connects only agents found under `.rbtv/agents/`.
- **Agent files:** an agent's `agent.md` gives the prompt; its frontmatter contains only `name`. Its optional Navigation section lists the agent's key paths, written relative to the installation root so that one root can be shared across machines. The units it has, its description, and its harness, model, and effort are in its `agent.json`. The installer writes an agent section into the agent folder's folder instructions, beside the pointer to `agent.md`. A component can ship an rbtv agent folder under `agents/`. The same agent folder serves `rbtv agent`, Ignite, `spark`, and `cast`; how an agent is installed and run is in the System and installation table. `cast` is documented here because launching agents on any harness is part of rbtv's `core`.
- **Agent description.** Use the four labeled description fields defined in Routing table. The Agent entry supplies their meaning for selecting and launching an agent, including the required task inputs. Keep procedure steps in the prompt.
- **Environment values.** The existing installation environment file has its entry at `capabilities/glossary/environment-file.md`; Config routes to it for value storage. Ordinary component records contain variable names. Consumers retain their documented loading behavior.
- **Settings.** `settings.json` stays one file in the agent's folder, not moved or split. Its convention: one top-level key per tool or concern, paths written relative to the installation root, no secrets. It is not shared through git.
- **Sub-agents and harnesses:** native placement writes `.claude/agents/<name>.md`, `.opencode/agents/<name>.md` or `.codex/agents/<name>.toml` from the same source agent folder. A separate `sub-agents/` source is refused. An rbtv agent instead launches through cast, spark or Ignite. A sub-agent is not a cognitive unit of its caller; its separate work shapes the caller’s context through the returned result.
- **Prompt:** the body of `agent.md`, one cognitive unit, with standing Role, optional Navigation, Procedure and optional Constraints. Scope and Done contract arrive with each task. Persona is optional inside Role and must shape a decision, not merely decorate the voice.
- **Where prompt sections are written:** all remain in `agent.md`; none has a separate entry or file. A Procedure step can read a capability directly when needed. A prompt has no entry-point routing table and does not copy the capability’s method.
- **Standing completion conditions:** conditions that apply to every task are check steps in the skill, command, or procedure that does the work; a done contract carries only its own task's conditions. Chosen over a default done contract carried by the skill, which would change the done contract's definition and need a rule for combining it with the task's.
- **Cognitive unit:** instructions an agent follows, shared by skills, rules, commands and prompts. Their shared authoring method belongs in that entry. A program or software-only record is not a cognitive unit. Supporting capability prose and folder content retain the definitions of their own entries.
- **Discovering cognitive units:** whoever creates an agent finds the available units through the `rbtv` non-interactive commands (`rbtv list`, `rbtv search`, `rbtv show`) and enters them in the agent file's `agent.json`; a new unit is built only for what nothing listed covers. Those commands must carry everything needed for that.
- **Capability:** a method or knowledge page read from source after a route or prompt step selects it. Callers supply inputs; the page performs the remaining work. Shared methods have one capability, and callers route directly to it. A short method needed by every reading can remain in its exposure method; no extra file exists merely to shorten the body.
- **Few exposures:** nest many capabilities, usually most or all of a component's, under as few skills or commands as possible; several short commands become capabilities under one skill. The agent first chooses among fewer entry points, then chooses which capability to open inside one. The owner chose this two-stage progressive disclosure to lower the agent's cognitive load.
- **Rules and agents:** an installed rule’s body is supplied on every task and states the condition for acting. It can route to a capability for a conditional method. A rule description selects installation, not one task. Agent prompts can name a capability at the Procedure step that needs it.
- **Exposure:** rule means the full instruction is presented on every task of every agent that receives it, with no human activation and no agent choice; a rule is not admitted because it is installed. Skill means the agent always sees a short description and chooses when to read the full body. Command means a human chooses when to invoke it. This follows the intended Claude Code sense of the three methods. Codex and OpenCode require harness-specific treatment for rules. The 0.1 rule design also allowed a scoped command-result rider; that delivery is not carried into this definition. An rbtv agent is reached through Slack (Ignite), `spark`, or `cast --agent`; `cast --rogue` launches a rogue agent file, which is not an rbtv agent.
- **Tool choice:** use executable software for exact, repeatable operations and model judgment for work that needs interpretation. A skill, rule, or command names the tool and the moment to use it. Placing the executable on `PATH` alone does not teach the agent when to use it. A tool reports success as status 0 and failure as any other status, so a caller checks the answer without reading prose.

## Memory

The owner declared the memory and folder-structure design complete and ruled its templates. The rulings below are in force.

- **Agent memory** lives in the agent's folder: a capped file of learned lessons plus topic files. Ignite injects the learned rules into every turn, as it does the agent's board. Topic files are read on demand. The agent discovers nothing; reliable recall comes from the runtime supplying it.
- **Only the shared dreamer writes long-term memory** — the agent's learned lessons and topic files, and general memory — working from the conversation transcripts Ignite already stores. The board is short-term memory the agent keeps itself; an explicit "remember X" and the owner's corrections are recorded by the agent at once. Every shipped system studied found notes taken during a conversation unreliable, and the transcripts already exist.
- **What the dreamer may change:** memory and the agent's own learned-rules file, freely; never `agent.md` and never rbtv source. A conflict goes to a digest for the owner. The agent learns from corrections without the owner editing anything, while a wrong lesson cannot rewrite the agent's instructions.
- **Always loaded into every Ignite turn,** timer wakes included: the general-memory profile, the agent's learned rules, the agent's board, the general-memory index, authored at setup and updated when its folders change (one row per folder, plus Workstreams), and the general-memory inbox. Workspace notes are supplied on a matching working directory; other memory is read on demand. Agent-memory systems studied converge on small always-loaded files plus an index; the owner counts the board as memory.
- **"Remember X" about the owner** goes to `inbox.md` in general memory, appended at once by any agent and seen by every agent; the dreamer removes only lines it filed or verified as already known. Appending cannot overwrite, and no agent asks the owner again. Length and malformed existing content do not refuse an append, since that would lose a "remember X"; past 20 bullet lines the owner is warned. Command or filesystem failure remains possible; append success is separate from warning delivery, as [Inbox](../ignite/capabilities/glossary/inbox.md) specifies.
- **Timeline:** daily and weekly timeline files, written only by the dreamer inside general memory, separate from the owner's own periodic notes, read on demand and never injected.
- **Moving Claude Code's own memory into rbtv memory** is one sorting pass: facts about the owner go to general memory; working lessons go to the learned rules of the agent that uses them, duplicates merged; notes about a repository or workspace go to its workspace file.
- **The dreamer** is one shared part of the ignite CLI that runs nightly and goes through the agents one at a time. It reads only messages past a cursor that only moves forward, and only after a durable write. The model proposes add, supersede, or archive; deterministic code validates and applies each proposal: an over-cap change is refused, never truncated; a file changed since it was read is not overwritten; no record disappears without a reason. Text that was injected, recalled, or written by the dreamer is never evidence. It archives, never deletes, and never edits `agent.md`; a conflict with the agent's instructions goes to the owner's digest. It stays silent when nothing changed, and a failure alerts the owner. Three reviewers agreed unanimously and the owner agreed.
- **Undo through git:** each agent's `memory/` folder and its `_artifacts/board.md` are tracked in git, changed paths are committed by a successful publication; applied writes already matching HEAD require no new commit. Any bad dreamer change can be undone without a backup scheme of its own. [Agent](capabilities/glossary/agent.md) owns which other agent files are shared.
- **Learned rules:** an owner correction becomes a learned rule without needing to be repeated, written when the dreamer has the required owner evidence; until then the board's watch-out covers it, and the conversing agent never writes learned rules. A lesson the dreamer infers on its own needs evidence from two separate conversations. Each learned-rule line starts with `[correction]` or `[inferred]`. The owner's word suffices; a single inference does not.
- **A memory file missing or broken when a turn starts** — broken meaning it fails the checking code — keeps its rejected working bytes. Ignite tries a checked committed copy and reports missing memory when none can be used; the turn continues. [Turn memory and recovery](../ignite/capabilities/runbook.md#turn-memory-and-recovery) owns the operation. Recovery must neither destroy unfiled work nor invent missing facts.
- **Expiry:** only a fact with an explicit end date ("until <date>") expires; nothing expires from disuse, so a temporary fact never becomes identity and a rarely used truth never vanishes.
- **Watchdog:** when enabled, it alerts the owner after 48 hours without a successful dreamer run.
- **One general memory per installation,** always at `.rbtv/memory/`; there is no location setting, so nothing extra is maintained or can drift.
- **General memory's index:** the always-loaded index, `<memory root>/_artifacts/index.md`, has one row per folder plus Workstreams, maintained when the folder set changes; each folder has a generated index of its files, read on demand, so the always-loaded part stays bounded. Memory indexes have no row cap. Dreamer publication includes changed general and agent memory. `workstreams.md` warns past 60 nonempty lines without a length refusal; malformed records can still be refused.
- **General memory's folders** (`.rbtv/memory/`) follow the Instinct article's ontology, adapted to what the owner's files actually contain. Always loaded: `profile.md`, `inbox.md`, and `_artifacts/index.md`, maintained when folders change. `entities/`: `people/`, `orgs/`, `places/` (geography only), and `devices/` (machines the owner and his agents operate). `knowledge/`: `facts`, `preferences`, and `decisions` (single files; a write that would pass a file's cap is refused and reported, and the file does not split), `self` (a distilled self-model), and `health` (only lines that change an agent's behaviour, pointing to the owner's notes; the always-loaded profile has no health section, and a health-driven constraint appears there only as the constraint). `workspaces/<slug>.md`: private notes about a shared repository or workspace. `timeline/daily/` and `timeline/weekly/`: written by the dreamer, linking to the owner's periodic notes, never copying them. `workstreams.md`: project/area lines point to their folder and board or state `board: none`; an agent subject names the agent and points to its board. No folder for communications: conversations live in Ignite's database.
- **Memory contains thin facts and pointers;** the content's own home stays canonical and is never copied. The transcription glossary stays where it is; people and organization files carry aliases and link to it.
- **General memory is seen by every agent,** with no per-agent grants or sensitive-topic restrictions (keep it simple; nothing needs them yet).
- **Rollout:** Ignite agents first; interactive harness sessions working in a workspace second, when Claude Code's own memory moves into rbtv memory and a pointer in folder instructions or a rule reaches them.
- **Private memory about a shared repository** lives in general memory, `.rbtv/memory/workspaces/<slug>.md`, loaded automatically when an agent works under that repository's or workspace's paths. A shared repository cannot contain one person's private memory, and this gives that memory one home.

- **The board** (`<agent folder>/_artifacts/board.md`) is the agent's short-term memory of what matters now, organized by subject and injected by Ignite into every turn; it follows the Instinct article. It points to threads, never the reverse: the agent notes a discussion that matters to a subject under that subject, with the thread's link, and Ignite never adds a thread to it. On every wake the agent reads it and knows what matters and where to resume or answer.
- **Board sections and their writers:** "What matters now" — one entry per subject (title, one to three lines of state, related threads, linked timers, link to detail), written by the agent through a short fixed form that code checks; an over-long entry is refused, never truncated. "Watch-outs" — the owner's corrections, recorded by the agent in the same turn (an owner fact accompanying the correction also goes to the inbox); the dreamer later folds them into the agent's learned rules. "Timers" — written by Ignite from its schedule database, never copied by hand. "Recently closed" — written by Ignite when the agent closes a subject.
- **Timers on the board:** the agent creates them itself on the owner's request (one-off reminders and recurring checks), as many as needed, and closes one when a wake finds its goal met.
- **The dreamer and the board:** the dreamer moves a subject's detail into a topic file in the agent's memory folder and keeps the board entry lean with a link; it learns from transcripts, not from boards. It writes the board only if the board is unchanged since it read it; otherwise it re-reads and retries.
- **Every board** — agent, project, or area — has the same four sections, empty when unused; closing a subject writes "Recently closed", and lines pruned from it are archived, never deleted. The Timers table sits outside the board's line cap.
- **Board safety:** deterministic checking code runs on every board write; no governance agent. Ignite flags subjects idle for seven days; nothing is deleted automatically. Caps are the implementation defaults below. Recently closed lines past the cap are archived, never deleted.
- Implementation defaults (owner not asked): Dreamer cursor is SQLite `rowid` with a run-start ceiling, advanced under the [publication conditions](../ignite/capabilities/runbook.md#dreamer-watch-outs-and-unread-messages), including applied writes already matching HEAD, with no new sequence column; late inserts are seen on the next run. Caps: board limits as defined in the [Board entry](../ignite/capabilities/glossary/board.md); profile 4,000 characters; learned rules 30; workspace memory 3,000 characters. Inbox is 20 bullet lines and workstreams 60 nonempty lines, with alerts at their thresholds rather than refusing valid appends or updates. Dreamer schedule and model: nightly at 03:00 America/Sao_Paulo, spawned from the daemon tick, only when `dreamer.enabled` is true in Ignite's configuration (off by default); the model is the `dreamer.model` setting, required while the Dreamer is enabled and for a run on demand, with no model in source used at run time; the [Dreamer runbook](../ignite/capabilities/runbook.md#dreamer) owns its fields. `ignite dreamer enable` and `ignite dreamer disable` change `dreamer.enabled` for the whole installation, and `enable` records `dreamer.model` when it is absent; their help tells agents to use them only on the owner's explicit request, with no access check, because the owner declined that complexity. `ignite dreamer run` runs the same pass once on demand, even while the nightly run is off. Migration: an installation whose configuration has `dreamer.enabled` true and no `dreamer.model` gets that key written before it runs this version, or its service refuses to start. Digest delivery: one Slack thread on the direct-message agent (`dmAgent`, currently `master`); later posts use `post --thread`. No digest when unchanged. Timer subject: `schedule add --subject` is optional; schedules without one render `none` in the board's Subject cell. Quiet-night liveness: at the 03:00 slot, if there is no unread owner row, due expiry, inbox item, or work to fold, record a successful run without calling the model and without sending a digest. An inbox line alone counts as work and may be filed with its own provenance as source. Conflict reporting: report each conflict in the digest once, not every night.

## Folder structure

- **Four folder types:** project or area; agent; rbtv folder (a module, component, or tool, including rbtv's core documentation); and collection (any other folder an agent maintains). A wiki keeps its own rules; a shared repository keeps its own and adopts rbtv's only by choice.
- **Conventions live in folder instructions,** never in a separate conventions file: any new convention is written into the folder instructions of the folder it governs, in the same change. Folder instructions reach the agent automatically; a second file would drift.
- **Boards and folder conventions:** preserve the workspace’s established layout. Authoring folder instructions does not itself require adding a board. Where an agent, project or area uses a board, its format is the board convention recorded above; task files retain the name the task tool requires. Conventions for additional folder types remain to be settled.
- **Optional folder artifacts:** add only those the workspace needs. Each artifact’s owning component defines its format and first-section convention; do not impose one template on every kind.
- **Nothing sits loose in a `build/` folder:** every file goes in a named subfolder, one per run or topic. The folder instructions of the folder that contains `build/` say so; no checking code enforces it.
- **Build history:** retain `build/`; completed and superseded work records live under `build/old/`, preserved intact with current references updated. A still-authoritative decision, active plan or product is not historical merely because its producing run finished.
- **Project and area overviews:** retain the workspace's named overview page for purpose, status and useful links. Folder instructions own reading and action conditions. If another current file owns execution state, link it rather than maintaining a second inventory. This does not introduce source-folder indexes. PARA remains in sb-os; broad application to other projects and areas is separate work.

- **Folder instructions contract:** use the current Folder instructions and Routing table entries. The body holds visit-wide facts and the table routes existing files, subfolders and artifacts by observable conditions. Do not impose a universal artifact directory or fixed line cap. Child instructions add to and do not contradict parents.
- **Write-time rules** live in the folder instructions, which every harness reads. A folder may add a harness hook as an extra, never as the only carrier: a hook fires only when the harness was started in that folder (verified: a Claude Code hook does not fire for a session started in a parent folder, and other harnesses do not run it).
- **The task file** keeps the workspace’s established location and the `<folder>-tasks.md` naming convention required by its task tool. Use `_artifacts/` only when that workspace already specifies it.
- **rbtv’s source folders stay in their documented layout.** `_artifacts/` is used only where the existing workspace convention specifies it; it is not imposed on every agent-maintained folder.
- **Folder routes:** name each needed target directly in the folder instructions. Do not add a sibling-file index to a folder artifact; preserve existing workspace conventions until a change to that workspace is authorized.
- **Routing rows:** the current Routing table entry owns the form of file-selection tables. Source folders have no index file.

## Ignite timers and threads

- **Every timer wake starts fresh,** bound to no thread. Ignite gives an agent one more ability: it can post into a named existing thread, and that post joins the thread's history, so the owner's reply there resumes the thread with its full history. A schedule is never re-bound to a thread. The owner's reason: the board, not the timer, tells the agent what to do and where to answer.
- **A wake passes only the name of the check that fired;** the board contains the check's details. With several checks on one board, a wake without content would make the agent infer which one is due.
- **Agents are taught one subject per thread:** reply in the thread whose subject your message continues; start a new top-level post only for a new subject. A board subject names its thread or threads when it has any; a subject may start with none, for example from a timer, because a thread is a consequence, not a cause.

## Ignite commands

- **The `ignite` command** contains what is unique to Ignite: `connect`, `disconnect`, `manage`, `turn`, `schedule`, `schedules-due`, `work`, `wake`, `post`, `board`, `remember`, and `dreamer`. `turn` moved from `cast` into `ignite`: its turn file and tests move into Ignite and use cast's shared launch files directly, nothing is copied, and `cast turn` leaves cast's help. The verb sits with its only caller; there is one copy of the launch knowledge. In 0.2 the command was `ignite-agent`, with `install`, `update`, `create`, and `create --remove`; the owner removed the install and update verbs, because an agent is managed by `rbtv agent`.
- **`ignite manage <agent> …`** is the one exception to one home per command: an Ignite agent has one place to manage itself. It has `add`, `remove`, `configure`, `update` (forwarded to `rbtv agent` for the agent itself), `models` (forwarded to `cast models list`), `list`, `search`, and `show` (forwarded to `rbtv`). It has no logic of its own: arguments and output pass through unchanged, and its help is taken from the originals, so nothing drifts.
- **Ignite's standard units** are the Ignite pack, turned on in the agent's `agent.json` (see the Pack bullet). The owner's choices stay in the agent's `files` and `packs`, so `agent.md` lists none of Ignite's units. To give the agent a unit, list it in `agent.json` or turn on its pack; a unit installed into its folder by hand is removed on the next `update`. The owner chose one source of an agent's units (ruling I1) over writing Ignite's units into each agent file, which would mix the owner's choices with Ignite's and leave dropped standard units behind.

## Module and component placement

- `core` is for rbtv's own operation, installation, configuration, and editing, and for the software that manages, runs, launches, and connects agents on any harness: the rbtv CLI with the provider accounts (`rbtv providers`), Ignite with its Slack connection and configuration, `cast`, and `spark`. `meta` is for how agents behave, communicate, plan, and coordinate work, such as the `plan` and `sub-agents` skills, with swarm and panel capabilities inside `sub-agents`. The owner placed `cast` in `core` because sub-agents and harness independence are central to rbtv, and Ignite there because it contains the Slack configuration. Other modules own their own subject areas; neither `core` nor `meta` is a catch-all. Only these two intrinsic modules receive module-specific glossary pages.
- This **reverses the 0.2 folder meanings**: in 0.2, `meta/` is about rbtv itself and `core/` is about general agents. The owner chose the inversion for 0.2.1 after considering both assignments. The reader pages use only the chosen meanings.
- Extend a component when its cognitive units and capabilities serve one coherent purpose; create a new one when the purpose is distinct. The owner chose this over grouping by shared audience, workflow, file type, or exposure method. 0.2 has exceptions, including `core/functions` (a pool of unlike conversational skills) and unrelated tool exposures under `meta/planning`; these are observations, not precedents for 0.2.1. This is a placement rule, not an authorization to reorganize existing components now.
- `core/rbtv`'s capabilities exist so that the `framework` skill (`skills/framework.md`) can teach agents to read and navigate them whenever they build skills, rules, commands, agents, tools, or other rbtv units. `meta/code` is the anticipated migration of the command-line work into a skill, `cli-creator`: an early test of how this documentation works in use; other cognitive units may follow.
- A capability lives in the component that owns its work. Workflow, scope and done-contract methods live in `meta/sub-agents/capabilities/`; callers route directly to their pages. Source-folder indexes are not used. Shared rbtv terms have one entry in the core/rbtv glossary; component-specific terms belong to their owning component’s glossary.
- The single navigation skill is `framework` in `core/rbtv/skills/framework.md`. It directly names the shared mandatory pages and conditional authoring pages for creation, editing, review and conversion. It has no intermediary capability index.
- The command-line experience of the `rbtv` CLI (its verbs, help, and output) is the reference for every rbtv command-line tool, and `cli-creator` was built from it. Every new or edited rbtv command-line tool follows `cli-creator`, and no edit lowers its standards. Until migration, hand-made loaders in the workspace's `.claude/skills/` and `.agents/skills/` point to the staged skill so it is followed now.
- Module and component names are nouns, never gerunds: `plan`, not `planning` (owner ruling). The 0.2 `meta/planning` component becomes `meta/plan`.
- Create a new module only when no existing module's purpose fits without stretching it. It may start with one component, but it must name a coherent area for future components. Decide the module, then the component, then whether any cognitive unit needs independent exposure.

## Principles

The principles act as rbtv's culture for agents: they guide how cognitive units, files, folders, memory, and folder artifacts are built. They exist to shape the agent's context window, so the model hallucinates and drifts less and reasons better. No one reinforces them, so each must state its own practical consequence.

Working records behind these choices: the principles audit (terminology clashes, overlaps and tensions, where each principle applies, candidate implications), the principles provenance record, and the external research on actionable principles, all working records of the 0.2.1 migration project.

- Each principle starts with a plain, testable design choice and the case where it still applies despite a competing convenience. Its method and checks help reject a broken design without requiring arbitrary sections in every result. Use the glossary-writing guide’s flexible organization; there is no mandatory Statement/Rationale/Implications shape.
- Principles guide how structure is defined; they never define the structure themselves. An implication is a test the builder applies to its own design, not a piece every design must contain. Every implication was swept against this rule and ruled by the owner one at a time; the rulings are in the principles sweep, a working record of the 0.2.1 migration project.
- State the tradeoff in natural language, not the formula “X, even over Y.” An observable test must distinguish designs that satisfy the choice from those that do not.
- Explain a principle’s context-window effect where that fact is needed to apply the choice or prevents an evidenced mistake. Do not append the same generic rationale to every instruction.
- A principle gives the builder usable decisions and design tests. It does not prescribe a running agent’s task-time behavior; that instruction belongs in its appropriate exposure method.
- "Task" is the one term for a piece of work given to a human or an agent, and has its own glossary entry. It replaces request, job, assignment, unit of work, seat, session, run, and execution (section 1b of the principles audit, a working record of the 0.2.1 migration project). The owner chose "task" because it is the same thing a task list contains, whether a human or an agent does it, which keeps human and agent work in one vocabulary (Agent parity). The deleted 0.1 task-goal cognitive unit stays deleted; a task states its goal in ordinary language.
- Micro agency gives each task and each cognitive unit one purpose whose result can be judged alone. An unrelated second purpose is a second unit. The principle owns the parallel-run limit: independent tasks run in parallel only when no two of them change the same file or record.
- Progressive disclosure supplies content when needed: skills by agent selection, commands by human invocation, rules by installation with task-time action conditions, folder instructions by location, and capabilities through conditional routes. Do not treat always-present rule text as always-required action.
- Folder instructions route the agent to the right file at that moment. That routing is what sets them apart from a rule, which travels with the agent into any folder. [Folder instructions](capabilities/glossary/folder-instructions.md) owns authored and generated files, inheritance and harness loading; [rbtv CLI](capabilities/glossary/rbtv-cli.md) owns generation and configured limits. Keep each file compatible with its parents and put only visit-wide information in the body, with conditional routes for other work.
- A skill, command, rule or agent description uses the four labeled fields in Routing table. Its concrete-kind entry defines selection and input requirements. Keep the distinguishing content and result first so the selection boundary survives listing limits. Module and component boundary descriptions follow their own entries.
- A principle lists implications only for the areas it actually changes, not a fixed checklist of areas.
- Merges are allowed: if two principles produce the same implications, propose merging them for owner approval. The candidate overlaps and their proposed owners are in section 2 of the principles audit, a working record of the 0.2.1 migration project.
- Each shared implication has one owning principle, following section 2 of the principles audit, a working record of the 0.2.1 migration project. Single source of truth owns "one implementation behind every way to perform an action", "one shared home for content that multiple units use", and consistency between files: a text never states a fact differently from the file that owns it. The owner placed that requirement in this principle and not in a rule about how a text is worded, because it concerns what a text says, not its wording. Agent parity owns "an agent can reach every action". Deterministic first owns "exact steps go to tools" and making tools known to agents. Keep it simple breaks ties.
- The parity principle is named Agent parity. It covers any software that humans and agents both use, not only the state rbtv manages: both reach the same operations through their own interfaces. An agent reaches an rbtv action by editing the same file a human edits, or through a tool when the action is more than a file edit, so the principle is not about command-line tools alone.
- "Workflow" is defined in the glossary: a set of tasks arranged as a DAG, run by sub-agents through `cast`, running at the same time every task whose needs are met except tasks that change the same file or record. It is written in `workflow.md`, which replaces 0.2's `seats.md`; the coordinating agent reads it and launches the ready agents. The owner chose a file only agents read, because no CLI needs to read it; a machine-readable file with a `cast` command that launches and monitors every ready agent was considered and not adopted. The principles still use no term such as "handoff"; one task's result being used by another is described in plain words.
- Compound engineering is not a principle. Its content moved to the compound engineering memory draft, a working record of the 0.2.1 migration project, to be designed together with `.rbtv/memory/`.
- Agent tooling is merged into Deterministic first. Both covered tools for agents, and one implication, naming the tool in the step that uses it, appeared in both.
- A principle shapes the system; an instruction about an agent's conduct during a task is a rule, never a principle ([glossary](capabilities/glossary/principle.md)). Always verify is therefore a rule, not a principle, and so are the former last implications of Deterministic first (check the installed tools before scripting) and Terminology is king (use glossary terms with humans). Their rule texts are drafted in the rule drafts, a working record of the 0.2.1 migration project until the component that contains them is chosen.
- Agents as teammates, Capabilities first, and Harness and provider agnostic are deleted. Of their implications, only two are kept: the clean-boundary test (a capability relies on nothing beyond what its user passes to it) is in the [capability guide](capabilities/glossary/capability.md), and the carry-over test is an input to the memory design (Open decisions). The rest, including the term "provider", are dropped.
- Principle texts use 0.2.1 terms only, such as no "seat" in Micro agency. The full list of clashes is in section 1 of the principles audit, a working record of the 0.2.1 migration project.

## Migration

- The 0.2 `core/coding` component moves into the `meta/code` component.
- The modules outside `core` and `meta` (`web`, `office`, `innovate`) are converted to the 0.2.1 layout mechanically, with a one-off script, in the same change as the installer's new reader, so the installer has one reader and no second format.
- The mechanical conversion removed every frontmatter key no schema allows (the 0.1 names `inputs`, `outputs`, `outcome`, `id`, and the unread 0.2 hints `tags` and `exposes-cli`), moved each component's `component.md` into its `capabilities/`, and deleted `module.md`; the descriptions live in the JSON records, and the rest stays in git history. The owner accepted it.
- The installer checks frontmatter and JSON records against the schemas with a small validator in its own code, covering only the schema keywords the templates use; it adds no outside dependency.
- The 0.2 `build` skill leaves the plan component now, and the plan component's `references/` are retired: the `plan` skill points to the build documentation (glossary and guides) where it pointed to those references. The file-by-file review (the plan references review, a working record of the 0.2.1 migration project) found two things the build documentation lacked, now carried into the agent and capability guides: no installation-specific value (channel id, path, account, host, credential) is typed into a prompt or capability, and an agent that runs without a person never waits for a result after its turn ends. The other nineteen files are covered, a deleted 0.1 concept, or an obsolete 0.2 mechanism.
- Components in this migration (owner rulings on the component table, a working record of the 0.2.1 migration project): `acct` becomes the verb group `rbtv providers` in `core/rbtv`; there is no `acct` command and no alias (owner, 2026-10-07); the Slack and Google tools (`stools` wrapper, `gtools`) and the `google-workspace` skill move to `meta/communication`, and Ignite installs them as standard units; `innovate/brand`, `innovate/conception`, `innovate/validation`, and `web/research`, which had no record in 0.2 but contain content other files point to, each get a `<component>.json` and become components with capabilities only.
- cast's file of the models it can launch is `supported-models.js`, renamed from `catalog.js`. The owner keeps three names for three things: "supported models" for what cast can launch, "model catalog" for an installation's table of models with their routing columns, and "source catalog", always written in full, for rbtv's list of components (owner, 2026-10-07). cast's glossary, `core/cast/capabilities/glossary/`, defines model catalog, supported model and selected model; provider and saved login are defined in rbtv's Provider entry, because `rbtv providers` owns them.
- Retired in this migration: the 0.2 `create-cli` skill (it overlapped `cli-creator`), and the `component-lint` and `capability-cards` tools (they read `exposure.csv`, and `component-lint` checked 0.1 shapes). Checking that a component follows the format is the installer's job: its schema validation and `rbtv doctor`.
- The 0.2 `create-primary-agent` skill's content moved into the building guides for creating an agent in `core/rbtv/capabilities/`, and the `create-agent` skill is retired. The `master` agent selects the `framework` skill instead, which routes any building request to the right guide. The 0.2 `workflow-authoring-checklist` skill is retired too: the workflow glossary entry, guide, and template cover writing a workflow.
- The 0.2 installer installs no dependencies. `package.json` stays in the four components that have it, untouched, because its `check` and `install` commands are the data a future dependency installer needs; that installer is not built in this migration (Open decisions).
- A tool's `entry` names its CLI inside its component, or uses `ws:` for a CLI in another repository of the installation, relative to the installation root. Any tool may use `ws:`; `gtools` is one example.
- Harness-native sub-agent files are generated from the same `agents/<name>/` source as rbtv agents. Claude Code and OpenCode receive Markdown pointers; Codex receives its native agent TOML file. The source has no separate `sub-agents/` kind.
- Kept from 0.2: generated files name source files by an absolute path, in a copy's links and in a sub-agent pointer; the installer keeps listing the files it generates in `.git/info/exclude`, so each machine regenerates its own and the absolute paths stay right.
- Agent commands: `rbtv agent add <agent>` installs what the agent's `agent.json` declares, the first time or again, plus any units named; `rbtv agent update <agent>` makes the folder match the file; `rbtv agent remove <agent> <unit>...` removes units; `rbtv agent configure <agent>` changes harness, model, or effort, checks them against `cast models list` (run from the agent's folder, so the model must be one that agent's installation selected), and regenerates files when the harness changes; `rbtv agent list` shows the agents. `rbtv agent` is a verb group, so an agent never collides with a unit verb; `spark <agent>` runs one interactively. Each verb takes the agent as a name or a folder path. The agent folder's ignore file is `.gitignore`, listing the database (`state.sqlite*`), `turns/`, and each conversation's harness session files (`conversations/*/session*`); conversation history stays shareable. The units an agent has are installed into the agent folder itself, so its hooks and MCP servers land in the agent folder's own harness files. `update` removes generated files the file no longer accounts for; it keeps `settings.json` and live data. `remove` takes back only what the installer wrote and keeps `agent.md`, `agent.json`, `settings.json`, and everything the agent made, following the installer's rule that it deletes only its own files. An effort given as a number from 1 to 5 is stored as the model's own effort word, and `inert` for a model with no effort setting.
- Hooks use Claude Code's event names, which Codex shares, with the fields event, optional matcher, command, and optional timeout; OpenCode receives no hooks. OpenCode's equivalent is a plugin, a JavaScript file loaded from `.opencode/plugins/`, not a settings entry; the owner translates a hook only where the harness takes a settings file, so none is generated for OpenCode.
- An MCP server's secrets reach each harness as the environment variable's name in that harness's own form: `${VAR}` for Claude Code, `{env:VAR}` for OpenCode, and Codex's forwarding list, which works only when the server's variable has the same name as the environment variable (otherwise the installer refuses it for Codex). rbtv never writes a secret: a server that logs in through the browser has its token stored by the harness, and an API key stays in an environment variable. One shared record serves all three harnesses.
- `cast` hands Codex its prompt as developer instructions on every platform. On Windows it starts Codex's executable directly, not through the `.cmd` wrapper, whose command-shell quoting breaks on characters such as `&`, `|`, `<`, `>`, `^`, `%`, and quotes; the same launch fixes every harness on Windows. Owner's reason: both platforms work the same way. This is true of every `cast` launch that carries a system prompt, not only Ignite's turns. Verified against the harness documentation: Codex forwards an environment variable by name through `env_vars`, and its `env` values are taken literally; OpenCode expands `{env:VAR}` in its configuration when it loads it, and an unset variable becomes empty.
- Each tool's CLI moves into its tool folder for the modules migrated now, `core` and `meta`. In `office`, `web`, and `innovate`, each tool's `entry` points to its CLI where it already is, inside its component, until those modules are migrated.
- `embed-search` and `control-panel` are not migrated now: their folders move, as they are, to the project's `_backlog/`, and their installed skill and commands are removed from the vault.
- Ignite's commands are verbs of `ignite`: `connect <agent> (--channel-name <name> | --dm) [--schedule-json <file>]` (on the machine that will run it: turns the Ignite pack on through `rbtv`, connects the Slack channel or direct messages, writes the route in that machine's `config/ignite/config.json`, and creates the board, the database, and the `conversations/` folder), `disconnect <agent> [--archive-channel]`, `manage`, `turn`, `schedule`, `schedules-due`, `work`, `wake`, `post`, `board`, `remember`, and `dreamer`. They replace 0.2's `ignite-agent install`, `update`, `create`, and `create --remove`.
- Ignite's standard units reach an agent folder as ordinary units of the Ignite pack, recorded in its `agent.json`. The `agent_units` record lists the units the agent has, so `rbtv agent update` removes only those the file drops, and `ignite connect` turns the pack on and creates the working files. The owner chose one source of an agent's units (ruling I1), as recorded under Ignite commands.
- `cast route --batch` names its input list `agents`, not `seats`: the word seat is retired.
- `cast`'s forms: `cast --agent <agent>` runs an rbtv agent from its folder with its `agent.md` as the system prompt. It takes no harness, model, or effort, because it always uses the agent's own, from `agent.json`; its other arguments are as in 0.2. `cast <harness> <model> <effort> [<folder>] (-p <text> | -f <file>) --rogue <agent file>` runs a rogue agent with the file's body as its system prompt; the caller passes harness, model, and effort, chosen with `cast route`.
