# Documentation decisions

The standing choices and comparisons behind the 0.2.1 reader pages. The [overview](capabilities/rbtv.md), `glossary/`, [Building guides](<capabilities/_under-evaluation/guides/procedure documents/choosing-what-to-build.md>), and `principles/` state the chosen design directly.

## Editorial decisions

- Write in English, call the product **rbtv** in lowercase, and make the overview short enough for a human to review end to end. Describe the intended 0.2.1 design as the design itself; keep migration notes here.
- Define rbtv once, in `rbtv.md`. Keep one glossary file per surviving rbtv concept or named structure. Explain general terms and the harness names Claude Code, Codex, and OpenCode inline rather than creating glossary pages for them. The one exception is `context window`: rbtv exists to shape it, so it has an entry, and that entry also holds hallucination, drift, and their four causes (context load, context gap, cognitive load, context poisoning) rather than giving each its own page.
- "Part" is not a term. Do not add a glossary entry for it, for "prompt part", or for "task part". A glossary entry would freeze several meanings under one name. Where a sentence means what a component contains, name the cognitive unit, capability, or tool. Where it means what a folder exposes, name skill, rule, command, or agent. Where it means the units listed in `glossary/prompt.md`, write "cognitive units of a prompt". Where it means scope and done contract, write "cognitive units a task carries". Plain English may say "piece". Do not use "part" for either.
- Link terms from the overview. Use ASCII diagrams for its two folder layouts and lists where they make the glossary easier to scan. Keep the settled principles in separate, self-contained files under `principles/`.
- Consolidate every view of an agent (the rbtv agent, the Ignite agent, the rogue agent, the sub-agent, and the agent file) in `glossary/agent.md`; do not create parallel entries for these views. Keep the installed `.rbtv/` folder distinct from the product rbtv.
- Say "folder", never "directory", matching the term folder artifact.
- The commands use the words **unit** (not item) and **installation** (not workspace), in help, results, refusals, and JSON field names (`units`; Ignite's flag is `--installation`). The state words `installed` and `not installed` stay, and "workspace memory" keeps its name. A retired command name has no working alias and no message that it moved.
- This project's folders keep one hand-written folder instructions file each, `CLAUDE.md`; the installer generates `AGENTS.md` from it. The owner dropped the earlier hand-kept `AGENTS.md` copies (never tracked: git ignores every `AGENTS.md` in the vault) because the installer refuses to overwrite a file it did not write, which blocked every install in the vault, and because the 0.2.1 design has the author write one basis file.
- The release is called **rbtv 0.2.1**. "Ignite" names only the `core` component that connects rbtv agents to Slack and wakes them, and its command `ignite`; the owner chose to keep the name for the component and drop it for the release, so one name has one meaning.
- Respect the owner's deletions. Do not recreate glossary entries for `agent type`, `reference`, `permissions`, `restrictions`, `resources`, `input`, `output`, `outcome`, `i/o spec`, or `task goal`. Those are 0.1 names, not cognitive units of a prompt. A task can still state its goal in ordinary language.
- Every standard file, folder, cognitive unit of a prompt, and cognitive unit a task carries has a building guide, as rule 2 of [`CLAUDE.md`](CLAUDE.md) requires. `guides/guides.md` lists them all, including guides in the capabilities of the component whose units use them, plus the guide for choosing what to build. There are no guides for deleted entries. A guide has no building guide of its own: it has a glossary entry and a template, and the template is the shape, so a second guide would restate it.
- Every guide uses one shape: one sentence saying what the unit is and linking its glossary entry; then Purpose, What good looks like, Making it good, and Traps. Purpose says what the unit is for and what fails without it, in a few lines. What good looks like holds tests a reviewer can pass or fail. Where a test comes from a principle, the bullet links the principle and states the test for that unit; it does not restate the principle. Making it good says how to reach those qualities; it is step-by-step only where writing a section needs it. Traps records only a trap a named source has shown; omit the section when none remain. Hand-authored units use that full shape. A file the installer creates stays a few lines: what it is for, that it is not hand-written, and what a good one shows. Those files are the thin loader, `config/`, `runtime/`, `.rbtv/` itself, `install.json`, `agent.json`, and Ignite's `config/ignite/config.json`. `mirror/` is hand-authored source inside the installer-created folder, so its guide is full.
- Choosing between kinds of unit lives only in `guides/choosing-what-to-build.md`. Each other guide's Purpose links that file and does not compare kinds. Three guides route rather than build one unit, so they do not use the fixed shape: that choosing guide; `guides/building-from-a-conversation.md`, which turns a conversation that just happened into a unit; and `guides/documenting-a-change.md`, the one home for which documents change when anything in rbtv is added, changed, renamed, or removed, including a new kind of thing (which needs the owner's agreement first). The repository's root `CLAUDE.md` does not list documentation duties itself: its rule sends every change in rbtv through the `framework` skill's entry file, `core/rbtv/skills/framework.md` — read directly, so it applies whether or not the skill is installed — and through that guide, so the duties have one home and the always-loaded file only carries the trigger. The latter carries the method of the outside Skillify skill (read the conversation first, then interview in rounds, show the draft before saving), translated into rbtv's units, templates, and installer; it hands over to the choosing guide and the unit's own guide instead of restating them. The owner retired the Skillify skill from the mirror once its method lived here, and the `framework` skill names the guide, so a request such as "turn this conversation into a skill" reaches it. The guide's name avoids "capture", a skill with another meaning, and "session", which these pages do not use for a piece of work.
- Guides do not state file mechanics: where a file goes, what the installer generates, frontmatter fields, or a template link. Those live in `rbtv.md`, one line each with a link. `rbtv.md` stays a concise navigation index, short enough for a human to review end to end.
- `guides/`, `principles/`, `glossary/`, and `templates/` each have an index file named for that folder (`guides.md`, `principles.md`, `glossary.md`, `templates.md`), listing every item in that folder with the moment to open it. Agent-maintained folders use `_artifacts/index.md` (Folder structure). The guide and template indexes also list building entries in other components' capabilities. The index does not list itself.
- Building guides in `core/build` live in `guides/`, not `build/`, because `build` is the name of the `core/build/` component that holds them; one name, one meaning. A guide may instead live in the capabilities of the component whose units use it, while `guides/guides.md` keeps its route.
- `templates/templates.md` lists both kinds of shape: **templates**, the agent-readable shape of a file (a cognitive unit), and **schemas**, the code-readable shape (a JSON Schema, `<name>.schema.json`). Schemas stay in `templates/`; a template may live in another component's capabilities when its units use it. The owner kept templates and schemas together by default because one file can follow both: an agent, skill, rule, or command file's body follows its template and its frontmatter its schema, and a folder instructions file holds the rbtv command's marked sections, which follow a template, beside the author's own text. For those files the template keeps a filled frontmatter example and the schema is the authority for the fields: the rbtv command validates every file's frontmatter against its schema and refuses a mismatch, and the template guide tests that the template's frontmatter keys equal the schema's, so drift fails loudly. Every exposed cognitive unit, and every tool, carries its own name and description, so the rbtv command can present it without a separate list: skills, commands, and rules in frontmatter, harness-native sub-agents in frontmatter, and tools in `<tool>.json`. A skill or command description is short: its first sentence is enough to decide whether to open or invoke it, and the rest names the situations and one similar case that must not. A rule description states what every agent that receives the rule does on every task; it names no case to skip. An rbtv agent's description is in its `agent.json`, not its prompt. The [`<tool>.json` schema](capabilities/templates/tool-json.schema.json) holds a tool's name and one-line description, because a program has no frontmatter; `<tool>.json` is used, not `<tool>.md`, because the index file is `_artifacts/index.md` (a wiki keeps its own index names), so `<tool>.md` would collide with neither a unit nor that index. Every file the system needs in order to work that has a fixed shape gets a schema here, including files only programs read: [`install.json`](capabilities/templates/install-json.schema.json), [`agent.json`](capabilities/templates/agent-json.schema.json), and Ignite's [`config/ignite/config.json`](capabilities/templates/ignite-config.schema.json). The owner's reason: the documentation defines what the system needs to work, and defining those shapes here is what keeps it consistent, even for formats only a program writes. They stay in this folder until their components (Ignite and the rbtv command) are staged. The `install.json` schema describes the root's record, including component source `tree`, ownership claims, and PATH links; it omits `path_bootstrap`, which the rbtv command does not write. The `agent.json` schema describes an agent's file: the author's fields and the record of what was generated. The `ignite/config.json` file drops two 0.2 `ignite.json` fields: `defaultLaunch`, because whoever adds an agent must choose its harness, model, and effort, and `workspace`, because the file's own place under the installation root already gives it. Files the rbtv command generates that agents read have templates too, because their shape is rbtv's decision: the [thin loader](capabilities/templates/thin-loader.md) and the rbtv command's parts of a [folder instructions](capabilities/templates/folder-instructions.md) file (a component's marked section, the agent section, and the header of a generated copy). Codex and OpenCode receive each rule's full text in its own labeled section of root `AGENTS.md`; the [folder instructions template](capabilities/templates/folder-instructions.md) shows that section. The guide template also holds the short shape for files a program creates. There is no template or schema for a tool's program (it is code), `runtime/` data or an agent's live data (written only by programs while they run), `memory/` (undefined), a capability, or the author's own text in folder instructions (no fixed shape).

## System and installation decisions

| Choice for 0.2.1 | Comparison or reason |
|---|---|
| rbtv supplies its own concepts for modules, components, cognitive units, and exposure. The installer translates them for Claude Code, Codex, and OpenCode. | The three harnesses have corresponding primitives but different installation formats. The overview should explain the common design, not give three separate authoring systems. |
| Each component has `<component>.json`, named after its folder, with its description and external software dependencies, in the fields `description` and `dependencies`. It records no exposure methods: the folder a skill, rule, command, sub-agent, hook, or MCP server sits in (`skills/`, `rules/`, `commands/`, `sub-agents/`, `hooks/`, `mcp-servers/`) decides its exposure. | `exposure.csv` is the current 0.2 exposure source; `component.md` separately describes a component; 0.1/Ignite 0.1 used `package.json` for external dependencies. The description and dependencies are consolidated in one record, and the owner dropped a separate exposure list because the folder already states it, which keeps one source for each fact and simplifies the installer; `component.md` ceases to exist in the intended layout. The record is named `<component>.json`, not `component.json`, so that all folder artifacts follow one naming pattern. Whether the installer installs external dependencies is not yet decided. |
| A component has no front page: no `capabilities/component.md`, and no `capabilities/capabilities.md` required as an index. `<component>.json` describes the component; anything agents need lives in the component's capabilities or is dropped. A component may still have its own capability pages, such as the `rbtv` component's `capabilities/capabilities.md`, by choice. | Owner ruling (KISS, YAGNI): in 0.2 `component.md` was the component's description and the `rbtv` catalog's entry point; after the move to `<component>.json` it duplicated the record. Every remaining `capabilities/component.md` is deleted, its useful content folded into the component's capabilities first. |
| The `rbtv` command has no catalog: no `rbtv`, `rbtv <module>`, `rbtv <module> <component>` drill levels and no `--rules`. Its verbs have no install level: `add`, `remove`, `update`, `list`, `search`, `show`, `doctor`, `selftest`, and `agent`, which manages rbtv agents. `spark` is not one of them: it is its own command in the `cast` component. Modules, components, and their units are browsed with `rbtv list`, which shows each with its description. The root help lists `agent` as one line that says when to use it; its verbs are in `rbtv agent -h`. | Owner ruling (KISS, YAGNI): the catalog duplicated `rbtv list` and was the only reader of `component.md`. Owner ruling: in 0.2 the verbs sat under `rbtv install`, and `spark` was one of them; the owner removed the install level so that `rbtv` names the command, and placed `spark` in `cast` as one small tool with its own shortcut on `PATH`. |
| Folder artifacts are standard files a folder can hold, each serving one fixed purpose. They give a folder a structure agents can navigate and store configuration about that folder. They live in a visible `_artifacts/` subfolder of their folder, under plain names that say their purpose, such as `decisions.md` or `board.md`, so one template serves an artifact in any folder; only the folder instructions file stays at the folder's top level (owner ruling: folders stay clean and nested; a dot-folder would be hidden in Obsidian and skipped by default by ripgrep and by sb-task's discovery, and the path already names the folder). The index file is `_artifacts/index.md`, a plain name like every other artifact. A wiki's index files are the exception: they keep their current names, so the wiki's links by file name keep working (owner ruling). An agent's board is `<agent folder>/_artifacts/board.md`. rbtv's own JSON records stay where they are — `<module>.json`, `<component>.json`, `<tool>.json`, an agent folder's `agent.json` and `settings.json`, and the root's `.rbtv/config/install.json` — because programs read them: they are records, not navigation artifacts. Each kind of folder has its own set: rbtv's module, component, and tool folders use their JSON record, `<module>.json`, `<component>.json`, or `<tool>.json`, and no index file; the sets for other kinds of folder are open. `rbtv.md` shows them in their own section with a diagram of a generic folder. | The owner chose "folder artifact" over "artifact", which also means build outputs and Claude's published pages. The index file takes a plain name because the path already names the folder, and one template then serves every folder's index; `README.md` stays out (human-facing by convention). The index file stays out of the component diagram because `<component>.json` already describes the component. In 0.2, a module was described by `module.md` and a component by `component.md`, read for a `description:` line; the owner replaced both with JSON records and dropped index files for modules, components, and tools, because the record already carries the description. **Caution:** renaming a folder without renaming its folder artifacts silently breaks them, so the installer must report a component folder without its `<component>.json` as an error, never skip it. |
| A component uses `skills/`, `rules/`, `commands/`, `agents/`, `sub-agents/`, `packs/`, `hooks/`, `mcp-servers/`, and `capabilities/`; tools sit in `capabilities/tools/<tool>/`. Each skill, rule, command, and harness-native sub-agent (`sub-agents/`) is one file, `<name>.md`, whose frontmatter `name` equals the file name. An rbtv agent in `agents/` is a folder holding `agent.md` and `agent.json`. A pack in `packs/` is one file, `<name>.json`, listing its units. Each hook and MCP server is one file, `<name>.json`, in rbtv's own format, which the installer translates into each harness's settings. Hooks and MCP servers are not cognitive units: like tools, they act outside the context window, but each has its own exposure method and so its own folder. A tool's `<tool>.json` names its program in `entry`. | The 0.2 component layout was less regular and kept tools in a separate `tools/`. `references/` is retired in favor of `capabilities/`. The owner placed tools inside capabilities because a capability is the one place for everything a component's cognitive units share. Harness-native sub-agent files are translated into all three harnesses' own formats, and an rbtv agent is never translated into one. The owner kept hooks and MCP servers (one MCP server, Chrome DevTools, is in use), moved them into their own folders with an rbtv format, and kept shareable self-contained skills only in the mirror (next row). |
| Skills and commands get thin loaders; rules are installed directly; tools are installed on `PATH`. | Skills and commands are read only after an agent or human selects them. A rule must reach the agent in full without selection. The `PATH` location varies by machine and operating system, so the installer handles that difference. Harness exposure can also tell agents when and how to use a tool. |
| The author writes one folder instructions file per folder — the basis, chosen when installing (the installer's basis setting, `CLAUDE.md` or `AGENTS.md`). The installer generates the other harness copies from it. Guides name the file by its role, never by a harness file name; the glossary states the names. Edit the basis file and run the installer again; never edit a generated copy by hand. Folders the installer does not walk — a nested git repository, an excluded path — get no copy by design. | The harnesses already load those file names. One authored file plus generated copies keeps one source without a third filename. Both copies exist on purpose; the generated copy is not a second source. Skipping non-walked folders is the user's choice of what to ignore, not a gap. |
| A component can ship folder instructions from a `folder-instructions/` source folder, sixth beside `skills/`, `rules/`, `commands/`, `capabilities/`, and `agents/`. Its files are flat; each names its target folder, relative to the installation root, in its frontmatter `target`, which the installer removes before writing the text. In the target, the component owns only a marked section inside that folder's folder instructions file, labeled with its module and component; two components targeting one folder each own their own section. Text outside the markers is never touched. The installer recreates a missing section; an incomplete, duplicate, or reversed fence pair stops the install. | Proven precedent: sb-os's marker-section model, where the installer rewrites only inside a marker pair and aborts on a missing marker (the i4 sb-os managed blocks working record of the 0.2.1 migration project). The owner chose flat files with the target in each file's own frontmatter over a mirrored folder tree and over a separate mapping file, so each file is its own single source. In 0.2, `agents.md` rows were listed as "guidance parts" inside the root section instead. |
| An installation has `.rbtv/mirror/`, `.rbtv/config/`, `.rbtv/agents/`, `.rbtv/runtime/`, and `.rbtv/memory/`. An rbtv agent may live in any folder; `.rbtv/agents/<name>/` is where `rbtv agent` finds an agent by name. | By owner decision (12), an agent folder lives anywhere and is addressed by its path, because a plan's agents belong inside the plan folder. In 0.2 every agent lived in `.rbtv/agents/`. Runtime data and memory are part of the installation alongside mirror and config. Memory's behavior is in the Memory section. Glossary entries name full paths, including `.rbtv/config/` and `.rbtv/mirror/`. |
| A unit is built in rbtv when it is general — usable by any user, with no value belonging to one installation — and ships through the rbtv repository; a local rbtv-format component is built in the mirror when it belongs to this installation only (a personal workflow, an installation-specific value, or an experiment); an imported or shareable self-contained skill also lives in the mirror and never in the rbtv repository; the installer exposes both the same way (owner ruling, stated in the choosing and mirror guides). A mirror component with the same module and component name replaces the shipped component as a whole. Local components use rbtv's format. The mirror alone also holds `_skills/<name>/` for self-contained skills in the standard shareable format. The installer lists each one and installs a thin loader to its `SKILL.md`, carrying that file's frontmatter. The loader is tracked in `install.json` so `rbtv update` and `rbtv remove` manage it; when the source is a git repository, `git pull` takes effect immediately through the loader. | The 0.1 mirror used file-by-file shadowing. The owner chose the simpler 0.2 whole-component substitution over it. Files from the two components are not merged. The `_skills/` exception lets users import someone else's skill or write one for sharing while rbtv's own skills retain their entry file and capabilities structure (owner rulings J0 and J1). In 0.2, `_skills/` was the older name of `_hub/skills/`, and `_hub/` also held commands, rules, hooks, and other kinds; 0.2.1 keeps only `_skills/`. |
| An rbtv agent's file is `agent.json` beside its `agent.md`: its description, harness, model, effort, voice, chosen units and packs, and the record of what the installer generated. The agent file holds no harness, model, or effort; whoever adds the agent must choose all three, and they are stored in `agent.json`, the one live source. Only `rbtv agent configure` changes them, including from Slack. `cast --agent <agent>` always uses the agent's own harness, model, and effort, with no override on the command line. | In 0.2, Ignite's create step took them as flags and `ignite.json` carried a `defaultLaunch`; `launch.json` held them in the agent folder, and `cast --agent` only checked that it existed. The owner moved them into `agent.json` so the value has one home and every launcher reads it the same way. |
| `rbtv agent add <agent>` installs an rbtv agent in place: it reads the agent's `agent.json` and generates, inside the agent's own folder, the folder instructions with the agent section, the folder artifacts the agent defines, the harness files for the units its file lists and the packs that are on, a `.gitignore` for its machine data, and the list of what it generated. Nothing is copied. `rbtv agent update <agent>` makes the folder match `agent.json`: it generates what is missing and removes generated files the file no longer accounts for, which is what a second machine runs after `git pull`. `rbtv agent remove <agent> <unit>...` removes the named units and their generated files. `settings.json` and the agent's live data are never touched by these verbs. Adding a shipped agent places a copy of its folder in `.rbtv/agents/<name>/` first. | In 0.2 an agent was built by `ignite-agent create` with its own install record in `install.json`, and a shipped agent was copied in on install. The owner made installing an agent an installer job for every agent, not only Slack ones. `agent.json` replaces the separate record, and `update` reconciles the agent as the root's does. |
| An agent folder is self-contained: all its live data stays in it, so it can be its own git repository and be shared between installations. `agent.json` holds nothing tied to one machine (no absolute path, no timestamp), so it is shared with the agent; the generated files are rebuilt in each installation, never shared. The root's `install.json` stays on its machine. The installer writes an ignore file that keeps machine-bound data (the database and turn files, which hold harness session ids that exist only on the machine that created them) out of git; the user may override it, which is safe only when one machine runs the agent at a time. An agent's live data is the one exception to "data created while a component runs goes under `.rbtv/runtime/`". | 0.2 already kept agent data in the agent folder. The owner chose self-containment so an agent can be shared through git; an agent is identified by its folder, not by a fixed place. |
| An Ignite agent is an rbtv agent with the Ignite pack on and a Slack channel that wakes it. The pack is a named list of units declared in a component's `packs/<name>.json`; the Ignite pack, `core/ignite/packs/ignite.json`, holds the nine standard Ignite units, among them the Slack message formatting skill, which stays in `meta`. `ignite connect` turns the pack on through `rbtv` and connects Slack, on the machine that will run the agent: the route lives in that machine's `.rbtv/config/ignite/config.json`, never in the agent folder, and only one machine connects a given agent. Ignite connects only agents under `.rbtv/agents/`. `ignite disconnect` removes the route and turns the pack off. Ignite's waking program runs from a deploy worktree fixed at a commit and changes only when a deploy runs it at a new commit. The concept is unchanged by owner ruling: a Slack channel wired to an agent folder, one turn per message, a thread reply continues its conversation, a new channel message starts one, and timers wake the agent. | In 0.2 the Ignite install step ran `rbtv install` and added the standard units, so a plain install left them out; one `ignite-agent create` did both, and the routes lived in `<workspace>/.rbtv/agents/ignite.json`. The owner made the pack a generic list held in data, so `rbtv` holds nothing specific to Ignite. |
| An rbtv agent runs through Slack (Ignite), interactively with `spark <agent>`, or launched by another agent with `cast --agent <agent>`. `cast --rogue FILE` launches a rogue agent: a prompt file with no folder, whose harness, model, and effort are given on the command line; it is not an rbtv agent. A seat is replaced by an agent folder plus a task, and `seats.md` by a [`workflow.md`](capabilities/glossary/workflow.md). A plan's agents are rbtv agents: the planner writes one agent folder per agent inside the plan folder, `rbtv agent add` manages it in place, and the plan launches it with `cast --agent`, so each has the skills, rules, commands, hooks, and MCP servers its `agent.json` selects. When the plan closes, `rbtv agent remove AGENT --all --yes` takes each agent back, removing every unit and generated file while leaving its folder as the plan's record. `cast --rogue` stays for rogue agents outside plans. | In 0.2, `cast seat` launched a `seat.md` whose frontmatter carried harness, model, and effort and whose whole file was the system prompt, and the `plan` skill wrote `seats.md` and seat folders. The owner chose rbtv agents for plans because an rbtv agent has access to its skills, rules, and other units, so it can do much more than a rogue agent. `spark` is one small tool in `cast` with its own shortcut on `PATH`; it reads `agent.json` live and finds agents by folder, so a new agent needs no `PATH` change. The owner dropped `cast -sk` (launching a skill as an agent) and a JSON format for rogue agents: `cast --rogue` keeps plain `cast`'s 0.2 inline arguments and takes a file. |
| Ignite's waking program runs on Linux only, so an Ignite agent's Slack side runs on a Linux machine. | In 0.2 it is a Linux systemd user service. The owner chose to keep this restriction, knowingly and to keep Ignite simple, against rbtv's rule that every component works on Linux and Windows; the rbtv repository's Linux-and-Windows rule must name this exception when Ignite is migrated. |
| Whoever launches an agent hands it its `agent.md` prompt as its instructions, through the harness's strongest channel: Claude Code's system prompt (`--append-system-prompt-file`), Codex's developer instructions (`-c developer_instructions`), and OpenCode's first message. `agent.md` reaches the model without its frontmatter on every launch path. The installer also writes an agent section, a marked section in the agent folder's folder instructions, that points the agent to `agent.md`; the key paths are the optional Navigation section the author writes in `agent.md`. `ignite turn` gains a system-prompt field for Ignite's turns, and `spark` delivers the prompt the same way through `cast --headed`. | In 0.2, Ignite wrote an agent's standing instructions, purpose, reference paths, and skill list into the agent folder's `CLAUDE.md`/`AGENTS.md`, and every turn ran from that folder so the harness loaded it; `cast seat` sent a whole `seat.md` as the system prompt; `cast turn` had no system-prompt field, and on Codex and OpenCode a system prompt was pasted into the first message. The owner keeps folder instructions about the folder, not the agent's identity, and chose the launcher's channel plus the pointer: the pointer survives a harness shortening a long conversation on all three harnesses, because each reloads its project instruction files, while a harness-native main agent (`--agent`) exists on Claude Code and OpenCode but not on Codex. The skills are no longer listed: the harness finds installed skills, rules, commands, hooks, and MCP servers itself. |
| Per-unit generated files carry `rbtv-managed`; shared files use booked keys or `rbtv:start` / `rbtv:end` fenced sections, guidance copies carry a generated banner, and the records list installed units and files. The root's `install.json` and each agent's `agent.json` hold that list: its per-component key is `units`, and each unit names its method (`skill`, `rule`, `command`, `sub-agent`, `hook`, `mcp-server`, `tool`, or `folder-instructions`). The records hold no machine-tied field: no install time and no target path. The installer keeps the user's `~/.rbtv/`: `bin/` for the commands it places on `PATH`, and `path-owners.json`, which records the installations that own each command. | In 0.2 the marker was `rbtv2-managed` and the fences `rbtv2:start` / `rbtv2:end`; the installer keeps recognising them during migration. The list key was `parts`, renamed because "part" is not a term. `~/.rbtv/` and `path-owners.json` (format version 1) exist in 0.2 unchanged; the documentation had not named them. `install-index.json`, named in 0.2 code but never written, is dropped. The machine-tied fields `installed_at` and `target` are dropped from the record, because an agent's record is shared through git. |
| The root `rbtv.json` is retired. Programs find the installation's environment file at its fixed place, `.rbtv/config/env/.env`. | `rbtv.json` is left from an older installer (its `rbtv_version` is 7.0.0); the 0.2 installer never reads it, and its one live use is the `env_file` pointer tools follow to the environment file. The fixed layout makes that pointer redundant. Migration: update every tool that reads `env_file` from `rbtv.json`. |
| `.rbtv/config/` holds all user-specific configuration rbtv and its components need, each component's under a folder named after it, such as `config/ignite/`. A configuration file names the environment variable that holds a secret, never the secret: programs read the operating system's environment first, then the installation's environment file, `.rbtv/config/env/.env`. | In 0.2, `ignite.json` pointed to Slack token files by absolute path. Migration: every program or app that reads those tokens must be updated to the environment variables, without breaking. |

The 0.2 installer reads `exposure.csv`; the reader pages describe the intended 0.2.1 design, not an implementation report.

## Agents and cognitive units

- **Agent:** a prompt, a model (with its effort), a harness and scaffolding. The harness is the program that runs the model (Claude Code, Codex, or OpenCode). Scaffolding is everything an agent is exposed to besides its prompt: the cognitive units it has (skills, rules, commands, folder instructions) and the hooks, MCP servers, and tools set up for it. The files `rbtv` writes for them are generated files, never scaffolding. This replaces 0.1's agent-type distinction and the proposal to make a fixed task inside the reusable agent. A user can supply the task interactively; another agent can supply it when invoking the agent. The task supplies the goal, [scope](capabilities/glossary/scope.md), and [done contract](capabilities/glossary/done-contract.md). An agent launched by another agent is a sub-agent (below). The word "role" is not used for this, because role is a cognitive unit of a prompt. "Primary agent" is not a term; the owner dropped it, and its 0.2 skill is retired.
- **Kinds of agent:** an **rbtv agent** is an agent that has a folder holding `agent.md` (its prompt) and `agent.json` (its description, harness, model, effort, voice, chosen units and packs, and the record of generated files). It replaces "installed agent". An **Ignite agent** is an rbtv agent connected to Ignite: the Ignite pack is on and a Slack channel wakes it. A **rogue agent** is an agent file launched with `cast --rogue`; it is not an rbtv agent and is never installed.
- **Sub-agent:** an agent launched by another agent, whatever its kind. Through some harnesses a person can also start one directly; `spark` is the route rbtv offers for interactive use. The unit type that lives in a component's `sub-agents/` folder is always written **harness-native sub-agent**: a file in a harness's own sub-agent format, shipped by a component; it is called through that harness's own tool, by an agent, and where the harness allows it by a person. A harness-native sub-agent can only be called by an agent; an rbtv agent in `agents/` can be called by a person or by an agent.
- **The root:** the installation root is an rbtv agent with no `agent.md` and no stored harness, model, or effort: the person chooses them when opening it. Its file is `.rbtv/config/install.json`. Both records share one shape, and the root's has the same fields without `name`, `description`, `harness`, `model`, and `effort`. Where a file is tells the root from an agent, never which fields are empty.
- **The `rbtv` command:** manages what an agent is exposed to, by managing which units it has, for the root and for agents, and creates agents.
- **Pack:** a named list of units a component declares in `packs/<name>.json`; the root or an agent turns it on or off, and an agent's `agent.json` lists the packs that are on. Packs are declared in data, so `rbtv` holds nothing specific to Ignite.
- **Launching:** `cast --agent <agent>` (an agent launching another), `spark <agent>` (a person, interactively), and Ignite (a Slack message or a timer) all run an rbtv agent with its own harness, model, and effort from `agent.json`; `rbtv agent configure` is the only command that changes them. `<agent>` is a name or a folder path. `cast --rogue FILE` launches a rogue agent file. Every launcher sets `RBTV_AGENT_HOME` to the agent's folder, so any agent, however launched, can manage itself. It replaces `IGNITE_AGENT_HOME`; `IGNITE_CONVERSATION` stays.
- **Shipped agents:** a component may ship an rbtv agent folder under `agents/<name>/`. `rbtv agent add <name>` places a copy of it in `.rbtv/agents/<name>/` and installs it there. The intended use is an agent that carries its skills through a pack, so it is easy to call and its work stays out of the caller's context window.
- **Flags and options:** a flag or an option is two dashes and a whole word, or one dash and one letter; a whole word after one dash is not used for a new or changed word. The rule is in the `cli-creator` skill's interface contract (`meta/code/capabilities/cli-ux/interface-contract.md`). Every command-line tool of the `core` module follows it: `cast list --models`, `cast list --agents`, `cast list --agent <agent>`, and, for launching, `cast --agent <agent>` and `cast --rogue FILE`. A list that shortens a description takes `--full`, which shows it whole: `cast list --agents`, `spark list`, `rbtv agent list`, `rbtv list`, `rbtv search`, and `rbtv show` for a module or a component.
- **Finding models:** `cast list --models` prints the harnesses, the models, and what each effort number means on each; `cast -h` names that command and prints no model, so the help page does not change when a model does.
- **One provider for the rules about an agent:** cast's `lib/agent.js` is the one place that says where an agent's folder is (`<installation>/.rbtv/agents/<name>`), whether a value is a name or a path (a slash or a backslash makes a path), and how `agent.json` is read. spark, the agent list and Ignite load it; none keeps a copy. A record must carry `harness`, `model` and `effort`, the effort as the model's own word; a record without one is not launched by cast, spark or Ignite.
- **Finding rbtv agents:** one list, held by cast. `cast list --agents` shows the agents that can be launched by name from the current folder, the agents of the nearest `.rbtv/agents/`, each with its name, harness, model, effort, whether it is an Ignite agent, and its description; `cast list --agent <agent>`, with a name or a path, shows that agent in full, with the packs, skills, rules, commands, MCP servers and hooks installed in it under the names `rbtv show` takes, which cast asks of the installer. An agent finds them there. `spark list` shows the same list to a person and `rbtv agent list` runs `cast list --agents`, so the three print the same text and no second listing exists. No other file under an agent folder is named `agent.json`: the file an Ignite turn writes its result to is `agent-result.json`, because two files with different purposes never share a name. `rbtv agent add <name>` looks first under `.rbtv/agents/`, then among the agents components ship. Ignite connects only agents found under `.rbtv/agents/`.
- **Agent files:** an agent's `agent.md` gives the prompt; its frontmatter holds only `name`. Its optional Navigation section lists the agent's key paths, written relative to the installation root so that one root can be shared across machines. The units it has, its description, and its harness, model, and effort are in its `agent.json`. The installer writes an agent section into the agent folder's folder instructions, beside the pointer to `agent.md`. A component can ship an rbtv agent folder under `agents/`. The same agent folder serves `rbtv agent`, Ignite, `spark`, and `cast`; how an agent is installed and run is in the System and installation table. `cast` is documented here because launching agents on any harness is part of rbtv's `core`.
- **Agent description.** The `description` in an agent's `agent.json` is a short description: the first sentence is enough to decide whether to invoke the agent; the rest names the triggers and one near-miss (a similar case that is not this agent). It does not hold steps.
- **Settings.** `settings.json` stays one file in the agent's folder, not moved or split. Its convention: one top-level key per tool or concern, paths written relative to the installation root, no secrets. It is not shared through git.
- **Sub-agents and harnesses:** Claude Code and Codex launch harness-native sub-agents of their own, but only on their own harness and models; `cast` removes that limit. A component's `sub-agents/` folder ships harness-native sub-agent files, which the installer writes in each harness's own format: `.claude/agents/<name>.md`, `.opencode/agents/<name>.md`, and `.codex/agents/<name>.toml`. An rbtv agent is never translated into those formats; it runs through `cast`, `spark`, or Ignite. In 0.2 the installer translated an agent file into the harness format, and Codex got none; the owner separated the two, so the file the installer writes is a different concept from an rbtv agent, with its own name. A sub-agent is not a cognitive unit of its caller: like a tool, it shapes the caller's context window indirectly, through a fresh context window, other models' views, and specialized agents to distribute tasks to.
- **Prompt:** only the surviving prompt-side units are described as its cognitive units: role, persona within role, procedure, and constraints. The deleted 0.1 prompt fields listed above must not creep back into its definition. Scope and done contract arrive with each task.
- **Where a prompt's cognitive units are written.** Role, procedure, and constraints are sections of the named agent file, under the headings in the agent template; the persona sits inside the role section. They are not separate files. An agent file stays a prompt and holds no capabilities: it reaches knowledge through the skills and commands it selects, or, when its whole work is one domain, routes to that domain's capabilities. When agents need the same knowledge, those units route to one capability, so one update keeps them current.
- **Standing completion conditions:** conditions that hold for every task are check steps in the skill, command, or procedure that does the work; a done contract carries only its own task's conditions. Chosen over a default done contract carried by the skill, which would change the done contract's definition and need a rule for combining it with the task's.
- **Cognitive unit:** text an agent reads that shapes its cognition, written in files (a whole file or a section of one) and organized in folders; the folders belong to it because they decide what reaches the context window through folder instructions and folder artifacts. A file only programs read is not a cognitive unit; one both read is. Folder instructions and folder artifacts are cognitive units. "Scaffolding" is the wider word defined under **Agent**, and the cognitive units are part of it.
- **Discovering cognitive units:** whoever creates an agent finds the available units through the `rbtv` non-interactive commands (`rbtv list`, `rbtv search`, `rbtv show`) and enters them in the agent file's `agent.json`; a new unit is built only for what nothing listed covers. Those commands must carry everything needed for that.
- **Capability:** reusable content kept in a component's `capabilities/` folder: instructions, knowledge, templates, or tools. It has no exposure method and no fixed shape, so it has no template. A tool is a capability but not a cognitive unit: it shapes the context window only indirectly, by doing work outside it. A skill or command is built by default as an entry point plus capabilities: its entry point holds the procedure and routes in plain prose to the component's capabilities index, which says when to open each page. A unit whose whole content is one short procedure stays one file. Several entry points can route to the same capabilities, so updating one capability keeps every unit that routes to it current and the agent reads less up front. Use only the kinds of page the domain needs: a reader page, glossary, guides, templates and schemas, and principles; never an empty folder or placeholder. `core/rbtv` is the worked example: its `framework` skill routes to its capabilities.
- **Few exposures:** nest many capabilities, usually most or all of a component's, under as few skills or commands as possible; several short commands become capabilities under one skill. The agent first chooses among fewer entry points, then chooses which capability to open inside one. The owner chose this two-stage progressive disclosure to lower the agent's cognitive load.
- **Rules and agents:** a rule holds all its content in its body because it is always loaded. A rule may route to capabilities only when an agent's whole work is that domain; the agent's own prompt is an equally valid place to route. An agent file stays a prompt and holds no capabilities itself.
- **Exposure:** rule means the full instruction is presented on every task of every agent that receives it, with no human activation and no agent choice; a rule is not admitted because it is installed. Skill means the agent always sees a short description and chooses when to read the full body. Command means a human chooses when to invoke it. This follows the intended Claude Code sense of the three methods. Codex and OpenCode require harness-specific treatment for rules. The 0.1 rule design also allowed a scoped command-result rider; that delivery is not carried into this definition. An rbtv agent is reached through Slack (Ignite), `spark`, or `cast --agent`; `cast --rogue` launches a rogue agent file, which is not an rbtv agent.
- **Tool choice:** use executable software for exact, repeatable operations and model judgment for work that needs interpretation. A skill, rule, or command names the tool and the moment to use it. Placing the executable on `PATH` alone does not teach the agent when to use it. A tool reports success as status 0 and failure as any other status, so a caller checks the answer without reading prose.

## Memory

The owner declared the memory and folder-structure design complete and ruled its templates. The rulings below are in force.

- **Agent memory** lives in the agent's folder: a capped file of learned lessons plus topic files. Ignite injects the learned rules into every turn, as it does the agent's board. Topic files are read on demand. The agent discovers nothing; reliable recall comes from the runtime supplying it.
- **Only a scheduled dreamer writes long-term memory** — the agent's learned lessons and topic files, and general memory — working from the conversation transcripts Ignite already stores. The board is short-term memory the agent keeps itself; an explicit "remember X" and the owner's corrections are recorded by the agent at once. Every shipped system studied found notes taken during a conversation unreliable, and the transcripts already exist.
- **What the dreamer may change:** memory and the agent's own learned-rules file, freely; never `agent.md` and never rbtv source. A conflict goes to a digest for the owner. The agent learns from corrections without the owner editing anything, while a wrong lesson cannot rewrite the agent's instructions.
- **Always loaded into every turn,** timer wakes included: the general-memory profile, the agent's learned rules, the agent's board, the general-memory index, written once (one row per folder), and the general-memory inbox. Everything else is read on demand. Agent-memory systems studied converge on small always-loaded files plus an index; the owner counts the board as memory.
- **"Remember X" about the owner** goes to `inbox.md` in general memory, appended at once by any agent and seen by every agent; the dreamer files it into its place and empties the inbox. Appending cannot overwrite, and no agent asks the owner again. The inbox never refuses an append, since refusing would lose a "remember X"; past 20 lines the owner is alerted.
- **Timeline:** daily and weekly timeline files, written only by the dreamer inside general memory, separate from the owner's own periodic notes, read on demand and never injected.
- **Moving Claude Code's own memory into rbtv memory** is one sorting pass: facts about the owner go to general memory; working lessons go to the learned rules of the agent that uses them, duplicates merged; notes about a repository or workspace go to its workspace file.
- **The dreamer** is one shared program that runs nightly and goes through the agents one at a time. It reads only messages past a cursor that only moves forward, and only after a durable write. The model proposes add, supersede, or archive; deterministic code validates and applies each proposal: an over-cap change is refused, never truncated; a file changed since it was read is not overwritten; no record disappears without a reason. Text that was injected, recalled, or written by the dreamer is never evidence. It archives, never deletes, and never edits `agent.md`; a conflict with the agent's instructions goes to the owner's digest. It stays silent when nothing changed, and a failure alerts the owner. Three reviewers agreed unanimously and the owner agreed.
- **Undo through git:** each agent's `memory/` folder and its `_artifacts/board.md` are tracked in git, one commit per dreamer run; the rest of the agent folder stays untracked. Any bad dreamer change can be undone without a backup scheme of its own.
- **Learned rules:** an owner correction becomes a learned rule without needing to be repeated, written at the dreamer's next run; until then the board's watch-out covers it, and the conversing agent never writes learned rules. A lesson the dreamer infers on its own needs evidence from two separate conversations. Each learned-rule line starts with `[correction]` or `[inferred]`. The owner's word suffices; a single inference does not.
- **A memory file missing or broken when a turn starts** — broken meaning it fails the check program — is saved aside, its last good version in git is loaded, and the owner is alerted: never fail, never stay silent.
- **Expiry:** only a fact with an explicit end date ("until <date>") expires; nothing expires from disuse, so a temporary fact never becomes identity and a rarely used truth never vanishes.
- **Watchdog:** the owner is alerted when the dreamer has not completed a run in 48 hours.
- **One general memory per installation,** always at `.rbtv/memory/`; there is no location setting, so nothing extra is maintained or can drift.
- **General memory's index:** the always-loaded index, `<memory root>/_artifacts/index.md`, has one row per folder, written once; each folder has a generated index of its files, read on demand, so the always-loaded part stays bounded. Generated indexes are exempt from the index row cap. The dreamer commits general memory once per run, as it does agent memory. `workstreams.md` alerts the owner past 60 lines, never refusing.
- **General memory's folders** (`.rbtv/memory/`) follow the Instinct article's ontology, adapted to what the owner's files actually hold. Always loaded: `profile.md`, `inbox.md`, and `_artifacts/index.md`, written once. `entities/`: `people/`, `orgs/`, `places/` (geography only), and `devices/` (machines the owner and his agents operate). `knowledge/`: `facts`, `preferences`, and `decisions` (single files; a write that would pass a file's cap is refused and reported, and the file does not split), `self` (a distilled self-model), and `health` (only lines that change an agent's behaviour, pointing to the owner's notes; the always-loaded profile has no health section, and a health-driven constraint appears there only as the constraint). `workspaces/<slug>.md`: private notes about a shared repository or workspace. `timeline/daily/` and `timeline/weekly/`: written by the dreamer, linking to the owner's periodic notes, never copying them. `workstreams.md`: one line per active subject, project, or area, pointing to its folder and board. No folder for communications: conversations live in Ignite's database.
- **Memory holds thin facts and pointers;** the content's own home stays canonical and is never copied. The transcription glossary stays where it is; people and organization files carry aliases and link to it.
- **General memory is seen by every agent,** with no per-agent grants or sensitive-topic restrictions (keep it simple; nothing needs them yet).
- **Rollout:** Ignite agents first; interactive harness sessions working in a workspace second, when Claude Code's own memory moves into rbtv memory and a pointer in folder instructions or a rule reaches them.
- **Private memory about a shared repository** lives in general memory, `.rbtv/memory/workspaces/<slug>.md`, loaded automatically when an agent works under that repository's or workspace's paths. A shared repository cannot hold one person's private memory, and this gives that memory one home.

- **The board** (`<agent folder>/_artifacts/board.md`) is the agent's short-term memory of what matters now, organized by subject and injected by Ignite into every turn; it follows the Instinct article. It points to threads, never the reverse: the agent notes an important discussion under its subject with the thread's link, and Ignite never adds a thread to it. On every wake the agent reads it and knows what matters and where to resume or answer.
- **Board sections and their writers:** "What matters now" — one entry per subject (title, one to three lines of state, related threads, linked timers, link to detail), written by the agent through a short fixed form that code checks; an over-long entry is refused, never truncated. "Watch-outs" — the owner's corrections, recorded by the agent in the same turn (a correction counts as "remember X"); the dreamer later folds them into the agent's learned rules. "Timers" — written by Ignite from its schedule database, never copied by hand. "Recently closed" — written by Ignite when the agent closes a subject.
- **Timers on the board:** the agent creates them itself on the owner's request (one-off reminders and recurring checks), as many as needed, and closes one when a wake finds its goal met.
- **The dreamer and the board:** the dreamer moves a subject's detail into a topic file in the agent's memory folder and keeps the board entry lean with a link; it learns from transcripts, not from boards. It writes the board only if the board is unchanged since it read it; otherwise it re-reads and retries.
- **Every board** — agent, project, or area — has the same four sections, empty when unused; closing a subject writes "Recently closed", and lines pruned from it are archived, never deleted. The Timers table sits outside the board's line cap.
- **Board safety:** a deterministic check program runs on every board write; no governance agent. Ignite flags subjects idle for seven days; nothing is deleted automatically. Caps are the implementation defaults below. Recently closed lines past the cap are archived, never deleted.
- Implementation defaults (owner not asked): Dreamer cursor is SQLite `rowid` with a run-start ceiling, advanced only after a durable commit, with no new sequence column; late inserts are seen on the next run. Caps: board limits as defined in the board template; profile 4,000 characters; learned rules 30; workspace memory 3,000 characters. Inbox is 20 lines and workstreams 60 lines, with alerts at their thresholds rather than refusing valid appends or updates. Dreamer schedule and model: nightly at 03:00 America/Sao_Paulo, spawned from the daemon tick, only when `dreamer.enabled` is true in Ignite's configuration (off by default); the model is the `dreamer.model` setting, default `codex gpt-6-sol`, effort 3. `ignite dreamer run` runs the same pass once on demand, even while the nightly run is off. Digest delivery: one Slack thread on the direct-message agent (`dmAgent`, currently `master`); later posts use `post --thread`. No digest when unchanged. Timer subject: `schedule add --subject` is optional; schedules without one render `none` in the board's Subject cell. Quiet-night liveness: at the 03:00 slot, if there is no unread owner row, due expiry, inbox item, or work to fold, record a successful run without calling the model and without sending a digest. An inbox line alone counts as work and may be filed with its own provenance as source. Conflict reporting: report each conflict in the digest once, not every night.

## Folder structure

- **Four folder types:** project or area; agent; rbtv folder (a module, component, or tool, including rbtv's core documentation); and collection (any other folder an agent maintains). A wiki keeps its own rules; a shared repository keeps its own and adopts rbtv's only by choice.
- **Conventions live in folder instructions,** never in a separate conventions file: any new convention is written into the folder instructions of the folder it governs, in the same change. Folder instructions reach the agent automatically; a second file would drift.
- **One board for every folder:** projects and areas use the same board template as agents, and keep their task file (`<name>-tasks.md`, which the task tool depends on). The board's caps stop state files from growing without limit.
- **Optional folder artifacts:** templates, glossary, tools, guides, and principles are each an optional folder artifact with one shared template; none is required anywhere, so an agent that needs one follows a known shape.
- **Nothing sits loose in a `build/` folder:** every file goes in a named subfolder, one per run or topic. The folder instructions of the folder that contains `build/` say so; no check program enforces it.

- **Folder instructions contract:** every folder instructions file carries an `| Open | When |` table pointing into `_artifacts/`, each row naming a moment, never a bare "see X". Besides the table it holds only one line on what the folder is, the folder's own rules and conventions, and one-line "BEFORE doing Z…" tripwires; facts, state, history, tasks, and full procedures live in artifacts, because the file loads on every visit. It stays under about 150 lines; longer content moves to an artifact the table points to. A subfolder's instructions only add; overriding a parent rule is explicit, with its reason.
- **Write-time rules** live in the folder instructions, which every harness reads. A folder may add a harness hook as an extra, never as the only carrier: a hook fires only when the harness was started in that folder (verified: a Claude Code hook does not fire for a session started in a parent folder, and other harnesses do not run it).
- **The task file** sits at `_artifacts/<folder>-tasks.md`, the one exception to plain names, because the task tool matches the `-tasks.md` ending.
- **rbtv's own `capabilities/` folders stay where they are;** `_artifacts/` applies to folders agents maintain.
- **The folder instructions table lists the folder's `_artifacts/` items; `_artifacts/index.md` lists the folder's content** (subfolders and documents); no item appears in both, so the table that matters most stays loaded automatically.
- **Index rows** use the `| Open | When |` table everywhere, rbtv's indexes included, replacing the list-row format.

## Ignite timers and threads

- **Every timer wake starts fresh,** bound to no thread. Ignite gives an agent one more ability: it can post into a named existing thread, and that post joins the thread's history, so the owner's reply there resumes the thread with its full history. A schedule is never re-bound to a thread. The owner's reason: the board, not the timer, tells the agent what to do and where to answer.
- **A wake passes only the name of the check that fired;** the board holds the check's details. With several checks on one board, a wake without content would make the agent infer which one is due.
- **Agents are taught one subject per thread:** reply in the thread whose subject your message continues; start a new top-level post only for a new subject. A board subject names its thread or threads when it has any; a subject may start with none, for example from a timer, because a thread is a consequence, not a cause.

## Ignite commands

- **The `ignite` command** holds what is unique to Ignite: `connect`, `disconnect`, `manage`, `turn`, `schedule`, `schedules-due`, `work`, `wake`, `post`, `board`, `remember`, and `dreamer`. `turn` moved from `cast` into `ignite`: its turn file and tests move into Ignite and use cast's shared launch files directly, nothing is copied, and `cast turn` leaves cast's help. The verb sits with its only caller; there is one copy of the launch knowledge. In 0.2 the command was `ignite-agent`, with `install`, `update`, `create`, and `create --remove`; the owner removed the install and update verbs, because an agent is managed by `rbtv agent`.
- **`ignite manage <agent> …`** is the one exception to one home per command: an Ignite agent has one place to manage itself. It holds `add`, `remove`, `configure`, `update` (forwarded to `rbtv agent` for the agent itself), `models` (forwarded to `cast list`), `list`, `search`, and `show` (forwarded to `rbtv`). It has no logic of its own: arguments and output pass through unchanged, and its help is taken from the originals, so nothing drifts.
- **Ignite's standard units** are the Ignite pack, turned on in the agent's `agent.json` (see the Pack bullet). The owner's choices stay in the agent's `units` and `packs`, so `agent.md` lists none of Ignite's units. To give the agent a unit, list it in `agent.json` or turn on its pack; a unit installed into its folder by hand is removed on the next `update`. The owner chose one source of an agent's units (ruling I1) over writing Ignite's units into each agent file, which would mix the owner's choices with Ignite's and leave dropped standard units behind.

## Module and component placement

- `core` is for rbtv's own operation, installation, configuration, and editing, and for the software that manages, runs, launches, and connects agents on any harness: the rbtv command, Ignite with its Slack connection and configuration, `cast`, and `spark`. `meta` is for how agents behave, communicate, plan, and coordinate work, such as the `plan` and `sub-agents` skills, with swarm and panel capabilities inside `sub-agents`. The owner placed `cast` in `core` because sub-agents and harness independence are central to rbtv, and Ignite there because it holds the Slack configuration. Other modules own their own subject areas; neither `core` nor `meta` is a catch-all. Only these two intrinsic modules receive module-specific glossary pages.
- This **reverses the 0.2 folder meanings**: in 0.2, `meta/` is about rbtv itself and `core/` is about general agents. The owner chose the inversion for 0.2.1 after considering both assignments. The reader pages use only the chosen meanings.
- Extend a component when its cognitive units and capabilities serve one coherent purpose; create a new one when the purpose is distinct. The owner chose this over grouping by shared audience, workflow, file type, or exposure method. 0.2 has exceptions, including `core/functions` (a pool of unlike conversational skills) and unrelated tool exposures under `meta/planning`; these are observations, not precedents for 0.2.1. This is a placement rule, not an authorization to reorganize existing components now.
- `core/rbtv`'s capabilities exist so that the `framework` skill (`skills/framework.md`) can teach agents to read and navigate them whenever they build skills, rules, commands, agents, tools, or other rbtv units. `meta/code` is the anticipated migration of the command-line work into a skill, `cli-creator`: an early test of how this documentation works in use; other cognitive units may follow.
- A capability lives with the units that route to it. The workflow, scope, and done-contract building guides and the workflow template live in `meta/sub-agents/capabilities/` because the `sub-agents` skill uses them to coordinate delegated tasks; `core/rbtv`'s guide and template indexes still route builders to them. Rule 2 of [`CLAUDE.md`](CLAUDE.md) allows a building guide or template in the capabilities of the component whose units use it when its build index lists it. The role, persona, procedure, and constraints building guides stay in `core/rbtv` because they teach writing the agent file, an rbtv unit the installer reads. All terms stay in the single `core/rbtv` glossary so each has one meaning.
- The navigation skill is named `build`, with no prefix; its source is in the `build` component's `skills/` folder in rbtv, and a harness receives only its thin loader. It replaces the 0.2 `build` skill (`meta/planning/references/build.md` in rbtv), which is deleted entirely. It triggers only on work on rbtv components: creating or reviewing a skill, rule, command, agent, hook, MCP server, tool, or other rbtv unit. It was written after the `core` migration, as `skills/build.md`. Its body is an entry point, not a second map: read `rbtv.md` to understand what rbtv is, the guides to build, the glossary for exact meanings, the templates and schemas for a file's shape, and always follow the principles. That routing already lives in `capabilities/capabilities.md`, so the skill points there instead of restating it, and it never repeats `rbtv.md`'s content. Owner's reason: an agent building on rbtv must land on the right page for its situation, and results must be installer-recognizable and follow the principles. The building of an agent, which the owner moved from the `create-agent` skill, is one of the building guides this skill routes to.
- The command-line experience of the `rbtv` command (its verbs, help, and output) is the reference for every rbtv command-line tool, and `cli-creator` was built from it. Every new or edited rbtv command-line tool follows `cli-creator`, and no edit lowers its standards. Until migration, hand-made loaders in the workspace's `.claude/skills/` and `.agents/skills/` point to the staged skill so it is followed now.
- Module and component names are nouns, never gerunds: `plan`, not `planning` (owner ruling). The 0.2 `meta/planning` component becomes `meta/plan`.
- Create a new module only when no existing module's purpose fits without stretching it. It may start with one component, but it must name a coherent area for future components. Decide the module, then the component, then whether any cognitive unit needs independent exposure.

## Principles

The principles act as rbtv's culture for agents: they guide how cognitive units, files, folders, memory, and folder artifacts are built. They exist to shape the agent's context window, so the model hallucinates and drifts less and reasons better. No one reinforces them, so each must state its own practical consequence.

Working records behind these choices: the principles audit (terminology clashes, overlaps and tensions, where each principle applies, candidate implications), the principles provenance record, and the external research on actionable principles, all working records of the 0.2.1 migration project.

- Each principle file has a **Statement**, **Rationale**, and **Implications**, following the architecture-principle format. The implications are the practical consequence, and each is written so a reviewer can confirm or reject it. The owner chose this over pass/fail checks with red flags, MUST/NEVER rule tables, and do/don't examples. All principles use this format.
- Principles guide how structure is defined; they never define the structure themselves. An implication is a test the builder applies to its own design, not a piece every design must contain. Every implication was swept against this rule and ruled by the owner one at a time; the rulings are in the principles sweep, a working record of the 0.2.1 migration project.
- The Statement names the trade-off the principle makes, in the form "X, even over Y". A principle nobody would disagree with guides no decision.
- The Rationale names the context-window effects the principle reduces, hallucination or drift, and the causes it acts on: context load, context gap, cognitive load, or context poisoning. The owner asked for this so that every principle is checkably aimed at those effects.
- Implications are instructions to the builder ("Link to the owning file"), not descriptions of the system. Agents act on instructions most reliably.
- "Task" is the one term for a piece of work given to a human or an agent, and has its own glossary entry. It replaces request, job, assignment, unit of work, seat, session, run, and execution (section 1b of the principles audit, a working record of the 0.2.1 migration project). The owner chose "task" because it is the same thing a task list holds, whether a human or an agent does it, which keeps human and agent work in one vocabulary (Agent parity). The deleted 0.1 task-goal cognitive unit stays deleted; a task states its goal in ordinary language.
- Micro agency gives each task and each cognitive unit one purpose whose result can be judged alone. An unrelated second purpose is a second unit. The principle owns the parallel-run limit: independent tasks run in parallel only when no two of them change the same file or record.
- Progressive disclosure has five loading moments: a rule, when the content applies to every task of every agent that receives it; a skill, when the agent judges it relevant; a command, when a human decides; folder instructions, when the agent reads or changes files in a folder; a file opened because a rule, skill, command, or folder instructions points to it, when it is needed only at that step. Folder structure and memory are designed around index files and pointers.
- Folder instructions route the agent to the right file at that moment. That routing is what sets them apart from a rule, which travels with the agent into any folder. The installer delivers them by writing a copy for each installed harness beside the basis file, as it does for every folder it walks; each harness then loads the copies by its own rules. rbtv accepts where a harness loads less and does not work around it: per the research, Codex reads folder files only from the root down to the folder it starts in, once per session, and stops at a 32 KB total (the rules and folder instructions investigation, a working record of the 0.2.1 migration project). A folder instructions file stays correct when read with its parent folders' files: it does not contradict them and does not rely on overriding them. The file in the highest folder of a tree stays small.
- What an agent sees before opening a unit, such as a skill description, is a name and a short description. The first sentence is enough to decide whether to open it. The rest names the triggers and one near-miss: a case that looks close but should not open it. An index line, and a record's description field, stay one line that names the moment or the decide sentence.
- A principle lists implications only for the areas it actually changes, not a fixed checklist of areas.
- Merges are allowed: if two principles produce the same implications, propose merging them for owner approval. The candidate overlaps and their proposed owners are in section 2 of the principles audit, a working record of the 0.2.1 migration project.
- Each shared implication has one owning principle, following section 2 of the principles audit, a working record of the 0.2.1 migration project. Single source of truth owns "one implementation behind every way to perform an action" and "one shared home for content that multiple units use". Agent parity owns "an agent can reach every action". Deterministic first owns "exact steps go to tools" and making tools known to agents. Keep it simple breaks ties.
- The parity principle is named Agent parity. It covers any software that humans and agents both use, not only the state rbtv manages: both reach the same operations through their own interfaces. An agent reaches an rbtv action by editing the same file a human edits, or through a tool when the action is more than a file edit, so the principle is not about command-line tools alone.
- "Workflow" is defined in the glossary: a set of tasks arranged as a DAG, run by sub-agents through `cast`, running at the same time every task whose needs are met except tasks that change the same file or record. It is written in `workflow.md`, which replaces 0.2's `seats.md`; the coordinating agent reads it and launches the ready agents. The owner chose a file only agents read, because no program needs to read it; a machine-readable file with a `cast` command that launches and monitors every ready agent was considered and not adopted. The principles still use no term such as "handoff"; one task's result being used by another is described in plain words.
- Compound engineering is not a principle. Its content moved to the compound engineering memory draft, a working record of the 0.2.1 migration project, to be designed together with `.rbtv/memory/`.
- Agent tooling is merged into Deterministic first. Both covered tools for agents, and one implication, naming the tool in the step that uses it, appeared in both.
- A principle shapes the system; an instruction about an agent's conduct during a task is a rule, never a principle ([glossary](capabilities/glossary/principle.md)). Always verify is therefore a rule, not a principle, and so are the former last implications of Deterministic first (check the installed tools before scripting) and Terminology is king (use glossary terms with humans). Their rule texts are drafted in the rule drafts, a working record of the 0.2.1 migration project until the component that holds them is chosen.
- Agents as teammates, Capabilities first, and Harness and provider agnostic are deleted. Of their implications, only two are kept: the clean-boundary test (a capability relies on nothing beyond what its user passes to it) is in the [capability guide](capabilities/guides/capability.md), and the carry-over test is an input to the memory design (Open decisions). The rest, including the term "provider", are dropped.
- Principle texts use 0.2.1 terms only, such as no "seat" in Micro agency. The full list of clashes is in section 1 of the principles audit, a working record of the 0.2.1 migration project.

## Migration

- The 0.2 `core/coding` component moves into the `meta/code` component.
- The modules outside `core` and `meta` (`web`, `office`, `innovate`) are converted to the 0.2.1 layout mechanically, with a one-off script, in the same change as the installer's new reader, so the installer has one reader and no second format.
- The mechanical conversion removed every frontmatter key no schema allows (the 0.1 names `inputs`, `outputs`, `outcome`, `id`, and the unread 0.2 hints `tags` and `exposes-cli`), moved each component's `component.md` into its `capabilities/`, and deleted `module.md`; the descriptions live in the JSON records, and the rest stays in git history. The owner accepted it.
- The installer checks frontmatter and JSON records against the schemas with a small validator in its own code, covering only the schema keywords the templates use; it adds no outside dependency.
- The 0.2 `build` skill leaves the plan component now, and the plan component's `references/` are retired: the `plan` skill points to the build documentation (glossary and guides) where it pointed to those references. The file-by-file review (the plan references review, a working record of the 0.2.1 migration project) found two things the build documentation lacked, now carried into the agent and capability guides: no installation-specific value (channel id, path, account, host, credential) is typed into a prompt or capability, and an agent that runs without a person never waits for a result after its turn ends. The other nineteen files are covered, a deleted 0.1 concept, or an obsolete 0.2 mechanism.
- Components in this migration (owner rulings on the component table, a working record of the 0.2.1 migration project): `acct` (provider accounts) folds into `core/cast`; the Slack and Google tools (`stools` wrapper, `gtools`) and the `google-workspace` skill move to `meta/communication`, and Ignite installs them as standard units; `innovate/brand`, `innovate/conception`, `innovate/validation`, and `web/research`, which had no record in 0.2 but hold content other files point to, each get a `<component>.json` and become components with capabilities only.
- Retired in this migration: the 0.2 `create-cli` skill (it overlapped `cli-creator`), and the `component-lint` and `capability-cards` tools (they read `exposure.csv`, and `component-lint` checked 0.1 shapes). Checking that a component follows the format is the installer's job: its schema validation and `rbtv doctor`.
- The 0.2 `create-primary-agent` skill's content moved into the building guides for creating an agent in `core/rbtv/capabilities/`, and the `create-agent` skill is retired. The `master` agent selects the `framework` skill instead, which routes any building request to the right guide. The 0.2 `workflow-authoring-checklist` skill is retired too: the workflow glossary entry, guide, and template cover writing a workflow.
- The 0.2 installer installs no dependencies. `package.json` stays in the four components that have it, untouched, because its `check` and `install` commands are the data a future dependency installer needs; that installer is not built in this migration (Open decisions).
- A tool's `entry` names its program inside its component, or uses `ws:` for a program in another repository of the installation, relative to the installation root. Any tool may use `ws:`; `gtools` is one example.
- Harness-native sub-agent files (`sub-agents/`) are written in each harness's own format on all three harnesses: Claude Code and OpenCode get a thin loader in their agents folder, as in 0.2, and Codex gets `.codex/agents/<name>.toml` with the sub-agent's name, description, and instructions. In 0.2 Codex got none; Codex now has native sub-agents.
- Kept from 0.2: thin loaders name their unit by an absolute path; the installer keeps listing the files it generates in `.git/info/exclude`, so each machine regenerates its own and the absolute paths stay right.
- Agent commands: `rbtv agent add <agent>` installs what the agent's `agent.json` declares, the first time or again, plus any units named; `rbtv agent update <agent>` makes the folder match the file; `rbtv agent remove <agent> <unit>...` removes units; `rbtv agent configure <agent>` changes harness, model, or effort, checks them against `cast list`, and regenerates files when the harness changes; `rbtv agent list` shows the agents. `rbtv agent` is a verb group, so an agent never collides with a unit verb; `spark <agent>` runs one interactively. Each verb takes the agent as a name or a folder path. The agent folder's ignore file is `.gitignore`, listing the database (`state.sqlite*`), `turns/`, and each conversation's harness session files (`conversations/*/session*`); conversation history stays shareable. The units an agent has are installed into the agent folder itself, so its hooks and MCP servers land in the agent folder's own harness files. `update` removes generated files the file no longer accounts for; it keeps `settings.json` and live data. `remove` takes back only what the installer wrote and keeps `agent.md`, `agent.json`, `settings.json`, and everything the agent made, following the installer's rule that it deletes only its own files. An effort given as a number from 1 to 5 is stored as the model's own effort word, and `inert` for a model with no effort setting.
- Hooks use Claude Code's event names, which Codex shares, with the fields event, optional matcher, command, and optional timeout; OpenCode receives no hooks. OpenCode's equivalent is a plugin, a JavaScript program file loaded from `.opencode/plugins/`, not a settings entry; the owner translates a hook only where the harness takes a settings file, so none is generated for OpenCode.
- An MCP server's secrets reach each harness as the environment variable's name in that harness's own form: `${VAR}` for Claude Code, `{env:VAR}` for OpenCode, and Codex's forwarding list, which works only when the server's variable has the same name as the environment variable (otherwise the installer refuses it for Codex). rbtv never writes a secret: a server that logs in through the browser has its token stored by the harness, and an API key stays in an environment variable. One shared record serves all three harnesses.
- `cast` hands Codex its prompt as developer instructions on every platform. On Windows it starts Codex's program directly, not through the `.cmd` wrapper, whose command-shell quoting breaks on characters such as `&`, `|`, `<`, `>`, `^`, `%`, and quotes; the same launch fixes every harness on Windows. Owner's reason: both platforms work the same way. This holds for every `cast` launch that carries a system prompt, not only Ignite's turns. Verified against the harness documentation: Codex forwards an environment variable by name through `env_vars`, and its `env` values are taken literally; OpenCode expands `{env:VAR}` in its configuration when it loads it, and an unset variable becomes empty.
- Programs move into their tool folders for the modules migrated now, `core` and `meta`. In `office`, `web`, and `innovate`, each tool's `entry` points to its program where it already is, inside its component, until those modules are migrated.
- `embed-search` and `control-panel` are not migrated now: their folders move, as they are, to the project's `_backlog/`, and their installed skill and commands are removed from the vault.
- Ignite's commands are verbs of `ignite`: `connect <agent> (--channel-name <name> | --dm) [--schedule-json <file>]` (on the machine that will run it: turns the Ignite pack on through `rbtv`, connects the Slack channel or direct messages, writes the route in that machine's `config/ignite/config.json`, and creates the board, the database, and the `conversations/` folder), `disconnect <agent> [--archive-channel]`, `manage`, `turn`, `schedule`, `schedules-due`, `work`, `wake`, `post`, `board`, `remember`, and `dreamer`. They replace 0.2's `ignite-agent install`, `update`, `create`, and `create --remove`.
- Ignite's standard units reach an agent folder as ordinary units of the Ignite pack, recorded in its `agent.json`. The `agent_units` record lists the units the agent has, so `rbtv agent update` removes only those the file drops, and `ignite connect` turns the pack on and creates the working files. The owner chose one source of an agent's units (ruling I1), as recorded under Ignite commands.
- `cast route --batch` names its input list `agents`, not `seats`: the word seat is retired.
- `cast`'s forms: `cast --agent <agent>` runs an rbtv agent from its folder with its `agent.md` as the system prompt. It takes no harness, model, or effort, because it always uses the agent's own, from `agent.json`; its other arguments are as in 0.2. `cast <harness> <model> <effort> [<folder>] (-p <text> | -f <file>) --rogue <agent file>` runs a rogue agent with the file's body as its system prompt; the caller passes harness, model, and effort, chosen with `cast route`.
