## Mechanism
`reply-leg.js`'s revive does not itself choose resume-vs-fresh-session — by owner ruling 2026-08-10 (decision 7) it rides the SAME follow-up mechanism (`forward-path.js#forwardFollowUp`, `corrective: true`) an ordinary owner message uses: an `enqueue-job` `send-message` job carrying the corrective feedback as a `note`. The actual resume/fork decision lives in `ignite/runtime/ticker/ticker.js`'s chain-decision code (`dispatch()`, the `why` ternary around `composeNewSenderMessages`): a chained turn RESUMES the predecessor's harness session only when `composeNewSenderMessages(parentRow)` finds a message row on the chain's thread newer than `parentRow.completion_msg_id`, filtered `sender != 'ticker' AND type != 'completion'`. That `completion_msg_id` watermark is set ATOMICALLY with the jobs_log row's STATUS going terminal, by the daemon's own periodic crash sweep (`ticker.js` "Task 7.7": `heartStore.recordMessage({type:'completion', ...})` stamps `status`/`completion_msg_id`/`ended_at`/`exit_code` in one write) or by the same-tick clean-exit path — never by `reply-leg.js`.

`reply-leg.js`'s OWN gate for "the turn ended" was `live === false` alone (`dispatch.js#handleInspect('status')` → `spawnManager.status(id)`, a raw, real-time CARRIER check — confirmed by reading `ignite/supervisor/spawn/spawn.js#status`, which returns `live: carrierInfo.active` completely independent of `row.status`). The bridge polls this every `pollMs` (default 3000ms); the daemon's own tick cadence (crash sweep) runs on a longer, independent cadence (~10s, per `ticker.js`'s own nudge-chain comment: "The loop runs every `tick_interval_ms` (10 s)"). A dead carrier is visible to the bridge before the sweep has run even once. Firing the corrective `send-message` enqueue in that window writes the note to the `messages` table BEFORE the sweep's own completion INSERT — since `msg_id` is assignment-order, not event-time, the note can land with a LOWER `msg_id` than the completion row the sweep writes moments later, becoming the new `completion_msg_id` watermark. `composeNewSenderMessages`'s `msg_id > completion_msg_id` filter then excludes the note — `why` resolves to `'no-new-messages'`, `chainPath:'transcript'`, and the ticker spawns a fresh harness session (the observed `1326693f`) instead of resuming (`resumeRef = parentRow.session_ref`).

This is the origin per the contract test in `root-cause`: `reply-leg.js`'s own revive-eligibility check (`live===false` only) is the earliest in-scope point that let a corrective note race ahead of a fact (the store's own completion watermark) its downstream consumer (the daemon's resume decision) requires to have already landed.

## Fix
`reply-leg.js`'s per-watched-exec loop now computes `storeCaughtUp = !IN_FLIGHT_STATUSES.has(statusRes.result.status)` (`IN_FLIGHT_STATUSES = {'running','launching','stalled'}`, the same wire vocabulary the file already reads for its STALL/RECOVERY checks) and gates ONLY the corrective-revive branch on it — never the conformant or best-effort/fallback delivery paths, which write nothing to the daemon's `messages` table and so never race the watermark. When a revive is warranted but the store has not caught up, the pass sets `failure = 'store-status-not-terminal'` and retries next pass, reusing the EXISTING bounded fetch/delivery retry cap (`maxDeliverAttempts`/`watch.attempts`, and its honest give-up notice) rather than inventing new bound machinery — consistent with the file's own "no crash, no unbounded retry" design.

Rejected: gating the WHOLE fetch/verdict/delivery cycle (not just the revive attempt) on `storeCaughtUp` — simpler to write, but it would add a latency tax to every conformant reply (which never races) purely to protect the one path that does. Rejected: importing `heart-store.js`'s own `TERMINAL_TURN_STATUSES` constant directly — `reply-leg.js` is a closed, gateway-facing consumer by design (D90, "NO NEW CAPABILITY … reaches the daemon ONLY through the injected `forwarder.inspect`"); reaching across `chat/` → `runtime/` → `state-store/` internals to share one Set would cross that boundary for a vocabulary the file already interprets structurally (it already names `'stalled'` and `'killed'` as literals from the same wire contract).

## Consequences
Nothing was deleted; the MAX_REVIVES budget, the compaction-turn retirement, the STALL/RECOVERY notices, and the spawn-wait/tombstone rungs are unchanged and still enforced identically. `probe-chat-reply-leg.js` gained one new arm (`v`, plus its bound sub-check) modeling the daemon's real resume-vs-fork verdict as a function of store-status timing at the moment `reply-leg.js` calls `redispatch` — driven through the SAME scripted forwarder every other arm in the file uses, filtered to its own thread so it cannot read traffic from another arm's leftover pending conversation. No existing arm's assertion needed to change: every pre-existing `state.status.set(execId, {live:false, ...})` fixture in this file already paired `live:false` with a terminal `status` (`'done'`/`'failed'`/`'killed'`), so the new gate is a no-op on all of them (verified: `probe-chat-reply-leg` unchanged pass/fail shape before and after, byte-identical check count). No other in-repo caller of `createReplyLeg` was found (`grep -rn "createReplyLeg" ignite/`) beyond `chat-bridge.js`'s own wiring and this probe file.

## ATTENTION
1. The gate reads `status`, never `live`, to decide "has the store caught up" — `live` is a raw carrier check that can go false a full tick cadence BEFORE the daemon's crash sweep records the turn's own completion. Reverting to `live===false` alone as the sole revive-eligibility signal re-opens this exact race.
2. The gate is scoped to the REVIVE branch only, deliberately — widening it to also hold the conformant/best-effort/fallback delivery paths would add avoidable latency to every reply, since those paths write nothing to the store that a resume decision watermarks against.
3. `IN_FLIGHT_STATUSES` is a hand-kept mirror of `heart-store.js`'s in-flight vocabulary (`'running'`, `'launching'`, `'stalled'`), not an import — `reply-leg.js` is a closed, gateway-facing consumer by design (D90) and must not reach into `state-store/` internals. If the store's status vocabulary grows a new in-flight value, this Set needs a matching update; nothing enforces that automatically.
4. This fix does NOT touch the warm/cold leg race, the inverted feed/turn timeouts, or the per-inbound-message idempotency guard (seed `slack-duplicate-replies.md` §9 criteria 3–4, `dup-idempotency`'s territory) — those are independent defects that compounded with this one in the 18:51/18:55Z incident and are not addressed here.
5. The RED-first mutation used to prove this (temporarily reverting the `storeCaughtUp` condition) was NOT left in the tree — `git diff` was re-verified against the saved fixed copy after restoring, and the committed `reply-leg.js` carries the fix, not the mutation.
