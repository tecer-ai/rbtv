## Observed
Owner saw two different-worded answers to one Slack question 4 minutes apart on `transcript-summarizer-build` (`slack-duplicate-replies.md`, 2026-08-31). Investigation isolated two independent contributors: a session-lineage fork (out of this fix's scope — `dup-revive-lineage`) and, separately, `ignite/chat/live-sessions.js:27`'s `DEFAULT_FEED_TIMEOUT_MS` (240000) being LESS than `ignite/supervisor/spawn/live-sessions.js:56`'s `DEFAULT_TURN_TIMEOUT_MS` (300000) — the bridge always gave up on a warm turn 60s before the daemon reaped it, making a cold fallback fire reliably. No idempotency mechanism existed at all: `outbox.js` mints a fresh id per post (proves Slack was asked, not that the question was already answered), and the only duplicate guard (`chat-bridge.js`'s `preEnqueueRefusal`) is byte-equality on OUTBOUND text, gated behind `!threadMap.has()` so it never runs on a mapped conversation, and two independently-generated answers are never byte-equal anyway.

## Mechanism
Two independent literal constants (240000 vs 300000) sitting in two different files, in two different processes (bridge vs daemon), with no shared source — a routine edit to either literal could silently invert or widen the gap, and did. Separately, `deliverToOwner` (the ONE choke point every conversation-addressed post passes through) had no concept of "which owner message am I answering" at all — only outbound text and channel/thread addressing — so nothing could distinguish "a second, differently-worded answer to a message already answered" from "a legitimate new answer".

## Attempts
First attempt held — checked: `slack-duplicate-replies.md` (the investigation handoff this fix executes against) and this component's `_issues.md`/`_creations.md` (grep floor for idempoten/duplicate/warm.cold/feed.timeout/turn.timeout/answered:false — no prior fix of this specific pair found).

## Fix
(1) New leaf module `ignite/supervisor/spawn/live-turn-timeout.js` exports `DEFAULT_TURN_TIMEOUT_MS` as the ONE source; `supervisor/spawn/live-sessions.js` now imports it instead of a literal, and `chat/live-sessions.js` derives `DEFAULT_FEED_TIMEOUT_MS = DEFAULT_TURN_TIMEOUT_MS + 30000` instead of carrying its own 240000 — proven single-sourced by editing only the leaf file and observing both sides move together (see commit message / seat report). A tiny dependency-free leaf (not the whole `supervisor/spawn/live-sessions.js` module) so the bridge process — which must hold no spawn capability, `probe-chat-boundary` — never pulls in `child_process`/`harness-config`/`bwrap` just to read a constant.
(2) `chat-bridge.js#deliverToOwner` takes an explicit `inboundMsgId` argument and refuses a second `answersOwnerAsk` delivery carrying the SAME id (`answeredInbound` map, keyed on the OWNER's message identity, never on reply text — two independently-generated answers are never byte-equal, so widening the existing byte-equality guard was explicitly rejected as the fix). Gated on `answersOwnerAsk` (the SAME signal `askRecord.reapAsk` already trusts) so a P3 system notice (slow/give-up/dead-air) can never mark or be blocked by the key — a first cut that checked/marked unconditionally would let a "still working" ping silently suppress the real answer that follows it (caught by this seat's own probe before landing). A first cut that instead kept a side-channel `chatThreadId -> latest owner ts` map (stamped on every inbound message, read back inside `deliverToOwner`) was ALSO rejected: it reintroduced the bug class `reply-leg.js`'s own header warns about — not every delivery on a conversation is preceded by a fresh owner message (a revive, a wake re-dispatch, a multi-page log continuation, a compaction follow-up all deliver against an already-armed cycle with no new inbound event) — measured via `probe-chat-reply-leg.js` checks g/h/i/j/k/l/n/o/p/q going red (the stale "latest id" wrongly refused every one of them).

## Consequences
The warm leg's half is fully wired (`onChatMessage`'s warm branch passes `chatMsg._msgTs`). The cold leg's own delivery (`reply-leg.js`'s `deliver()` call, inside its per-exec delivery block) needs the SAME `inboundMsgId` threaded through `arm(chatThreadId, inboundMsgId)` → stored on `p.inboundMsgId` → passed into that `deliver()` call — a small, additive, non-breaking change (extra optional argument) — but it is NOT included in this fix: at commit time `reply-leg.js` carried a large, unrelated, in-flight uncommitted edit (`dup-revive-lineage`'s session-lineage-fork fix, the OTHER contributor to this same owner-visible defect) and committing that file would have published someone else's unfinished, unreviewed work under this commit. `chat-bridge.js` already calls `replyLeg.arm(chatMsg.chatThreadId, chatMsg._msgTs || null)` — harmless today (the unmodified `arm(chatThreadId)` ignores the extra argument) and forward-compatible for whoever lands the `reply-leg.js` threading next. Until that lands, the guard is DORMANT for the cold leg (only warm-vs-warm races, which do not structurally occur today, are covered) — a disclosed gap, not a silent one.

## Verification
New `ignite/chat/probes/probe-chat-duplicate-idempotency.js` (13 checks) proves: (a) a warm answer followed by a differently-worded delivery carrying the same `inboundMsgId` is refused — quoting both texts and confirming they are not byte-identical; (b) a genuinely unanswered message's cold delivery is NOT suppressed (the discriminator); (c) a system notice never marks or trips the guard, but a genuine second answer after it still does. Red-first proof: ran the same probe against a clean `git worktree add <tmp> HEAD` (pre-fix) — the guard-dependent checks failed and BOTH texts posted, reproducing the duplicate; restored (working tree with the fix), all 13 pass. Full `node ignite/deploy/probe-suite.js --dir chat/probes` run with ONLY this fix's files applied to a clean HEAD worktree: 25/29 pass, the same 4 pre-existing failures as an unmodified HEAD (`probe-chat-ask-release`, `probe-chat-boundary`, `probe-chat-live-session`, `probe-owner-ask-hold` — none caused by this change). Not yet deployed.
