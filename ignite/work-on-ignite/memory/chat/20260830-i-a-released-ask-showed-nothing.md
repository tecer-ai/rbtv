The asks were on `stools-canvas-audio-elevenlabs` and on `meet-transcript-summarizer`. The re-send bought a goal-master sitting that read the bare letter `a` as a check-in and joined the goal's roster as a paneless owner door. Filed as `G-second-brain-43-0828-2119` against `ignite/chat/chat-bridge.js`; the owner ordered it fixed on 2026-08-30. ## Mechanism
The ask-release leg reacted on nothing, then deleted the thread from `askThreads`.

Two independent lines in `chat-bridge.js#releaseAskFor`, and neither is a parser bug. First, nothing on the ask-release leg ever reacted: the ⏳ read-receipt is stamped only by `markPending`, and the only two callers were the warm forward and the cold forward. A reply that RELEASED an ask therefore produced the same visible nothing as a reply the bridge had dropped — and the owner cannot tell those apart, so they re-send. Second, an actual release ran `askThreads.delete(<channel>:<threadTs>)`. That map is the ONLY thing that makes `onChatMessage` recognize a message as an ask reply (it is checked before every other leg, keyed off the raw event). Deleting the entry did not merely forget a finished thread — it re-classified every later message in it as ordinary goal-channel traffic, which routes to the goal master. The two lines compose into the observed loop: no ack causes the re-send, and the deletion turns that re-send into a paid opus sitting with roster side effects.

## Fix
Commit `4ba72876`, two hunks in `releaseAskFor` plus the state loader. (1) When `askDoor.release` reports `released === true` — the exact condition behind the journal's `authorized reply RELEASED the ask` line, so marker and log cannot disagree — the bridge queues a `white_check_mark` reaction on the owner's own `_msgTs` through the existing serialized `queueReaction` chain. Reusing ⏳ was rejected: ⏳ means "accepted, an agent will answer you" and is REMOVED when that answer lands, so it would promise a reply that is never coming and would collide with `hourglassAt` bookkeeping on the same conversation. Every §2.4 refusal returns `released: false` and so gets nothing, which is the ruling already in force — wrong thread and unauthorized are silent, unparsed posted its own NACK, a mechanical verb has the pause/resume door's answer. (2) The delete becomes `markReleased`, which keeps the entry with `released: true`, `releasedAt` and the recorded `outcome`. A later authorized, parsed reply then reaches this same door with `reap: entry.released !== true && …`, so `ask-thread.js` returns `parsedOnly` without reaping, and a short in-thread NACK naming the recorded outcome is posted through the bridge's own `postSlack`. Rejected alternatives: a grace window (a timer plus a clock to be wrong about, for a fact that never expires), and widening `ask-thread.js` with a third act (the module holds no state by design, and the "already answered" fact is the bridge's, not the door's). The bound on the map is a COUNT, not an age or a reaper: `RELEASED_KEEP = 200`, oldest-by-`releasedAt` evicted when a new entry is marked, chosen because eviction then happens on the only event that can grow the set and the entire cost of an eviction is that a reply to a months-old answered thread falls through exactly as it did before this commit.

## Consequences
The already-answered refusal sits BEFORE the `kind` fork, which closed a second hole the deletion had been hiding: with the thread remembered, a repeated `approve` in a materialized approval thread would otherwise have re-dispatched D12 and started an execution twice. The same-cause delete on the approval leg (`dispatched.done === true`) was changed to the same mark for the same reason. Two `probe-chat-approval` arms asserted the deletion as the mechanism — B3 (`b3.leg !== 'ask-release'`) and D4 (`!_askThreads.has(...)`) — and were inverted in place with the reason recorded beside them; B3's actual safety claim, exactly one `materialize` call, is unchanged and still asserted. `probe-chat-ask-release` E6 was inverted for the same reason and E8 now expects two persisted entries. The state file gained three additive keys with `STATE_VERSION` unchanged; nothing migrates old entries and nothing may — they carry none of the keys, load as `released: false`, and behave as before. The filing's third suggestion, guarding the goal master against reading a bare single letter as a check-in, was left undone deliberately: with the thread remembered the re-send never reaches a goal master.

## ATTENTION
1. The ✅ fires on `released === true` and must stay there. Moving it to "the ask door handled this message" would put a landed-answer mark on every refusal — including the unauthorized reply that §2.4.2 requires to be answered with total silence, which would hand anyone in the channel a way to make the bot respond on demand.
2. `reap` is now suppressed by `entry.released` as well as by the approval `paused` flag. An edit that reverts it to `!(isApproval && entry.paused === true)` re-arms a second `reapAsk` on every remembered thread — a relaunch signal fired at a seat nobody re-asked, which is the exact failure `[T3-R22]` was written for, now reachable from every ordinary ask rather than only from a paused approval.
3. The already-answered refusal must stay ABOVE the `kind` fork. Below it, a repeated `approve` in a materialized approval thread reaches `approvalDispatch` and starts an execution a second time; the deletion this commit removed was the only thing that had been preventing that.
4. `askThreads` entries are restored by a WHITELIST in `loadState`, not by spreading the parsed object. A key written into the map but not added to that loader is silently lost at the next restart — and the bridge is a systemd unit with `Restart=on-failure`, so the restart lands in the middle of ordinary owner traffic rather than at some rare moment.
5. `RELEASED_KEEP` bounds the map by count and is enforced only inside `markReleased`. Code that writes a released entry by calling `askThreads.set` directly bypasses the bound entirely, and the map grows without limit through the state file with nothing to notice it.
- the released thread stays in askThreads on purpose — deleting it is what turned the owner's re-send into a goal-master sitting
