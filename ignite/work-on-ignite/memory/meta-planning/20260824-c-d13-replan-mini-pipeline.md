## Motivation
D13 replanning — patch a milestone whose closing gate returned FAIL — had a settled design in the redesign baseline but no workflow content anywhere in `meta/planning/`. The old system replanned through the per-milestone splice retired by D9/D10, so after `impl-pipeline-seats` authored the five-seat one-pass planning pipeline (`67f93286`) a gate FAIL had nothing to route to. The runtime half already existed: `impl-planning-door` landed the door, the `planning/current/` lock and the supervised materialize wrapper, and `spec-planning-door` §2.3 fixes D13's mint as path A (same-goal atomic seat mint inside the EXISTING execution goal) through that one wrapper. Nothing was owed in code; what was owed was the scaffolding a mint has to instantiate.

## Design
Three seats reusing the pipeline's understander/drafter/verifier prompts byte-unchanged, paired with two new tasks — gap-understand (verdict + what execution produced, ending in one contained|cross-milestone call) and patch-draft, walled to one milestone and an unwidened envelope.

Understand → draft → verify, one linear pass. No design stage (the milestone's contract is frozen, so the approach is not open) and no review stage (verify's contract check is the only check the patch needs) [D13, T3-R9]. All three seats REUSE the pipeline's `understander` / `drafter` / `verifier` prompt definitions BYTE-UNCHANGED — the D13-specific part is the paired TASK. Two new tasks: `gap-understand` (the combined understand — gate verdict plus what execution actually produced, ending in one explicit `contained` / `cross-milestone` boundary call) and `patch-draft` (the patch, or the escalation analysis). `verify-plan` is reused as written because its check (b) — every milestone id still present with its done-criteria unbroken — IS the unchanged-contract check D13 needs [T3-R16].

Two walls are written into `patch-draft`'s done contract rather than left to seat judgment [T3-R19]: the patch amends ONLY the failed milestone's plan and seats, and it MUST NOT widen the permission envelope. A gap that crosses milestone boundaries, or that needs one more grant, is not patched at all — the disposition line flips to `escalate` and the file carries analysis with ZERO patch content, so an escalation cannot be materialized by mistake. The disposition is a machine-readable second line (`disposition: patch|escalate`) bound to the gap brief's boundary call, so the routing fact is one authored word rather than an inference over prose.

Rejected: a fourth "escalate" seat — the escalation is the draft seat's own product under a different disposition, and a seat that only re-reports another seat's conclusion fails the ethos ladder's first rung. Rejected: editing the three reused prompts to name D13's artifacts — the prompts are another seat's product and each already delegates its write path to "the path the paired task's Write clause names", which is exactly the seam a new task is supposed to use. Rejected: implementing the two-failed-replan counter — that is daemon policy and belongs with the verdict history, not with a seat that cannot see its own predecessors.

## How it works
`meta/planning/workflows/d13-replan/` pairs `workflow.md` (orientation) with `d13-replan.csv` (three rows, linear, no forks, no guards). Seat ids are `repl-understander` → `repl-drafter` → `repl-verifier`: the workflow FOLDER carries the D13 name but the seat prefix cannot, because `workflow_code()` in `ignite/capabilities/bindings/tool/bindings.py` refuses any code that is not exactly four ASCII LETTERS and `d13` carries digits. The code names the casting sheet `.rbtv/config/modules/meta/planning/bindings/repl.json`.

Three rows were appended to `meta/planning/seats.csv` pairing the reused prompt with the D13 task: `repl-understander`/`understander`/`gap-understand` writing `planning/replan/gap-brief.md`, `repl-drafter`/`drafter`/`patch-draft` writing `planning/replan/patch-plan.md`, and `repl-verifier`/`verifier`/`verify-plan` writing `planning/approval-digest.md` with `on-fail-relaunch` = `repl-drafter,repl-verifier` — declared on the seat that ISSUES the verdict, per the authoring checklist, so a failed check re-fires the fixer AND the checker. Both new artifacts land under the goal's `planning/` workspace (the one subtree the cage opens read-write to every seat) at `planning/replan/`, each carrying a first-line marker its consumer checks: `GAP-BRIEF` and `PATCH-PLAN`. `planning/current/` is deliberately untouched — it is the planning door's locked derived tree.

Stage-to-stage launch is the ordinary task-graph `after` edge [CF-11]; the workflow implements no mint, no splice and no door of its own.

The same applies more weakly to `drafter`'s step 1, which orders a `DESIGN` read. Both files are `impl-pipeline-seats`' product and were left byte-untouched.

## ATTENTION
- A workflow folder name is NOT the workflow code. `workflow_code()` derives the code from the shared seat-id prefix and refuses anything that is not exactly four ASCII LETTERS, so the D13 seats are `repl-*` inside a folder called `d13-replan/`. Naming the seats `d13-*` to match the folder passes every authoring read and is refused later at casting-sheet time, after the workflow is authored and committed — the same wall the forge workflow met with its five-letter `forge-*` ids.
- The two-failed-replan cap in `workflow.md` is documentation of DAEMON policy, not an unfinished seat feature. A seat in this workflow cannot see how many prior replans a milestone has had and must not be given a counter; implementing one inside a seat would produce a cap that resets on every mint.
- `verify-plan` and the `verifier` prompt still order an `APPROVAL-DIGEST` with the four plan-approval owner outcomes, which is the wrong product for a lane that continues autonomously and only notifies. This reuse was directed, and the two files belong to the pipeline-seats seat; do not "fix" it by editing them without a ruling on who owns the D13 verify contract.
- `patch-draft`'s two walls are done-contract clauses, not prose advice: a patch touching a second milestone or adding one grant is a FAIL, and the correct move is the `escalate` disposition with zero patch content. An escalation that carries patch content is materializable by mistake, which is why the contract demands the file be empty of it.
- The D13 artifact paths (`planning/replan/gap-brief.md`, `planning/replan/patch-plan.md`) are literal `goal-writes` values with no milestone token, so two D13 replans of DIFFERENT milestones in the same execution goal would write the same two paths. Bounded in practice by one replan being live at a time, but it is not enforced anywhere in this workflow.
- seat ids must be four ASCII letters (repl-*), not the d13 folder name
