## Motivation
`relaunch-budget.js`'s own header describes an exit — *"THE EXIT: ONE BOUNDED D6 LEADER ATTEMPT. The lane stops, the leader gets exactly one attempt"* — that the running system never took. A repo-wide grep for `leaderHandoff` and `executeLeaderInstruction` returned only their definitions, the export block and the module's selftest: NO production caller anywhere. `budgetState` and `spendRecoveryRelaunch` were equally unwired, so the recovery relaunch budget counted nothing and could not trip. The consequence, recorded as role-action-program matrix row M56 (build entry B11): the leader was never asked for any of the four instructions the design gives it (`rewrite-brief` / `reassign` / `blocked-pending-plan-gap` / `escalate`), and had no verb, message type or payload path by which it could report one — the knowledge graph's *"arbitrates redo-exhaustion"* mandate had no mechanism at all. `meta/leader/prompts/leader.md` does not mention the duty either.

## Design
Three parts, each placed where the existing structure already had a home for it, so nothing new transports anything.

THE ASK is asked by `reconcile.js`, in the launch loop, on a class-A `incomplete` target — the recovery cause `armed-incomplete` [T1-R6]. The budget is asked FIRST and that branch RETURNS, which is the module's own stated contract: budget and attempt-counter are independent, whichever trips first takes its exit, and the other must not also fire in the same act. The three new action kinds are therefore excluded from the counting block below them, exactly as the disarm and provider-backoff skips are. The ask itself rides the door that ALREADY puts a question in front of the leader — the D33(a) leader wake — with `handoffPayloadText` appended after the boot prompt, in the same shape `nontermPayload` uses. A new coordination verb was rejected: the coord kit is another component's, and `supervise surface-refusal` addresses `owner`, not the leader.

THE ANSWER is a JSON file at `.rbtv/runtime/ignite/leader-instructions/<goal>--<seat>.json`, beside the ask records [spec-state-store 1.1] and in the same shape `blocked-pending-plan-gap` already writes `replan-requests/` in. A file and not a CLI verb because there is no ruling instrument left to carry it: `rule-disposition` was deleted [T2-R12, T1-R9] and nothing replaced it. Parsing the leader's prose off `coordination/messages.md` was rejected as fragile — a judgment that must be machine-applied needs a machine-readable carrier.

THE SPEND is `spendRecoveryRelaunch({cause:'armed-incomplete'})`, called at the moment a class-A relaunch actually reached the queue — never on intent, per the module's own rule that a budget decrementing on consideration stops lanes that were never relaunched.

## How it works
`reconcile.js#handoffFieldsFor` assembles the payload from what the pass already reads: the seat's `seats/<seat>/seat.md` as the brief, its last two ENDED session rows for the kill reasons (`disposition` + `disposition-writer`) and the transcript pointers (`harness:native-session-id @ workdir`), and `checkpoint.readProgressNote` for the note. ⚠ The progress note is ONE file per seat, not one per sitting, so only the latest sitting's note can exist on disk; the earlier one is reported absent WITH THAT REASON rather than as a seat that wrote nothing — `assembleHandoff` refuses a payload with a hole [T4-R6] and a blank would spend the leader's one attempt on a guess. `leaderHandoffFor` then calls `relaunchBudget.leaderHandoff`, which sets `leader_attempt_used` in the same act; the commonest failure arm is that flag already being 1, which is not an error but the bound working, and the pass records `budget-exhausted-no-handoff`. On success the leader is woken by `launchSitting` with `promptFn` composing boot prompt + `handoffPayloadText(payload, answerPath)`; the block names all four instructions off `INSTRUCTION_LIST`, the tripped cap and its counts, the brief, both sittings' notes, the kill reasons, the transcripts, the exact answer path, and the CF-3 wall in the leader's own reading. `drainLeaderInstructions` runs at the TOP of each reconcile pass (never on a dry pass, and only with an ending store and a workspace root), reads every pending file whose name starts `<goal>--`, applies it through `executeLeaderInstruction` — the one place an instruction is ever performed — and moves the file to `done/` or `refused/` with an `.outcome.json` beside it. A file that stayed would re-apply the same judgment on every cadence: for `rewrite-brief` a lane re-armed forever, for `escalate` an ask re-opened forever.

## Consequences
The relaunch budget now actually counts on the live path, so `recovery_relaunch_count` starts advancing on class-A relaunches where it previously never moved — a lane that reaches `relaunch_budget_total` (seeded 5) now stops and asks the leader instead of relaunching indefinitely under the attempt counter alone. Composes with B16 in the same commit: a goal with no leader chair records `budget-exhausted-no-handoff` rather than handing the payload nowhere. `reconcile.selftest.js`'s counting-branch RED arm had to be re-anchored — it matched the whole `if` condition verbatim, which grew three arms here; it now anchors on the first and last lines so the next arm added does not silently un-anchor the red. The leader's own instructions still do not mention this duty: `meta/leader/prompts/leader.md` is another seat's custody and the line is handed off, not written here.

## ATTENTION
- The budget question RETURNS from the launch loop and its three action kinds are excluded from the counting block. Adding a fourth budget-exit kind without adding it to that exclusion list spends BOTH bounds on one event and lands the owner ask a pass early.
- The progress note is ONE file per seat. `sittingDirs` in `assembleHandoff` implies one directory per sitting and there is no such layout — pass `progressNotes` explicitly, as `handoffFieldsFor` does, or the same note is read twice and reported as two.
- `leader_attempt_used` already being 1 is the NORMAL steady state after the first ask, not an error. `leaderHandoffFor` returns `{ok:false, why:'handoff-refused'}` for it; treating that as a fault would re-ask a bound the design deliberately spends once.
- A pending instruction file MUST leave the inbox in the same act it is applied. `settleInstruction` is what guarantees that; a drain that only reads would re-apply `rewrite-brief` on every cadence.
- The answer path is a FILE because no ruling CLI exists. If a leader-facing ruling instrument is ever built (matrix B9), this inbox is the thing it should write, not a second channel beside it.
- the budget exit RETURNS and is excluded from the counting block - a new exit kind must join that exclusion
