## Observed
Every uncaged staff sitting — `leader`, `goal-master`, `channel-master` — ran with no `~/.local/bin` on its PATH, so every instrument the three roles are promised BY NAME resolved to `command not found`. Measured across the 2026-08-26 role-action-program inventory (matrix rows M1, M2, M18, M45, M53, M58 and 27 more): inside a live channel-master sitting (`68b787e5`) `which owed-answers` → not found, `PATH=/usr/local/sbin:…:/snap/bin`; the live uncaged spawn argv of 2026-08-26T11:24:02Z carries no `--setenv` at all; `systemctl --user show-environment` → PATH without `~/.local/bin`. The same names run fine by absolute path and fine once `~/.local/bin` is prepended by hand — 10 of them re-verified `--help`-only in the matrix's §3.0 step-2 table. An earlier, narrower sighting is in the acceptance wave: `owed-answers` missing in one sitting and present in the next, 50 s apart, same route. Deployed tree and HEAD agreed — the early return has been in `spawn.js` since the staff-uncaged ruling [T2-R4] and no later commit touched it.

## Mechanism
`composeCageFor` (`ignite/supervisor/spawn/spawn.js`) is the ONE composer both spawn doors use, and it is where a seat's declarations become the walls and the environment of the process about to run. Its first line was `if (isStaffUncaged(seatPath)) return { uncaged: true };`. Everything that reads a declaration sits AFTER that line: `resolveLocalBinGrant` (which reads `local-bin:` out of the seat's own `seat.md` frontmatter, via `seat-grants.js#seatDeclares`) and the `--setenv PATH` composition at the tail of the function. So for a staff seat the declaration had NO CONSUMER — not a wrong value, an absent one. The caged branch's own comment states the contract the uncaged branch was silently failing: *"A mount the occupant cannot NAME is not a grant. Emitted only WITH the grant."* The two masters had carried `local-bin` in their `meta/master/seats.csv` `cage-grants` column all along; it did nothing for them, because they are staff and never reach the reader. Nothing downstream compensated: an uncaged seat takes no bwrap wrap, so it has no `--setenv` flag list, and none of the three doors composed an environment of its own. `carrier.js#toolExecEnv` — the F1 fix that gives a FIRED TOOL its PATH — is a different door (`fireTool`, not a seat spawn) and its header says so explicitly.

## Attempts
First attempt held on this exact defect — checked: `git log -S'isStaffUncaged' -- ignite/supervisor/spawn/spawn.js` and `git log -S'local-bin'` show only the grant's original introduction and the D56/D74 refusal-shim work (`7f6eaf3e`, `9060c3cc`), neither of which touches the uncaged branch. The SIBLING class was fixed twice before and each time the fix was scoped away from this branch on purpose: `d-owner-f1-carrier-env-0808` fixed the same "systemd-run --user inherits the manager's env, which has no `~/.local/bin`" fact for fired tools at the carrier (`carrier.js#toolExecEnv`), and its own comment records the deliberate non-unification with the caged-seat composer — *"they are not required to agree"*. That reasoning is why the third case, the uncaged seat, had no owner at all. The matrix put the question to the owner as OQ-15 (*was the missing environment an omission or a design choice?*) and OQ-21 (*where should the repair be made*); the answers are "omission" and shape (b+).

## Fix
Commit `af326d61` (2026-08-26). The uncaged branch now reads the SAME declaration through the SAME reader and composes its PATH through a new single-policy function `composeSeatPath(pathDirs)`, which the caged branch's `--setenv PATH` line was refactored to call — so there is exactly one PATH policy for a seat and a change to it cannot reach one branch and miss the other. The branch returns `{ uncaged: true, env: { PATH } }` when the seat declares `local-bin: true`, and `{ uncaged: true, env: {} }` otherwise.

Shape (b+) is the owner's ruling of OQ-21 (`role-action-program/decisions.md`, 2026-08-26): honour the declaration, never grant unconditionally. Option (a) — grant it to every uncaged staff seat regardless of the descriptor — was rejected because it makes the declaration decorative and removes a seat's ability to decline the grant; option (c) — fix it in the descriptors alone — is impossible, because the descriptor is read by code the uncaged path never reaches. The ruling's stated consequence was that (b) alone fixes the two masters and leaves the leader exactly as broken, so the same commit adds `local-bin` to the leader's `cage-grants` in `meta/leader/seats.csv` — the catalog column that `materialize-seats.py#_cage_frontmatter` renders into the descriptor frontmatter `seatDeclares` reads.

An uncaged seat has no flag list to ride, so the composed `env` is applied at each of the three doors that consume `composeCageFor`, one line each: the dispatch (headless) door passes it as `setenv` in `common` → `systemd-run --setenv`; the live/warm-session door passes it into the same `buildSystemdRunArgs`; the headed door passes it into `composeSeatSpawn`, which emits `tmux new-window -e NAME=VALUE` — the only environment channel a pane with no bwrap wrap has. `spawnSetsid` learned `setenv` in the same change (merged OVER `process.env`, never replacing it — an uncaged child needs HOME, USER and the harness credentials), so the repair cannot hold on the production carrier and silently rot on the fallback one.

## ATTENTION
- Nothing here proves a bare tool name works in a live sitting. The composition is proven; the sitting is not. Until CP-2 re-spawns a staff seat and runs a bare name, this is a fix in the tree, not a fix in the running system — and the daemon boots from the deploy worktree, not from this repo.
- A staff seat's PATH follows its catalog row's `cage-grants` column, NOT the fact that it is staff. Removing `local-bin` from `meta/leader/seats.csv` or `meta/master/seats.csv` silently returns that role to `command not found` for every named instrument, with no refusal and no log line — the grant's absence is indistinguishable from a seat that never wanted it.
- There are now THREE PATH composers in this tree and they are not one thing: `composeSeatPath` (seat spawns, caged and uncaged, grant-scoped), `carrier.js#toolExecEnv` (fired tools, unconditional), and the daemon unit's own `Environment=PATH=`. `carrier.js`'s header records the non-unification as deliberate. Changing one does not change the others; a symptom that looks like "the daemon's PATH" may be any of the three.
- The `env` returned by `composeCageFor` reaches the process only because each of the three doors applies it. A NEW door that composes through `composeCageFor` and ignores `.env` gets a staff seat with correct walls and a broken PATH — the exact defect this entry records, re-created one door at a time. `seatCage.uncaged` and `seatCage.env` travel together.
- `tmux new-window -e` is the headed door's only env channel and it is a tmux argv flag, not a bwrap or systemd one: it must stay ahead of `-P -F` and before the `--` separator. Moving it past `--` turns it into an argument of the pane command.
- A staff seat's PATH follows its catalog row's cage-grants column, not the fact that it is staff — removing local-bin returns the role to command-not-found silently
