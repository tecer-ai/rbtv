## Observed
A goal created by the DIRECT route was skipped by the daemon forever, in silence. Measured on the live box 2026-08-26: the channel-master sitting `d6a47ac2`, asked in a Slack DM to create a goal, ran `rbtv goal scaffold cli-tools-reachability-report --lane daemon` as its `master-scaffold-flow` reference orders. `ls .rbtv/goals/cli-tools-reachability-report/` showed no `taskforce.csv` and no `seats/`; `execution-lane` read `daemon`; `journalctl --user -u rbtv-ignite | grep -c cli-tools-reachability-report` returned **0** — the daemon never mentioned the goal once over its entire life. The creating command had printed `scaffolded … / reindexed` and exited 0. Same shape recorded in the role-action-program CP-1 matrix rows M30/M31/M32 (build entry B12) and in the paused acceptance wave's `bound-direct-create` cell.

## Mechanism
Two halves, one at each end of the path. `goal_cli.py#cmd_scaffold` writes `goal.md`, `threads.sql`, `execution-mode`, `execution-lane`, `milestones.csv`, `planning/` and the standard artifacts — and no `taskforce.csv`. That file has exactly ONE writer in the system, `scaffold-seats` (`planning/materialize-seats.py`), which requires `--seat|--workflow` plus an explicit `--after|--root` and is reached only by the goal-creation request route (`goal_creation_request.py#create`). Nothing the daemon runs invokes it. At the other end, `supervisor/lane-watch.js#runLaneWatch` adopts a daemon-lane goal only when `taskforce.csv` exists, and its skip was `skipped.push({goal, reason:'no-taskforce-yet'}); continue;` under a comment reading *"a normal state between `rbtv-goal scaffold` and `rbtv-goal materialize`, not a fault. Quiet."* Both clauses of that comment were false: it is not a state the goal leaves on its own, and quiet meant the goal was unfindable. The repair the comment names is itself unavailable — `rbtv goal materialize` REFUSES when `taskforce.csv` is absent or empty (`goal_cli.py:2885-2891`), which is precisely this state (matrix M28, the `master-bootstrap` §3 self-contradiction).

## Fix
Owner ruling OQ-22(b) (2026-08-26): **no queue — the lane advances the goal**, so a created goal must end WITH a taskforce and the fix is the missing taskforce plus a loud skip, with no job-queuing added. Cause end: `cmd_scaffold` now REFUSES `--lane daemon` (typed code `daemon-lane-unmaterialized`) unless the caller passes `--materialize-follows`, placed beside the 7.777 lane gate and therefore BEFORE the first filesystem write, so a refusal creates nothing and the operator can re-run the right command against the same name. The refusal names both routes that do produce a taskforce (the request route; or console lane → `scaffold-seats` → `lane --set daemon`). Writing a taskforce here was rejected: there is nothing to derive one from (no workflow is named at scaffold), and a header-only file would be worse than none — the goal would be ADOPTED with zero seats and look healthy while doing nothing. Refusing `--lane daemon` outright was rejected because it would break the one creation route that works. The console lane is deliberately untouched: a human types `rbtv run` and is present to see the goal has no seats, and `plan-console`'s own entry procedure scaffolds exactly that way. `--materialize-follows` is not an override but the route's declaration, and it is made TRUE rather than asserted: in the same change both of `create()`'s refusals (ruled name absent from PATH; missing `--seat|--workflow` or `--after|--root`) moved AHEAD of the scaffold act, where they always belonged as pure input checks — run after it, they left a created daemon-lane goal standing with no second act coming, i.e. this exact dead end minted by the handler that declares it materializes. Watcher end: the skip stays (there is nothing to seed) and gains a `say(shouldShout(goalFolder, raw) ? 'warn' : 'debug', …)` naming the goal, the missing file, and `scaffold-seats` as the fix — never `rbtv goal materialize`, which refuses in this state.

## Consequences
`create()`'s two refusals now fire before any write, so a request refused for a missing insertion point no longer leaves an orphan goal directory behind; `scaffold_and_queue`'s V2 disclosure of a colliding goal's `seats/` count still reads the same way. A `scaffold-seats` invocation that fails at RUNTIME still leaves the goal standing (no unwind is built, and none may be added) — that goal is now named loudly by the watcher rather than skipped. Build entry B13 (`master-bootstrap.md` §3's self-contradiction) depends on this shape and is another seat's. The `rbtv goal materialize` refusal on an absent taskforce is untouched here.

## ATTENTION
- `rbtv goal materialize` is NOT the repair for a taskforce-less goal — it REFUSES when `taskforce.csv` is absent or empty, which is exactly that state. Every surface that names it as the fix for this state is wrong; the writer is `scaffold-seats`.
- `--materialize-follows` is a DECLARATION, not a bypass. A caller that passes it and does not invoke `scaffold-seats` in the same act re-creates the dead end under a flag that says otherwise. Its truth rests on `create()`'s refusals sitting AHEAD of the scaffold call — move either one back below and the declaration becomes a lie.
- A header-only `taskforce.csv` is worse than none: `lane-watch` would ADOPT the goal, report it seeded, and enqueue nothing. Do not "fix" a taskforce-less goal by writing an empty one.
- The loud line is keyed on the LANE MARKER text via `shouldShout`, not on the taskforce. Fixing the goal by materializing it does not itself re-arm the line; a successful seed does (`failedOn.delete`). A goal that stays stuck is named once per daemon boot, by design.
- The console lane is deliberately NOT gated. `plan-console`'s entry procedure scaffolds a console goal with no taskforce on purpose. Extending the gate to it would break that flow.
- rbtv goal materialize REFUSES on an absent taskforce - it is not the repair for this state; scaffold-seats is
