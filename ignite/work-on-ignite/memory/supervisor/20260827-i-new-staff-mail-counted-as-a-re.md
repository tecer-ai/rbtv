## Mechanism
Two independent births, both in `reconcile.js`.

The count itself. `countRetry` advanced the counter on every pass that produced a launch target, testing nothing about what the pass was owed for. spec-recovery section 5 says the counter "increments on a same-reason RETRY", and a retry is a second attempt at work already counted. The journal's own pass lines show the owed set being strictly REPLACED each hop — classA `[plan-understander]` at 16:40Z, `[plan-designer]` at 16:55Z, `[plan-drafter]` at 17:11Z, never accumulating — so three FIRST attempts at three different pieces of work were counted as three retries of one failure. At the third the counter reached N=3 and the lane disarmed. The 17:26Z pass, the one whose classA was `[plan-reviewer]` and whose mail was #7, hit `counterDisarmed` and took `skip-disarmed`. Note the reason class that disarmed is `nonterm`, not `unread`: the `unread` target for the same chair is deduped behind it as `skip-already-targeted`, which is why its own counter kept climbing (12 and rising) while never reaching the brake.

The silence. `skip-disarmed` carried no `say()` at all — the audible branches beside it were only the budget-exhausted ones — so the strongest act a pass can take on a lane left no trace. Worse, the exit at N never ran either: `reconcileGoal` reads `engine.endingStore`, and nothing in the deployed tree ever sets it, so `countRetry`'s `!store || typeof store.stampSystem !== 'function'` guard returned `exit: 'no-ending-store'` with no journal line, no `disarmed` stamp and no ask record. That guard is the branch production always took, which is exactly why five rows sat at or past N with no ask directory on disk. `RE_ARM` is a closed list and, as measured below, nothing fires any member of it, so no lane re-armed on its own.

## Fix
Fix at the driver, not the key — the key stays a failure CLASS and `refuseVolatile` is untouched. Each launch target now carries the owed ITEM IDS it was derived from: `owedItems` is `[seat]` for a class-A `incomplete` relaunch (invariant by construction, so the check is provably a no-op there, matching D40), the owed seat names for a `nonterm` leader wake, and the chair's highest pending message number for an `unread` wake. `countAttempt` takes those as an optional `items` argument and advances only when the recorded set INTERSECTS the current one.

Intersection rather than equality is the whole design choice, and it is what lets the fix coexist with the ruling it looks like it reverses. Byte-equality would have made a GROWN owed set read as new work and reversed [C-4]; intersection keeps `{a}` then `{a,b}` counting to N, because `a` is still owed and the leader still owes judgment it was already woken for. Only a set with NO surviving item is new work. And the response to new work is to DECLINE TO ADVANCE, never to reset: `prev.attempts` is carried through untouched, so spec-recovery's "resets ONLY on a named re-arm event" holds byte for byte and the deleted sweep stays deleted. The marker rides the counter ROW as `owed_items`, never the key.

Audibility is a second, separate act. `announceDisarm` journals a `warn` once per (subject, disarm) naming the counter row, the owed items, N, and the four re-arm events, and raises the stop on the surface that already exists for owner-visible stalls — `exhaustion.js#recordGroupedAsk`, the same signature-grouped ask record plus `open_asks` row the exit at N writes. No new channel was invented, which was the explicit constraint. The once-marker is `disarm_announced_at` on the counter row rather than process state, so a restart does not re-announce, a five-minute cadence does not become a five-minute alarm, and `rearm` deleting the row is what makes the next disarm audible again. The exhaustion exit sets the same marker so the two paths never both speak for one disarm. The `no-ending-store` branch announces too: it cannot stamp, but the lane still stops, and the stop is what the owner needs to see.

## Consequences
Nothing was deleted. `countAttempt` gained an optional argument and two row fields (`owed_items`, `disarm_announced_at`); a caller that hands in no items behaves exactly as before, which is why `ticker.js`'s `ticker-deferred` driver needed no change — its subject is `job:<jobId>` and its classes are `unknown-tool`, `unknown-workflow` and `argv-template-refused`, so every re-fire genuinely retries the same job and a new job gets its own counter. `markDisarmAnnounced` is a new export and the only writer of the once-marker.

Three defects found and NOT fixed here, all outside this change's walls. `runtime/ticker/ticker.js`'s `defer-disarmed` action is silent exactly the way `skip-disarmed` was. Nothing anywhere fires a `code-deploy` or `config-change` re-arm — `counters.rearm` has one production caller, `exhaustion.js#consumeDisarmed`, and `consumeDisarmed` itself has ZERO. And `chat/pause-resume.js#applyResume` row 1 re-arms the ENDING flag through `store.fireNamedEvent` but never touches the counter file, while `reconcile.js#counterDisarmed` reads the counter file and not the ending row — so a mechanical `resume {goal}` lifts the stamp and leaves the lane disarmed anyway. Together those mean the seven currently-disarmed live rows cannot be cleared by any wired path.

## ATTENTION
1. This is NOT the deleted evidence-driven sweep coming back, and reading it as one will get it reverted. The sweep CLEARED a count when the owed set changed; this DECLINES TO ADD to a count when nothing it previously counted is still owed, and never resets. Grep for a reset in `attempt-counters.js`: `rearm` is still the only one.
2. The [C-4] inversion survives and `reconcile.selftest.js` still asserts it. Intersection, not equality, is what preserves it — an owed set that grows while its old rows STAND still counts to N. Switching `isRetryOf` to an equality test silently reverses a ruling and reopens the unbounded relaunch the counter exists to close.
3. `reconcile.js#counterDisarmed` reads the COUNTER FILE, and `chat/pause-resume.js` re-arms the ENDING ROW. They are two different facts and nothing joins them, so a mechanical `resume {goal}` today lifts the stamp and leaves the lane disarmed. Do not report a lane re-armed on the strength of a `resume` that succeeded.
4. Nothing in the deployed tree fires any of the four named re-arm events. `counters.rearm` has one caller (`exhaustion.js#consumeDisarmed`) and that function has none, so a restart, a deploy and a config edit all re-arm exactly nothing. A disarmed counter row today is permanent until the ledger is edited by hand.
5. A live counter row written before this change carries no `owed_items`. `isRetryOf(null, current)` returns TRUE by design — a driver that names no items always counts — so those rows keep advancing and stay disarmed. The fix changes what happens NEXT, not what is already stuck.
