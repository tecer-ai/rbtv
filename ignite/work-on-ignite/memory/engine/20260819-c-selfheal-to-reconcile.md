## Design

808902df (2026-08-19 21:23:11Z, `feat(engine): reconcile owed work from the ledgers (D1/D15)`) landed `reconcile.js` as one derivation of owed work from `sessions.csv` and `messages.md`. It never re-derives DAG readiness — it calls `seeding.readySeats` and classifies what those ledgers already say. The rejected alternative is the event/job model above: discrete `selfheal-room*` jobs and a scheduled `goal-watcher-job` that could not see a seat's last disposition or unread mail. d1ca8097's commit message records the deletion method: land the watcher, then a Q1–Q5 coverage table against that code, delete only what the table shows is covered — dead-room detect+recover via `roomState`/`recoverRoom`; shells `jobs/recover-room.py` (that script stays); auto-armed per goal structurally via `lane-watch.js` `maybeReconcile`, no per-goal registration; staleness from the ledgers via `deriveOwed`; per-execution process silence, no, left to `ticker.js`. The ticker's `stall_warn_ticks` / `stall_halt_ticks` / `stall_kill_ticks` / crash-sweep / `dedupeByExecId` arms were marked KEEP because each is keyed on one `exec_id` — "a blind spot, not coverage": a goal that never seeded produces no execution row, so the ticker never saw it either. Owner escalation stays inside the daemon process because a fire-tool job cannot reach the Slack credential (`ticker.js#runToolLikeExec`).

## How it works

`runLaneWatch` in `lane-watch.js` calls `maybeReconcile` once per goal folder that is not `_`-prefixed and that carries `taskforce.csv` or `sessions.csv`; a live console run is `dryRun` so the attached lane is not fought. `maybeReconcile` wraps `reconcileGoal` in try/catch so a thrown pass never kills the daemon tick. Cadence is `CADENCE_MS = 5*60*1000`, persisted in heart-store table `reconcile_pass` (`getReconcilePass` / `setReconcilePass`, same 808902df commit as the schema and migrations) unless `force`. `deriveOwed` classifies four owed sets: **classA** — a seat's last session ended with a non-terminal disposition and no later sitting superseded it; **classB** — a staff chair (`leader` / `consultant` / `goal-master`) has unread mail and is not live or queued; **classC** — classA filtered to `outputs-unverified`; **classE** — frozen-frontier: `readySeats` returned 0 READY, pending seats exist, nothing live or queued. Landing classA does not relaunch the stranded seat: it enqueues the **leader** once with signature `nonterm:<sorted seats>`. ClassB enqueues the chair itself (`unread:<seat>:<lastNum>`). `launchSitting` is `heartStore.enqueue` with `onSeatBusy:'queue'` and `enqueuedBy:'goal-watcher'`; it refuses a missing seat folder, an uncast seat, a missing boot prompt, and a deduped enqueue. On launch failure, `strike` increments a durable `(goal, seat, reason)` row in `reconcile_attempts` (`getReconcileAttempt` / `upsertReconcileAttempt`); at `attempts >= STRIKE_LIMIT` (3 as landed) it runs `coord.py … send auto … --type stuck`; at `STRIKE_LIMIT + OWNER_AFTER_STUCK` (3 more) or if the subject is the leader or goal-master, it calls `lane-watch.alarmOnStall`. If the goal is owed work and tmux `has-session` / `list-panes` shows the room dead or empty, `recoverRoom` shells `jobs/recover-room.py`. `checkinOf` at landing did `Number(raw)` on the session `checkin` cell and treated a non-numeric timestamp as cursor 0 — classB was wrong from the first commit (D35, `20260820-i-unread-mail-cursor-fix.md`).
