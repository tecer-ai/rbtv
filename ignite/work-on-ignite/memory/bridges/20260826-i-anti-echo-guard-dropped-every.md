## Observed
Between the 2026-08-25 cutover and 2026-08-26, every Slack direct message the live-acceptance-tests wave sent to the bot AS THE OWNER — posted through the `stools` CLI with the owner's own user token — produced absolutely nothing: no reply, and, worse, not one line in `journalctl --user -u rbtv-chat-bridge`. Messages the owner TYPED by hand in the same DM worked normally. The wave's seats were blocked on this: they act in the owner's place over Slack by standing owner grant, and the one surface they act through was mute. Raw `conversations.history` on the owner↔bot DM `D0BJ50Y1DC6` settled the shape (2026-08-26): a stools-posted owner message carries `user: U0BK19YE91N` — the owner's HUMAN account, `is_bot: false` — together with `bot_id: B0BSTPLDDT6` and `app_id: A0BSQ2U532N`, and no `subtype`. A hand-typed message from the same account carries `bot_id: null`. Deployed and HEAD were the same tree (`acdc9203`, detached deploy worktree `/home/henri/.local/state/rbtv-deploy`), so this was not a deploy-lag artifact.

## Mechanism
`toChatMessage()` in `ignite/chat/slack-socket-mode.js` opened with `if (event.bot_id || (event.subtype && !isFileShare) || typeof event.user !== 'string' || typeof event.text !== 'string') return null;`. The first arm read the PRESENCE of `event.bot_id` as proof the event was the bridge's own echo. It is not: Slack stamps `bot_id`/`app_id`/`bot_profile` on every message that travels through any Slack app, including one posted with a HUMAN's user token by a third-party app. So the arm's predicate ("is this an echo?") and its test ("is `bot_id` set?") were never the same question, and the gap is exactly the class of message an agent posting on the owner's behalf produces. The second half of the defect was the return path: `toChatMessage` returned `null` with no log call at all, and `handleFrame` only acts on a truthy result, so a discarded message left zero trace anywhere — which is why the symptom read as "the bridge is dead" rather than "the bridge refused something".

## Attempts
First attempt held — checked: the whole `bridges` build-memory index (`_issues.md`, `_creations.md`) plus `capabilities/20260825-c-the-watchdog-alarm-shim-s-slac`, two `rbtv embed-search` queries over `ignite/work-on-ignite/memory` ("slack bot_id anti-echo guard drops owner messages", "ignite/chat/slack-socket-mode.js toChatMessage transport"), and `git log` back to the guard's introduction. Nothing in memory or in git had ever touched this arm: it dates from the module's first version, when the only app posting into these conversations was the bridge itself, and under that assumption presence and identity happened to coincide. `grep -rn bot_id ignite/ --include=*.js` confirmed the arm had exactly one other reader anywhere in the tree (`ignite/chat/goal-channel-cli.js`, a diagnostic printer) and no probe covering it.

## Fix
Owner ruling 2026-08-26 (`1-projects/build-ignite/build/live-acceptance-tests/decisions.md`, "bridge anti-echo guard ruling (a)"): drop only the bridge's OWN echoes, and make the drop audible. `authTest()` — which the bridge already calls once at start to arm the mention route — now also caches `resp.bot_id` and `resp.user_id` into module-scope `selfBotId`/`selfUserId`, and a new `isSelfEcho(event)` drops a `bot_id`-carrying event only when it matches one of them. Caching inside the existing `auth.test` call was chosen over a second identity lookup because the response already carries both ids and the bridge already makes the call; a config-supplied id was rejected outright — the rbtv "content must be general" rule forbids baking an instance id into code, and an id in config is one more thing to get wrong on the next install. `app_id` is deliberately NOT compared: `auth.test` on this workspace returns `bot_id`, `user_id`, `team`, `team_id`, `url`, `user`, `is_enterprise_install` and no `app_id`, so there would be nothing truthful to compare against. The unknown-identity branch fails CLOSED (drops, exactly the pre-ruling behaviour) rather than open, because `chat-bridge.js#start` attaches the socket BEFORE awaiting `authTest()`, and the cost of guessing wrong inside that window is the bridge answering its own posts in a loop. Commit `39bb9a72`; a same-day follow-up `ca07637f` renamed the drop line's Slack-timestamp field from `ts` to `event_ts`.

## Consequences
The `subtype`/`user`/`text` arms are untouched, so what newly reaches the handler chain is exactly one class: an app-posted message carrying a real `user` string. A classic bot post (`subtype: 'bot_message'`, no `user`) is still dropped by the subtype arm. That newly-admitted class is attributable to a real Slack principal and meets the existing per-principal gates — `ignite/chat/forward-path.js#onChatMessage` calls `allowlist.check(chatUserId)` and refuses with `not-paired` before any forward, and `ignite/chat/ask-thread.js#release` refuses a sender outside the instance-config authorized set in silence (spec-owner-io §2.4.2). It also newly exposes a pre-existing hole: the mechanical `pause`/`resume` door runs BEFORE admission in `chat-bridge.js#onChatMessage` and `pause-resume.js#handle` takes no sender argument at all, stamping `who_stamped: 'owner'` unconditionally — any workspace member reaching the bridge can pause a goal. That hole is NOT created here (a hand-typed message from a non-owner already reached it), and it is surfaced to the wave's `loose-ends.md`, not fixed in this change. The first commit also introduced and then fixed its own small defect: the drop line's `ts` field overwrote the logger's ISO stamp, because `index.js#jsonLog` builds `{ ts: isoNow(), ...entry }` and spreads the entry last.

## ATTENTION
- `auth.test` returns NO `app_id` on this workspace — only `bot_id` and `user_id`. Anyone extending the echo test to `app_id` must first confirm the field actually arrives, or the comparison silently degrades to "never matches" and the guard stops catching echoes.
- The unknown-identity branch MUST stay fail-closed. `chat-bridge.js#start` attaches the Socket Mode connection before it awaits `authTest()`, so there is a real window where `selfBotId`/`selfUserId` are null; letting `bot_id` events through in that window lets the bridge ingest its own posts and answer itself.
- The presence of `bot_id` on an event says nothing about whether a human sent it. Any future filter written against `bot_id`, `app_id`, or `bot_profile` alone will drop the owner's own agent traffic exactly the way this one did.
- A drop path in `toChatMessage` that returns `null` without logging is indistinguishable from a dead bridge to whoever is watching the journal. That silence is what turned a one-line predicate bug into a multi-day blocker.
- Admission is NOT enforced before the mechanical `pause`/`resume` door: `chat-bridge.js#onChatMessage` calls `mechanicalDoor.handle` ahead of the forward path, and `pause-resume.js#handle` receives no sender. Do not read "the guard narrowed safely" as "every door downstream authenticates" — only the forward path and the ask door do.
