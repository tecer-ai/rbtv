## Mechanism

§3 ranked the route by WRITABILITY, gating the request route on an EROFS an uncaged seat never gets.

`master-scaffold-flow.md` §3 carried a heading — "Which write route is yours is a FACT YOU READ" — that made WRITABILITY the discriminator: DIRECT `rbtv goal scaffold` was "the master's route (D49): the whole workspace, goals ROOT included, is writable", and the goal-creation request was "fallback only — if a direct write still returns EROFS (old cage, undeployed daemon)". That ranking was true when D49 opened the goals root, and false from `4ed8acc8` (2026-08-26) onward: `cmd_scaffold` now refuses `--lane daemon` before its first write with code `daemon-lane-unmaterialized` (`ignite/operator/goals-tree/tool/goal_cli.py:660-671`), because scaffold writes no `taskforce.csv` and the daemon adopts only a daemon-lane goal that has one. The reference was never swept when the refusal landed — the same second-statement failure class as `20260826-i-master-material-contradicts-th`: the master's prose restates a fact the code owns, and nothing re-derives it.

The consequence is specific to an UNCAGED seat, which is what makes it total rather than intermittent. The channel master assigns the daemon lane on every goal (its own ruled arm, same §3). Its only instruction for the request route was gated on an EROFS it can no longer receive. So the gate never opens, the refusal arrives with no instruction covering it, and the seat improvises — down the refusal's OTHER named route, taken half-way: `--lane console` (act 1) without `scaffold-seats` (act 2). `master-bootstrap.md` §3, loaded next, could not stop that: it told the reader to run `scaffold-seats` "over the plan workflow ALREADY PRESENT for this goal — pre-placed", which contradicts its own firing condition (the act fires only when NO seat and NO workflow materialized the goal, so nothing is pre-placed to find) and describes something that does not exist — a workflow is a CATALOG artifact resolved as `<catalog-root>/<component>/workflows/<name>/`, never a thing sitting inside a goal folder. A reader who looks for the pre-placed workflow, finds none, and has no other instruction does the work itself. The wrong branch is BORN in the reference; the tool, the daemon and the drain job were all correct throughout.

## Fix

Commit `1c49ffc4`, two reference files, no code and no tool change — the defect is entirely in the prose, and the tool is the deployed truth it must agree with.

`master-scaffold-flow.md` §3's route block is replaced by one whose discriminator is the LANE, not writability: the heading now reads "Which write route is yours FOLLOWS FROM THE LANE — never from what you may write", and it opens by stating that `scaffold` writes no `taskforce.csv`, that it therefore refuses `--lane daemon` with `daemon-lane-unmaterialized`, and that the refusal names the two routes that do produce one. The CHANNEL MASTER arm is the goal-creation request, on every goal, always, in four numbered steps: write the payload (closed set, five required, table in `master-instruments.md` § Goals); `rbtv-goal-request validate <file>` before staging; stage into the seat folder's `requests/` inbox and nothing else; report the goal as queued for the daemon's next drain pass, which runs every 300 seconds, name what the owner will see next (goal folder with taskforce, then the Slack channel on first seeding), confirm at the product afterwards, and read the refusal record if one lands beside the request. The arm says outright that the seat never runs `scaffold-and-queue` and never runs `scaffold-seats` — the drain is the DAEMON's job (`spawn-profiles.yaml:1120-1147`), and staging is the whole act. The CONSOLE MASTER arm keeps the direct verb for a console-lane goal, and, where the owner answers `daemon`, carries the refusal's other route as three acts in one sitting (`--lane console` → `scaffold-seats` → `rbtv goal lane --set daemon`) rather than leaving that answer with no route at all.

A new subsection states the refusal handling as four NEVERs, because the observed failure was not a missing instruction but a filled-in guess: never re-run with `--lane console`; never pass `--materialize-follows` (it is the request route's declaration that it materializes in the same act, not an override — the flag's own `--help` says so); never run `scaffold-seats` from this door to repair a goal just created; never perform the goal's own work in the sitting and never call `finish-goal` on a goal just created. Naming the routes without naming the wrong branches was rejected: the seat had the correct route available in the refusal text itself on 2026-08-27 and still took the other one half-way, so the bans are what the evidence asks for.

Two clauses in §4 moved from "the daemon's next watch pass" to "the daemon's next DRAIN pass (every 300 s), and the goal is seeded on a later watch pass". Leaving them was rejected: §3 now states the 300 s drain, and a file that names two different mechanisms for the same wait teaches the next reader to trust neither. Every other ruled line in the file is untouched — §1's raw-ask contract, §2's execution-mode resolution and its interactive confirmation, both lane arms, "State the lane, or the creation is REFUSED", "There is NO profile to name", §4's verify-at-the-product and its three-outcome branch, §5 and §6.

`master-bootstrap.md` §3 is corrected only as far as the routing defect reaches. The "ALREADY PRESENT … pre-placed" premise is struck and replaced with what the workflow actually is — a catalog artifact resolved as `<catalog-root>/<component>/workflows/<name>/`, named by walking the component tree, never something inside the goal, "a bootstrapped goal is DEFINED by having nothing materialized into it". A bound is added stating that this reference is NOT the goal-creation route and is NEVER the repair for a creation that refused: on `daemon-lane-unmaterialized` while creating, the reader is in `master-scaffold-flow.md` §3 and stages a request, and re-scaffolding on the console lane so this reference's command becomes available is named as the defect that produced a seatless goal. §4's existing "completing its work by hand is the one recovery NEVER available" gained one paragraph extending the same bound to the goal's OWN work and to `finish-goal`. A wider rewrite of the file was rejected as beyond what the evidence supports.

## ATTENTION

- A route ranked by WRITABILITY is a route an uncaged seat can never reach. Any instruction shaped "do X; if X returns EROFS, do Y" is dead for a seat that never gets EROFS — and if Y is the only correct route, the seat improvises instead. Rank a route by the LANE, the artifact or the refusal, never by a permission the seat may not have.
- A tool refusal that NAMES two routes is not an instruction: this seat received that exact text and still took the wrong route half-way. Prose that names the right branch must also name the wrong ones it must not take, or the seat fills the gap itself.
- `--materialize-follows` on `rbtv goal scaffold` is a DECLARATION, never a bypass. A master seat that passes it and does not run `scaffold-seats` in the same act re-creates the dead end under a flag that says otherwise — it is reachable from the same `--help` that shows the refusal, which is why the ban is written down.
- The channel master's references do NOT live in its descriptor. `seat.md` carries thin skill loaders naming the absolute SOURCE path, so a reference edit is live at the next sitting with no re-render, no deploy and no restart — and, symmetrically, a re-render is not evidence that a prose fix landed.
- A fix to `meta/master/references/**` is HALF a sweep. The same fact is restated in `meta/master/prompts/**` and `meta/master/tasks/**`, and the tasks render into the live descriptor's definition of done — so a corrected reference can be contradicted by the seat's own done-criteria in the same sitting. Sweep all three trees or say which you did not.
- master-scaffold-flow's route follows the LANE, not writability - the CM stages a request, always
