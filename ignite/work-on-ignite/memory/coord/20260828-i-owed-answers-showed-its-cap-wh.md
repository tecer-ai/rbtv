## Observed
On 2026-08-26 the live acceptance wave's test 2 — an owner DM asking the channel master for "system status", scored against measured reality — FAILED, and the owner ruled it failed by omission (`1-projects/build-ignite/build/live-acceptance-tests/decisions.md`, CP-A ruling 2). The channel master answered "5 ⛔ RUN HALTED" when at least ten run-halted escalations stood across three goals, 17 owed answers in total. The wrong number came out of the seat's ONLY sanctioned derivation, `owed-answers` (`ignite/coord/owed-answers.py`), whose standing prompt forbids any vault-search fallback — so the seat had no second source to notice the disagreement against. Source and deployment were the same file: `~/.local/bin/owed-answers` is a symlink onto the source `ignite/coord/owed-answers.py`, live-read per invocation, so deployed and HEAD did not differ. Re-measured at HEAD 28ad5a22 before the fix: 24 owed answers stood in the live tree, 22 of them halts across 6 goals, and the digest's header said only `24 owed answers — oldest 5 shown` above five ⛔ rows.

## Mechanism
`render()` composed the header as the OWED total alone (`f"{len(rows)} owed answer{'s'}"`, plus `" — oldest {CAP} shown"` when `len(rows) > CAP`, `CAP = 5`), then printed `rows[:CAP]`. Each row carries its own kind tag in the line body — `⛔ RUN HALTED · ` for a halt, `⏳ AWAITING A REPLY FROM · ` for an unanswered owner ask, nothing for an ordinary ask — so the halted count existed in exactly one place in the output: the truncated list. A reader forming "how many are halted" has only one arithmetic available to it, counting the visible ⛔ rows, and that arithmetic returns the CAP whenever halts exceed it. Because `collect()` sorts halts first (deliberately, so a halt can never be truncated away), an over-cap digest shows exactly five ⛔ rows whether ten halts stand or fifty — the cap and the count are indistinguishable in the output, which is why the seat relayed one as the other rather than mis-reading anything. Nothing downstream could catch it either: there was no `--all` or `--limit` to cross-check against (argparse carried `--workspace`, `--package`, `--selfcheck` only), and `selfcheck()` asserted `len(items) <= CAP` as a FEATURE, so the truncation was verified while the count it hid was not. The contract the code broke is its own: `team-kit.md`'s tool row and all three master prompts state "over the cap, state the total", and the header stated one total for a list carrying three kinds.

## Fix
`render(rows, unreadable, cap=CAP)`: when and only when the cap truncates, the header now carries a total for every kind present, plus the goals the halts span — `17 owed answers · 10 ⛔ run-halted across 3 goals · 7 open asks — oldest 5 shown (--all lists every row)`. The kinds come from a new module constant `KIND_LABELS`, one entry per VISIBLE tag in the list, in sort order, with `{s}` marking where a plural goes; the invariant it encodes is that every count a reader could form by summing the visible rows is also printed as a number, so no arithmetic over a truncated list can return a cap. A second flag `--all` renders `cap=None`: every row, same line format, header without the cap clause. Alternatives rejected: raising or removing `CAP` (the cap is the masters' KISS cold-contact presentation, owner-settled, and the defect is not the cap but a count that lives only inside it); printing the per-kind totals unconditionally (below the cap nothing is hidden, so the numbers would be noise, and the empty state and the short-list header stay byte-identical this way, which is what keeps the change invisible to the presentation contract); and putting the count in the master prompts as a derivation the seat performs (that re-implements arithmetic in prose, which is exactly how a wrong number reaches Slack). The prompts got the reciprocal one-clause rule instead — the halted count is the HEADER's number, never the count of ⛔ rows shown — because a tool that states a total is useless if its reader is still told to count rows.

## Consequences
`selfcheck()`'s cap assertion had to change scope: it now runs only when the digest it was handed was produced with a cap, since `--all --selfcheck` legitimately renders more than CAP items. Default-run cap coverage did not weaken — the new fixture arm asserts the cap directly on a synthetic over-cap digest, independent of whatever the live tree holds. `render()` gained a third parameter with a default, so its two existing call sites inside `selfcheck` (the `--package` filter arm) keep working unchanged; no other caller exists anywhere in the repo — a sweep for `owed.answers|owed_answers` across `.py`/`.js`/`.json`/`.csv` found only the exposure row, `deploy/link-tools.py`'s symlink table, and prose. ## ATTENTION
- A CAP AND A COUNT ARE THE SAME OUTPUT WHENEVER THE CAPPED KIND SORTS FIRST. Halts lead by design (`collect`'s reversed sort key), so an over-cap digest shows exactly CAP ⛔ rows for any number of halts. Any future kind that is given a leading sort position inherits this hazard, and the only defence is a header number — never "the reader can see the list".
- ADDING A KIND MEANS ADDING IT TO `KIND_LABELS`, NOT ONLY TO THE TAG BRANCH IN THE ROW LOOP. A kind rendered with a visible tag but absent from `KIND_LABELS` is summable off the truncated list and stated nowhere — the exact 2026-08-26 defect, reintroduced for the new kind. The selfcheck's per-kind loop only catches it if the fixture happens to carry a row of that kind.
- THE PER-KIND TOTALS ARE DELIBERATELY CAP-ONLY. Printing them unconditionally would change the short-list header and the presentation contract the three master prompts state; the empty state `no owed answers` must stay byte-identical because `selfcheck` and the prompts both key on that exact string.
- `selfcheck`'s cap assertion is now conditional on `cap is not None`, so a run through `--all` no longer asserts truncation at all. The default-run cap is proven by the synthetic arm instead — deleting that arm silently removes the ONLY remaining proof that the cap applies.
- THE PROMPT HALF OF THIS FIX IS INERT UNTIL A DESCRIPTOR REFRESH. The four edited lines in `channel-master-prompt.md`, `console-master-prompt.md` and `goal-master-prompt.md` are sources; the seats read rendered descriptors under `.rbtv/goals/…/seat.md`. Until `materialize-seats --refresh` runs, the tool states the total and the live seat is still told to count rows.
