# Planning a workflow

You already hold every planning input: the scope, the decisions, the rulings. This file rules ONE thing — the SHAPE you write them into, so a coordinating agent can execute the result without you present.

## What this format never does

- It NEVER interviews, NEVER decides content, and NEVER chooses the work — the sanctioned owner question is exactly ONE: the loose-ends destination (§ Loose ends). It NEVER asks "do you want checkpoints?" (§ Owner checkpoints): a checkpoint is written only for a judgment item that survived the test there, or for a hard checkpoint the owner requested during planning. Every fact the plan states arrives from what you already hold; a fact you are missing is a gap you STATE to your caller, never one you invent to fill an agent.
- It NEVER resolves where the plan folder goes. The caller names that folder; this file rules only what goes inside it.
- It produces NO registration of any kind. A plan has no prompt/task pairs, no workflow JSON, no cast runner, no exposure row, no casting sheet, and no materializer step — the files you write ARE the deliverable, live the moment they are saved. The coordinating agent follows the rules in `workflow.md` itself. The four-letter workflow-code law binds registered workflows and NEVER these: no manifest reads these names, so a prompt.md is named for the unit's job, and the agent's name is `<plan>-<agent>`.

## The plan folder

```
<plan-folder>/
├── workflow.md                 the ONE surface the coordinating agent reads to schedule
├── read-first.md               what EVERY executor reads before its own task file
├── agents/<plan>-<agent>/      one rbtv agent folder per agent: prompt.md (its prompt) and agent.json (its description, harness, model, effort, files, packs)
├── agents/<plan>-<agent>/prompt.pre-split.md the parent prompt.md kept UNCHANGED when a boundary moved (§ The review before handover)
├── tasks/<agent>.md            one task file per agent — the result, scope, phases and done contract
├── tasks/<agent>.pre-split.md  the parent task file kept UNCHANGED when a boundary moved
├── reports/<agent>.md          written when the agent finishes; the coordinating agent reads it to set done or failed
├── checkpoints/cp<n>-<name>.md owner judgment gates (§ Owner checkpoints) — when the plan carries any
├── judgements/<judge-name>.md  judge verdict files (§ Judge agents) — when the plan carries judges
├── judgements/plan-review.md   the plan-review verdict file (§ The review before handover)
├── CLAUDE.md                   two lines: coordinating this plan → read workflow.md, + the folder-artifact roster
└── AGENTS.md                   same two lines, for non-Claude harnesses
```

`<plan>` is the plan folder's name. `<agent>` is the short job name, the file stem. The agent's name, its folder name, and the workflow table's Agent cell are `<plan>-<agent>`. `cast --agent` takes the agent folder's path. The plan folder KEEPS the agent folders as the record after `rbtv agent remove`.

A plan MUST carry `workflow.md`, `read-first.md`, and one agent folder (`prompt.md` and `agent.json`) plus one task file per agent. An agent's scope is NEVER split across extra files — the one sanctioned pointer is to a scope, design, or ruling document that ALREADY EXISTS.

`CLAUDE.md` and `AGENTS.md` each carry these two lines and nothing else:

```
If you are coordinating the execution of this plan, read workflow.md first.
Folder artifacts used here when applicable: loose-ends.md (captured loose ends, PARA -tasks format), issues.md (open questions needing a ruling), doubts.md (self-resolved doubts + reasoning, recorded for later review), ideas.md (framed, not ruled), decisions.md (rulings, append-only), status.md (current state).
```

They exist so an agent landing in the folder cold is pointed at the scheduling surface and knows the canonical artifact names; they are not documentation and never grow beyond these two lines.

## `workflow.md` — the one scheduling surface

Only the coordinating agent reads it. It carries, in this order: the workflow table, the owner-checkpoint table directly under that table (§ Owner checkpoints — omitted only by a plan that states it has none), the Install section, the scheduling rules, and the coordinating-agent contract. There is no second agent table, no description column, and no diagram: the Needs column IS the DAG. There is no workflow JSON and no cast runner.

**The table has exactly these columns — `Agent | Task | Needs | Status`:**

| Agent | Task | Needs | Status |
|---|---|---|---|
| `<plan>-store-schema` | `tasks/store-schema.md` | — | open |
| `<plan>-watchdog` | `tasks/watchdog.md` | `<plan>-store-schema` | open |

- `Agent` is the agent's name, `<plan>-<agent>`, spelled exactly as its folder name and as the `name` in its `prompt.md`.
- `Task` is the path of its task file, from the plan folder.
- `Needs` names every agent in this table whose results this task reads, comma-separated; `—` means the agent is a root. No chain of needs loops back. A preference or a priority is NEVER a Needs edge. A Needs edge is also how two agents that change the same file or record are ordered when one must finish before the other (§ Sizing and parallelism); the scheduling rules then name the shared file, so a reviewer can tell a read from a write-order.
- `Status` is exactly one of `open`, `running`, `done`, or `failed`. The cell carries that word and nothing else — no evidence text, no verdict, no approval string. Outcome and evidence live in `reports/<agent>.md`. The coordinating agent reads that report to set `done` or `failed`. A run that cannot finish is `failed`, and the reason is in the report; a failed agent blocks everything that needs it.
- The table NEVER carries a harness, model, or effort column, and NEVER a description column. Harness, model, and effort live only in each agent's `agent.json`, and are written there before the Install section names the agent. A human dependency is a checkpoint hold, visible in the checkpoint table, not a marker in this table.
- `read-first` is not a row. It is a file every task file opens by requiring. `plan-review` (§ The review before handover) IS a row: an ordinary agent, launched by the planning session, left `done` before handover. The coordinating agent launches only `open` rows.

**The checkpoint table** sits directly under the workflow table. Columns:

| checkpoint | opens when ALL of these are `done` | holds these agents (and their downstream) until owner PASS | file (read only when it opens) |

A held agent is simply not launched until its gate is PASS. A checkpoint is not a Needs edge.

**The Install section** lists one exact command per agent, so a reviewer can audit each agent. Its harness, model and effort are NOT in the agent's `prompt.md` and NOT in the table: they live in the agent's `agent.json`. Choose them with `cast route`, write them into `agent.json`, then write the command:

```
rbtv agent add <plan-folder>/agents/<plan>-<agent>
```

`effort` in `agent.json` is the model's own word, such as `high`, as `rbtv agent configure` takes it. `cast --agent` reads all three values from `agent.json`, so its command line carries none of them. The planning session runs every add command before handover, so a dry-run can address the agent and so plan-review can be launched. The coordinating agent runs them again before its first launch (`rbtv agent add` is idempotent) and, when the plan closes, takes back the generated files of every one. The agent folder stays:

```
rbtv agent remove <plan-folder>/agents/<plan>-<agent> --all --yes
```

**The scheduling rules** are the constraints that are not read-dependencies, stated as their own list BECAUSE a preference must never hide inside Needs. The one that recurs is custody: a file or record two or more agents both change. They never run together. The order is a Needs edge — one needs the other — or a stated exclusion line that names the file, names every agent that changes it, and states the limit ("at most ONE of A, B, D in flight"). An exclusion line is not a Needs edge; the coordinating agent honors it the same way, and does not launch an agent while another named on its line is `running`. A named writer with the others barred from the file is a wall in those task files, not an exclusion line. Append-only writers still change the file: they need an order or an exclusion line, and they commit with a pathspec.

**The coordinating-agent contract** is the section below, written into `workflow.md` in your own words for the agent that will run this plan. That agent holds the plan folder and nothing else — it never reads this reference.

## `read-first.md` — what every executor reads first

ONE file, read by every executor before its own task file, carrying exactly what is TRUE FOR ALL of them:

- **Program context** — what this program is, what settled it, and that those rulings ARE settled. An executor that reads a ruling as open re-litigates it.
- **Where things live** — the code trees, the runtime state, the branch. State that a cited `file:line` may have drifted and MUST be re-located by content.
- **Hazards** — every trap that would cost an executor its work: a file that MUST be saved through a gate rather than written in place, a surface that goes live the instant it lands versus one that waits for a restart, shared repos where other sessions hold uncommitted work, the commit form that keeps a foreign change out of your commit.
- **The reporting bar** — what `reports/<agent>.md` MUST state: what was done, what was VERIFIED with the command output that proves it, and the loose ends. A report naming no command has verified nothing. The coordinating agent decides `done` or `failed` from that file, not from tone.
- **The craft bindings** — stated once here, binding every executor: an agent that writes or edits CODE reads `meta/code/skills/coding.md` (and the four references it names) BEFORE its first edit and holds them for the whole change; an agent that creates or changes SCAFFOLDING (a rule, prompt, skill, task, agent, capability, workflow, or any component surface) reads the build documentation — glossary, guides, and principles — starting at `core/rbtv/skills/framework.md`, BEFORE its first write, and holds those reads for the whole change. A verification-only agent reads neither. These reads are part of each agent's measured context budget.

Nothing agent-specific goes here: a fact true of ONE agent belongs in that agent's task file.

## The agent folder and the task file

One rbtv agent per unit of work. The agent's `prompt.md` is the standing prompt. The task file is this run's work. `cast --agent` runs the agent: its folder (`<plan-folder>/agents/<plan>-<agent>/`) is the working folder, its `prompt.md` is the system prompt, and the wake (`-f <task-file>`) is the task file itself.

**Agent folder** — `agents/<plan>-<agent>/`, holding two files. `prompt.md`: frontmatter carries `name` (`<plan>-<agent>`) and nothing else. Body is Role, Procedure, and Constraints — the standing purpose, not this task's goal, scope, or done check — and may hold a Navigation section of paths from the installation root. Procedure tells the agent to do the task it was given, to write `reports/<agent>.md`, and not to read `workflow.md`. Constraints include: do not wait after the turn ends (a `cast` run is one turn; nothing wakes it with a result; any check its conclusion depends on runs to completion inside the turn). `agent.json`: `name` (`<plan>-<agent>`, the same as the folder name and as `prompt.md`'s `name`), `description` (one quoted line in the four-field format of [Routing table](../../../../core/rbtv/capabilities/glossary/routing-table.md): `CONTAINS: ... PURPOSE: ... ALWAYS LOAD WHEN: ... DO NOT LOAD WHEN: ...`; it holds no steps), `harness`, `model` and `effort` (chosen with `cast route`, see the Install section), `files` (the files the agent needs, as full ids `<module>/<component>#<name>`) and `packs` when any: the names of the packs turned on for it. A pack is turned on with `rbtv agent add AGENT --pack NAME`, never by naming it as a file. Do not carry component workflow keys (`exposes`, `goal-writes`, `rw-paths`, `human-interactive`) into either file: they grant nothing here. Neither file holds a channel id, absolute path, account, host, or credential.

**Instrument selection.** While authoring each agent and task file, discover existing files before inventing one: `rbtv list`, `rbtv search`, `rbtv show`. Put each selected file and its purpose in that agent's task file or in its `prompt.md`.

**Task file** — `tasks/<agent>.md`. The occupant is a fresh sub-agent with zero memory of the session that planned this, holding the prompt.md, `read-first.md`, and this ONE file. The file follows [Task](../../../../core/rbtv/capabilities/glossary/task.md): the result first, then `## Scope`, then `## Done contract`. A plan adds the opening directive and the `## Phases` block. In order:

- **The task OPENS with the directive to read `read-first.md` first**, by installation-root-absolute path, then to do this file, then to write the report to the installation-root-absolute path `reports/<agent>.md`. The wake is that file: `cast --agent <plan-folder>/agents/<plan>-<agent> -f <task-file>`, with `<task-file>` installation-root-absolute. `-p` TEXT is the alternative when the wake must point at the task file and add a resume note; do not pass both.
- **The result comes next**: the one result this launch produces, stated before any heading.
- **Every path the task names is installation-root-absolute.** The working directory is the agent folder, so an installation-relative path resolves against the wrong root.
- **`## Scope`** holds two closed lists, `Examine:` and `May change:`, then the rest of the boundary:
  - **The entire scope is INLINE** — the defect, the ruling it implements, the shape of the change, and the couplings to other agents that matter to THIS one. A pointer is allowed ONLY to a document that already exists.
  - **Explicit out-of-scope walls** — the surfaces this agent MUST NOT touch, named. A wall is load-bearing: crossing one is a failed agent, never initiative.
  - **The discipline that binds this agent** — its context ceiling, its commit form, and what it MUST NEVER do (restart a service, write a captured task, reach the human directly).
- **A `## Phases` block directly above the done contract** — the written phase → resource → hand-off table of § Sizing and parallelism, authored BEFORE the rest of the task file; the plan-review agent checks it and never reconstructs it.
- **`## Done contract`** — numbered clauses, every clause falsifiable, and every clause a machine can check MUST carry the exact command that checks it. "The tests pass" is not a clause; the command that runs them and the result that counts is. It closes with the action on a missing input or a failed clause: stop and report it, never wait for a reply.

Shared outputs go at paths named by both producer and consumer in their task files. Scratch files only when needed.

**ALWAYS verify an agent launches before the plan is handed over.** After the Install command has been run: `cast --agent <plan-folder>/agents/<plan>-<agent> -f <task-file> --dry-run` prints the composed command and exits 0 without launching. A bad install or a bad wake is otherwise found by the coordinating agent, mid-run, on an agent it cannot start.

## Sizing and parallelism

- Every agent MUST be sized for ONE sub-agent's context, and MUST state in its own task file that it finishes at ≤~40% of that context — stopping at a clean checkpoint and reporting state precisely beats degrading. An agent that cannot fit is two agents.
- **The ceiling is MEASURED before the task file is authored, never assumed.** For each candidate agent, estimate its full context spend against the real tree: the read set (spec + read-first + the actual files it must open — check their line counts with `wc -l`, and count every mandatory gate read), plus writing, plus verification output. Reading alone often costs 60–90k tokens on a code agent; if the estimate exceeds ~40% of one window, it is two agents. A declared-honest 40% clause on an unmeasured agent is how a plan ships oversized: agents authored without this step, each carrying the 40% sentence, have come in over budget, typically 2–4×, and had to be re-split.
- **Split at the artifact boundary, never by count.** Every task file carries a `## Phases` block above its `## Done contract`: one row per phase — `phase | resource it writes | hands to the next | artifact path OR same-state: <the input that cannot be written down>`. For each hand-off apply ONE test, the owner's: could a stranger holding only a file carrying exactly what the next phase needs do that phase correctly? Where a file can carry ALL of it, the agent ENDS there — next phase, own agent, Needs edge, holding only that artifact — and the artifact's path becomes a numbered done contract clause of the producing agent, so the hand-off is verified by the agent that owes it. Where some needed input cannot be written into a file (a live decision that shapes the next edit, coherence one mind holds across related edits), the phases stay together and the `same-state:` cell NAMES that input in one line; a KEEP claimed without naming it is a plan-review FAIL. Rows that hand each other NOTHING are not phases of one agent: where two rows write disjoint resources, each resource is its own agent and they launch together, whether or not any ordering ruling exists — a loop over targets inside a task file is this shape wearing a numbered list. Evidence: `grep -L '## Phases' <plan-folder>/tasks/*.md` prints nothing. File count, operation count, and target count are NOT the criterion: bundling related edits is often cheaper in context AND better in result. Every SPLIT states its reason as the artifact path or the contended resource that forces it. A SPLIT whose stated reason is a number — of files, operations, targets, or steps — is VOID: strike it and restore the agent. Every block is written BEFORE the rest of its own task file, because after the file exists sunk cost defends the bundle. Bundling "decide, then apply on N targets" or "N targets, N toolchains, hours of I/O each" into one task is how a plan ends with almost every agent queued behind one chain, and a ready agent idling behind an exclusion line drafted per subsystem.
- **Corollary — an ORDERING ruling is a Needs edge, and its targets are GROUPED BY RESOURCE.** An ORDERING ruling — "do X on the source first, then propagate to every target" — is a Needs edge, never a task file that does the source and then each target in numbered parts. Downstream of that edge, targets are GROUPED BY RESOURCE, never counted. Two targets are ONE agent when any of these binds them: they share a file either agent WRITES, they are proven by one verification run, or they contend for one device, host or slot. They are separate agents when none does and each has its own writer command. Targets inside one repo or one artifact are a BATCH — one phase, one agent, driven by the source agent's artifact. Independence is CHECKED, never asserted: the scheduling rules carry one line naming both agents' write sets and pasting their empty intersection; where it is not empty, that line is a custody rule instead (one needs the other, or an exclusion line). Where one tool invocation performs the source's and one target's write atomically, the cut follows the TOOL: one agent per resource, each carrying the source slice its tool performs with that resource. Every agent that writes a resource names, in its task file, the command that performs that write. A SPLIT that leaves a new agent writing a resource with no named writer command — or with a scratch script the parent did not already carry — is VOID.
- **Corollary — long mechanical I/O is its own agent only when the cut FREES something the plan can name.** A phase of long mechanical I/O (a whole-device hash, a bulk conversion, a bulk copy) is its own agent WHEN a stranger could drive it start-to-finish from an artifact alone, its failures are report-and-stop, and the cut FREES something the plan can name in one line of that task file: work that runs beside it, or a reasoning agent that closes instead of holding its window through the wait. I/O that is the inner loop of per-item judgment stays with the judgment; a terminal verification on a device the agent already serially holds stays in the agent that holds it. The split is only real if the Install line changed — the same harness, model, and effort waiting on the same command bought nothing and is a KEEP.
- **A strictly SERIAL boundary is served by a RESUME POINT.** An artifact boundary between strictly SERIAL phases, where the plan can name nothing that would run beside the cut, is served instead by a RESUME POINT: the task file carries the literal line `Resume point: <artifact path>` at that phase, and the agent's recorded ceiling estimate is under its claimed ceiling. It becomes an agent when either condition fails, or when the phases want different executors (a different harness, model or effort in `agent.json`). A boundary with neither an agent nor a `Resume point:` line is a plan-review FAIL.
- **Whole-suite verification runs ONCE per chain**, in the chain's terminal agent; earlier agents run only the tests their own files touch. A full baseline sweep appended to every builder is context spent N times to learn one fact.
- **Every file two agents would both change gets a custody line** — one needs the other, or a stated exclusion line (at most one in flight; append-only writers still use pathspec commits). A named owner with the others barred is a wall, not a custody line. A split without custody lines trades one oversized agent for a shared-index collision. Custody is scoped to the FILE, never the subsystem — and any custody drafted BEFORE the task files existed is provisional: re-derive it from the authored task files' real edit sets before handover, because a subsystem-wide guess serializes agents that share nothing (narrowing subsystem groups to per-file rows frees agents to run concurrently). A custody row's path is CONCRETE and its writers are WRITES ONLY: cite, per agent, the task-file line whose verb is edit / write / repoint / delete / back up. A path a task file only reads, counts, reports, locates or is forbidden to open is NOT custody. A path carrying a wildcard or a `<placeholder>` names a subsystem, not a file: expand it, or state in the same row the two agents' expanded sets and paste the empty intersection. A row citing no task-file line was drafted before the task files existed and is void. After any carve, DIFF the new custody lines against the parent's: a new rule serializing siblings that share no write-file is a carve defect — fix the task files, never keep the rule.
- Every agent that CAN be a root MUST be one. Wall-clock is set by the longest dependency chain, so a plan of ten roots and one edge beats a plan of ten agents in a line — and most work that looks sequential is not. A write-order Needs edge is the exception that keeps two writers of one file from running together; it is not a way to express a preference.
- A Needs edge is a true read-dependency, or the write-order a custody rule states. A preference, a priority, or a mere sequence is never an edge. Contention that is not given an order is an exclusion line, never a silent serialization and never a false Needs edge.

## Owner checkpoints — judgment holds, never mechanical verification

A checkpoint is a HOLD GATE where the owner rules a judgment before the agents it holds are allowed to launch. It exists so a preference, a risk, a quality call, or a human-only act is ruled by the only person who can rule it. A broken layer is caught by a judge at its own boundary (§ Judge agents), never by the owner re-running a check, and never discovered under three layers built on top of it. A held agent is simply not launched until its gate is PASS.

**A checkpoint contains judgment items only.** A judgment item is exactly one of these, and the file names which:

- a preference only the owner holds;
- a risk the owner must accept — an irreversible or destructive step is ALWAYS one;
- a quality call only the owner can make;
- an act only a human can perform — this last kind is NAMED as such, NEVER dressed up as a judgment.

**Every mechanical check belongs to a judge agent, NEVER to the owner.** Mechanical has ONE definition: the pass-condition test below. The author MUST design the judge that performs every item that test names mechanical (§ Judge agents). The checkpoint MUST hand the owner the judge's results as stated facts, NEVER as steps to re-perform.

**The pass-condition test** for each candidate checkpoint item, applied before the item is written. It is an act that leaves an artifact. A self-assessment is not the test.

1. WRITE THE PASS CONDITION. For each candidate checkpoint item, the author MUST write — before the check runs — the exact observation that makes it pass: a command and the output it must print, a file and the content it must hold, a count and the value it must have.
2. If you can write that pass condition, the item is MECHANICAL: it goes to a judge agent, and the pass condition you wrote becomes that judge's criterion, verbatim, in the judge's task file. It is not a checkpoint item.
3. If you cannot write that pass condition without an evaluative word — good, acceptable, enough, reasonable, appropriate, clear, worth it — or if the right answer would be different for a different owner looking at the same evidence, the item is a JUDGMENT: it is a checkpoint item.
4. A mixed item is split: the observable part gets a written pass condition and goes to the judge; only the evaluative remainder is the checkpoint item. "The backup exists and its checksums match" is a pass condition; "are you willing to delete the original on that evidence" is the judgment.
5. Does a documented rule or the specification already answer it? YES → the coordinating agent resolves it and records the reasoning in the plan's `doubts.md`. It is not a checkpoint item.

Only what survives both — a judgment under step 3 or the evaluative remainder of step 4, and not already answered by step 5 — is a checkpoint item.

**No surviving item → no checkpoint.** The plan proceeds on the judge's verdict; the gate is not written. A judge FAIL still stops the affected agents through the judge-failure rule (§ Judge agents). The one exception is a hard checkpoint the owner already requested (below). A plan that carries no checkpoint states that in one line where the table would be. A checkpoint item that has a written pass condition is a defect — NEVER one per agent, and NEVER a quota written to look thorough.

**Hard checkpoint — the one exception.** The owner MAY request, DURING PLANNING, a checkpoint at a specific point for a specific reason. It is written even when it holds no judgment item, carries the owner's stated reason in its text, and is recorded in the plan's `decisions.md`. The author NEVER invents a hard checkpoint and NEVER asks the owner "do you want checkpoints?" as a routine question. A hard checkpoint still carries no mechanical check for the owner to re-perform.

**Designed before the task files, never proposed as a set.** The author applies the pass-condition test, designs the judge for every item that test names mechanical, and writes a checkpoint only for what survived — or for a hard checkpoint the owner already requested. Then the agents are authored so each pass condition is copied verbatim into that judge's task file, and each checkpoint states the facts that condition names. A checkpoint bolted on after the task files exist can only point at evidence that happens to be lying around. The author NEVER proposes a checkpoint set to the owner.

**Where a hold sits.** Only where a surviving judgment item, or a requested hard checkpoint, actually lives. An irreversible or destructive step ALWAYS produces a risk-acceptance item, and the hold sits BEFORE that step. A preference, a quality call, or an act only a human can perform sits at the boundary where that ruling changes what is allowed to launch. A foundation layer, a finished increment, or the riskiest diff is a judge's boundary unless a judgment item survived there.

**The shape.** Each checkpoint is ONE file, `checkpoints/cp<n>-<name>.md`, plus one row in workflow.md's checkpoint table, placed directly under the workflow table.

- A checkpoint is a HOLD GATE, never a Needs edge — the Needs column stays read-dependency plus stated write-order, and a held agent is simply not launched while its gate is pending or failed.
- The file is read by the coordinating agent ONLY when its gate opens. It is sized and worded for that moment; opening it early spends the coordinating agent's context on a moment that has not arrived.

**The file's two halves**, split by a `---` divider:

1. ABOVE the divider, the coordinating-agent preamble: exactly when to open this file, which agents it holds, which facts to verify, and the protocol — when the gate opens, FIRST verify every fact the lower half will state; a fact that does not hold routes the named agent through the contract's failure arm and the gate is NOT presented; then relay ONLY the judgment items, each with the verified fact stated, never a step to re-perform; a hard checkpoint with no judgment item is relayed as the owner's stated reason and the release ask, still with no step to re-perform; hold ONLY the gated agents while everything else keeps running (the owner is AFK by default); record pending → PASS/FAIL in status.md; on FAIL route the named agent through the contract's failure arm and re-present the checkpoint after the fix; NEVER answer a judgment item yourself.
2. BELOW the divider, the owner-facing ask, written for the owner COLD: plain words on what just landed and why this gate exists, the judge's results as stated facts, then NUMBERED JUDGMENT ITEMS — each naming its kind (preference, risk acceptance, quality call, or act only a human can perform) and asking for the ruling, never a command and never an evidence read the owner must re-perform — closing with the exact reply format: `CP<n> PASS` or `CP<n> FAIL: <which item + the ruling>`. A hard checkpoint's lower half is the owner's stated reason and that same reply format, and nothing else.

## Judge agents — machine verification without the owner

A judge is an ordinary agent whose occupant verifies OTHER agents' finished work adversarially and verdicts PASS/FAIL per agent — so neither the owner nor the coordinating agent does deep verification, and so no mechanical check is ever handed to the owner (§ Owner checkpoints). The author MUST design the judge that performs every item the pass-condition test named mechanical; that judge is not optional and is not a substitute offered when the owner declines a gate. Beyond those, ALWAYS CONSIDER further judge agents and CREATE them when the plan warrants it: several builder agents sharing surfaces, a high-stakes change (credentials, destructive acts, live services), or serialized go-live windows. A plan skips judges ONLY when the pass-condition test named nothing mechanical and none of those warrants hold — then workflow.md says so in one line beside the checkpoint statement.

**The shape (when created):**

- **Cluster judges at critical points** — one judge per cluster of builders sharing a subsystem, launched when its cluster's rows are terminal (Needs names them), so cross-agent regressions on shared files are caught together. Never one judge per agent by default, and never only a single final judge on a deep plan (a broken foundation would be found under everything built on it).
- **A go-live sweep judge** where the plan has serialized deploy/restart windows — launched by the coordinating agent at the end of each window with the window's agent list, it runs every just-shipped fix's live-verification commands against the running system. Not a Needs edge; the scheduling rules state that launch, so the reason is in the file.
- **A final judge** — verdicts the unclustered agents and any leftovers, spot-audits the cluster judges (re-runs a sample of a PASSed agent's commands), and issues the whole-plan ACCEPT/HOLD before any closeout agent runs.

**The judge's bar, written into its task file** (the prompt.md's Constraints repeat read-only and fix-nothing): it re-runs every machine-checkable done contract command ITSELF (a claim it cannot reproduce is a FAIL, whatever the report says — never grade from tone); it probes at least one adjacent edge per agent beyond the stated commands (the discriminating controls, the failure arms); it re-runs the reproduction behind any stale-defect claim; it checks the builder's diff against the craft bindings (a violation the change CREATED is a FAIL finding; a pre-existing one not surfaced is a note); it is READ-ONLY on the code — it fixes nothing, and destructive probes run only in a scratch copy; every FAIL carries an actionable finding. It writes its verdicts to `judgements/<judge-name>.md` and leads `reports/<judge-name>.md` with the verdict list.

**The coordinating-agent flow (written into workflow.md's contract when judges exist):** on a builder's completion the coordinating agent reads `reports/<agent>.md` (judges read it there). If the agent exited without writing it, the coordinating agent saves the launch's stdout into that path and then judges the file. It does a LIGHT sanity check only (report present, clauses addressed, commands present), and sets the row — the deep verification of contract rule 6 is delegated to the judges. The judge-failure rule: a judge FAIL sets the builder back to `open`, and it is relaunched as a resume carrying the judge's findings verbatim; after repeated judge FAILs (TWO consecutive on one agent), stop relaunching. Ask the owner ONLY when the open point is a judgment item (§ Owner checkpoints). When a documented rule or the specification decides it, the coordinating agent resolves it and records the reasoning in the plan's `doubts.md`. Otherwise set `failed` and write the one-line reason into the report — do not queue an owner ask. A repeated mechanical failure is not a judgment. Nothing new launches on a failed row; dependents already launched are not recalled. A failed agent blocks everything that needs it.

## The review before handover — a second mind reads the plan you wrote

The author of a plan is the worst-placed reader of its shape: the agents follow the task list the author holds, and every sizing rule above has been violated by authors who had just read it. So EVERY plan, before handover, is reviewed by an agent that is not its author.

**The shape.** `agents/plan-review/` (its `prompt.md` and `agent.json`) and `tasks/plan-review.md` in the plan folder. Its agent record (`agent.json`) names a DIFFERENT model from the one that authored the task files, chosen with `cast route`. The planning session launches it with `cast --agent` once items 1–12 of the self-check below pass (item 13 is this review's own evidence). Its row in `workflow.md` is an ordinary row; the planning session sets it to `done` once the review returns. The coordinating agent does not re-launch a `done` row. Its verdict file is `judgements/plan-review.md`, and that file OPENS with `authored-by: <model id of the session that wrote the task files>` and `reviewed-by: <the `model` in this agent's agent record, `agents/plan-review/agent.json`>`; the two MUST differ. The author writes the `authored-by:` line into the plan-review task file when creating it — nothing else in a plan records which model authored it, and an unrecorded authoring model makes "a different model" unverifiable.

**Its bar, written into its task file (template below).** It reads `workflow.md`, `read-first.md`, EVERY `agents/<plan>-<agent>/prompt.md`, and EVERY `tasks/<agent>.md`, and for each agent:

1. It reads that agent's WRITTEN `## Phases` block and checks it against the task file — it NEVER reconstructs one; an agent with no block is a FAIL, not a reconstruction job. A task file without `## Scope` or `## Done contract`, or with the `## Phases` block anywhere but directly above `## Done contract`, is a FAIL. A hand-off cell naming a path that is insufficient for a stranger is a SPLIT; a `same-state:` cell naming no un-writable input is a SPLIT.
2. It RECORDS two numbers per agent in the verdict table: the `wc -l` total of the agent's named read set plus `read-first.md` plus the craft-binding reads it inherits, and the ceiling its `## Scope` claims. A recorded total contradicting the claim is a SPLIT. A ceiling sentence with no number recorded beside it is not evidence: that agent is a SPLIT by default.
3. For each Needs edge it names the ARTIFACT PATH the downstream agent reads from the upstream one and quotes the task-file line that reads it. An edge with no nameable artifact is struck and the downstream agent becomes a root — but where the two agents' WRITE sets intersect, that edge stays as write-order (one needs the other) or becomes an exclusion line naming the shared files, NEVER nothing. Every "X first, then Y" ruling carried inside a task file is a SPLIT. The agents that could be roots and are not are exactly the edges struck here.
4. It re-derives custody from the task files under the custody rule of § Sizing and parallelism — WRITES only, concrete paths, a cited task-file line per row, the expanded sets and their empty intersection pasted — and strikes every rule that serializes agents it has just shown share no written file. Each surviving rule is either a Needs order or a stated exclusion line.

Its verdict per agent is KEEP or SPLIT/RE-EDGE with the exact new shape.

**It MAY REWRITE the scheduling surface — and NEVER a body.** The scheduling surface is `workflow.md` only: table, Needs, scheduling and exclusion lines, checkpoint table. It does not edit the harness, model, or effort in any `agent.json` (the author chose those with `cast route`). It does not create or edit prompt.mds, task files, checkpoint files, or judge files: those return as HOLD carrying the exact new shape — per new agent, its name, its Needs cell, the resource it writes, the command that performs that write, the clause-reallocation table and the wall table — stated completely enough that a diff can confirm the author implemented it. A new agent's Install command is part of that HOLD; the author runs `cast route`, writes the result into the new agent's `agent.json` and adds the line. The AUTHOR performs the file carve and the name repoint in the same sitting, while the reasoning state is still held. Before any rename, copy the parent prompt.md unchanged to `agents/<plan>-<agent>/prompt.pre-split.md` and the parent task file unchanged to `tasks/<agent>.pre-split.md` and leave them. The reviewer then re-runs only the mechanical checks — the old-name grep, `cast --agent <plan-folder>/agents/<plan>-<agent> -f <task-file> --dry-run` exit 0 on every touched agent (after the planning session has added it), the custody diff — and the planning session sets the row to `done`. Every step in this loop leaves an artifact; a step with no artifact did not happen. **On a plan already RUNNING** (a coordinating agent is flipping rows in `workflow.md`), the reviewer edits `workflow.md` NEVER — a concurrent writer would lose its flips; it writes the rewritten table and rules as a `## workflow.md payload` section of the verdict file, and the coordinating agent applies that payload as one edit between its own flips.

**The wall table.** A boundary change IS a wall change: the parent's walls were written for the parent's scope, and a split MUST duplicate some, re-scope others, drop some, and INVENT the one wall the parent never needed — the sibling exclusion (a split's two children each need a wall naming the other child's files, devices, and state files; without it both children are authorized to open all of them, the collision the split existed to prevent). For each parent wall: DUPLICATE it into every child whose files it still names; RE-SCOPE it (rename the file, device or state file) where it named a now-split target; DROP it from a child that no longer touches that target. ADD one sibling-exclusion wall per child, naming the other child's files, devices and state files. Inventing a topical wall, or dropping one that still applies, is forbidden. The wall table — `parent wall → child: duplicate | rescoped | dropped | added` — is recorded in the verdict file as HOLD payload the author implements.

**The clause-reallocation table.** Clause identity is per CLUSTER whose boundaries moved: the union of done contract clauses of every agent whose boundary moved equals the pre-split union, plus any NEW contract clause — allowed only when it names an artifact a downstream agent already must read, by path and section heading. A neighbour whose work was the source of a moved phase MAY be rewritten by the author: its task file states what was cut, its walls gain the cut surface, its done contract drops the moved clauses. The verdict file carries the clause-reallocation table — `old-agent #n → new-agent #m | dropped-because-moved | new-contract <path § heading>` — closing with `before: N, after: N + k new contract clauses`. A clause with no destination row is a dropped clause and the split does not stand.

**The repoint inventory.** `--dry-run` exit 0 proves the agent launches and proves nothing about a stale agent name inside a judge's grep or a checkpoint's FAIL map (after a split performed by hand, surfaces still name an agent that no longer exists — a builder's done contract `grep -c` pinned to the old PASS-row count, a final judge's covered-agent list, a checkpoint's FAIL route to a deleted file, and a cluster judge's `N agents / M clauses` arithmetic — while the workflow table itself is correct). So: before rewriting or renaming, copy the parent prompt.md unchanged to `agents/<plan>-<agent>/prompt.pre-split.md` and the parent task file unchanged to `tasks/<agent>.pre-split.md` and leave them. Then repoint, in the same edit, every surface on this closed list: (1) `workflow.md` table, Needs, scheduling and exclusion lines, checkpoint table, Install section, judge blurb; (2) every `checkpoints/cp*.md` opens-when, holds and FAIL-routing cell; (3) every judge task file — agent list, adjacent-edge bullets, clause-count arithmetic, and any `grep` in its done contract (a split that changes judged-agent cardinality REWRITES the judge's grep and its `N agents / M clauses` sentence in the same edit); (4) every sibling or consumer task file naming the parent — walls, contracts, Needs prose (each child's Needs prose MUST match its own Needs cell; quote both); (5) `read-first.md` contracts; (6) every prompt.md that names the parent. The reviewer records this inventory; the author performs it, because the reviewer rewrites only `workflow.md`. Then `grep -rn '<old-agent-name>' <plan-folder>` — hits allowed only in `decisions.md`, `status.md`, and the preserved pre-split files. Paste the output into the verdict file as `old-name grep: 0 live hits`.

**The author's approval.** The author approves four things and nothing more: (i) `workflow.md` table + rules + Install section, (ii) the reviewer's file list as a diff, (iii) `old-name grep: 0 live hits`, (iv) the walls and done contract of every new or touched task file. They then append `author approved <YYYY-MM-DD>` to `judgements/plan-review.md`, not to the status cell — a status cell is only `open`, `running`, `done`, or `failed`. A plan whose verdict records a rewrite and has no approval line is NEVER handed over. A task file whose walls or done contract the author rejects is reverted; the reviewer does not get a second carve on it.

**Template task file** (the author writes it into `tasks/plan-review.md` with BOTH placeholders filled as absolute paths: `<plan-folder>`, and `<rbtv-root>` — the rbtv repo root, since the working directory is the agent folder and a relative toolkit path resolves nowhere). The prompt.md is Role, Procedure, Constraints: do this task, write the report, do not edit a task file or a prompt.md, do not read `workflow.md` except as this task's named input.

```
FIRST read <plan-folder>/read-first.md completely, then <plan-folder>/workflow.md. Vocabulary (root, Needs, custody, ceiling): <rbtv-root>/meta/plan/capabilities/methods/planning-a-workflow.md §§ "Sizing and parallelism" and "The review before handover" — read nothing else of that method. You are changing scaffolding when you write a file: BEFORE your first write, read <rbtv-root>/core/rbtv/skills/framework.md and the glossary, guides, and principles it leads you to for a workflow file. A review that verdicts every agent KEEP writes nothing and reads them never. NEVER split on a number of steps, files, operations or targets.

For EACH agent with a task file under <plan-folder>/tasks/ (skip `*.pre-split.md`):

(c) For each Needs edge, name the ARTIFACT PATH the downstream agent reads from the upstream one and quote the task-file line that reads it. An edge with no nameable artifact is struck and the downstream agent becomes a root — unless the two agents' WRITE sets intersect, in which case that edge stays as write-order or becomes an exclusion line naming the shared files, never nothing. (d) Re-derive custody from WRITES only: cite per agent the task-file line whose verb is edit / write / repoint / delete / back up; a path a task file only reads, counts, reports, locates or is forbidden to open is NOT custody. ## The coordinating-agent contract
```

The agent executing the plan SCHEDULES; it does not execute. Written into `workflow.md`, these are its rules. Before the first launch it runs every command in the Install section. When the plan closes — every row `done`, or the caller stops the run — it runs `rbtv agent remove <plan-folder>/agents/<plan>-<agent> --all --yes` for every agent, which takes back the generated files and leaves the agent folder in place. The plan folder keeps the prompt.mds.

1. **It reads the main documents itself and receives supporting material through reports**, as [Delegating work](../../../sub-agents/capabilities/methods/delegating-work.md) says. The main documents are the entry point (`workflow.md`, which only the coordinating agent reads), the guides that govern the work, and the documents being changed or evaluated; the contract names the last two by path, and the coordinating agent reads them before the first launch and before judging a result. A sub-agent's summary does not replace that reading. A prompt.md, a task file and `read-first.md` are sized for the executors' context and stay delegated: the coordinating agent does not read them to schedule. It reads `reports/<agent>.md` to decide `done` or `failed`, and a checkpoint file only when that gate opens. When a decision rests on a claim, it reads the one document that settles it, a prompt.md, a task file or `read-first.md` included.
2. **An agent is ready when it is `open`, every name in its Needs cell is `done`**, no exclusion line holds it, and no owner checkpoint holds it (a held agent is not launched until that checkpoint's recorded answer is PASS).
3. **It launches ALL ready agents at every scheduling moment**, in ONE parallel batch — subject only to Needs, the exclusion lines, and the checkpoint holds. Each launch is `cast --agent <plan-folder>/agents/<plan>-<agent> -f <task-file>` (values from the Install section and the Task cell; the task path installation-root-absolute), run as a HARNESS-TRACKED background command (`run_in_background`) — NEVER `nohup … &` or `setsid` inside a foreground call, which detaches the job so no completion ever reaches the coordinating agent (a finished report can sit unread). cast itself REFUSES a detached launch at startup (exit 2, `--detached` is the deliberate override), so a wrong shape fails loud instead of silently losing tracking. `cast --agent` BLOCKS until the agent finishes. The tracked call's completion notification IS the scheduling signal. The report file, not tone and not an empty status cell, is what the row is judged from. At launch cast prints one `cast: handle {…}` line on stderr — the job's PID and session id; that handle, never a `pgrep` pattern, is how the job is addressed afterwards (`pgrep -f` self-matches the shell running the check and reads dead jobs as alive).
4. **It ARMS `cast monitor --watch` ONCE per batch, also as a tracked background command** — NEVER a hand-rolled poll loop (the obvious one, watching output growth, is silently wrong: claude's stdout stays at 0 bytes until exit). The monitor is silent while everything is healthy, never narrates progress, never reports success, and terminates printing `STALL`/`NO-SIGNAL` lines (exit 3) on the first frozen or dead-at-launch job, prints `ENDED` lines (exit 4) when a job it had seen alive LEFT the roster, or exits 0 only when it was armed against nothing — its termination is the nudge. **Exit 0 is NOT a reading of "everything finished fine"**: a whole batch dying can produce exactly that silence. A `STALL`/`NO-SIGNAL` line is a prompt to VERIFY, NEVER authority to kill — a healthy agent has been killed on this alarm; before killing, confirm BOTH that no live descendant sits under the handle PID and that no file the agent named is still being written. Only then does the coordinating agent kill the hung dispatch BY THE HANDLE'S PID and relaunch that agent as a RESUME, handing the new executor the dead run's uncommitted work as the resume point (`-p` that points at the task file and names that work, or `-f` the task file when its `Resume point:` line is enough); then re-arm the monitor for the remaining batch. An `ENDED` line is NEVER a kill: that job is already gone — read its output and exit code instead.
5. **It sets `open` → `running` at launch.**
6. **It verifies the report against that agent's done contract from the report's CONTENT, never from its tone** — clause by clause, where a clause whose command output is absent is UNMET. The report carries the clauses, so this check needs no task file; a clause the report does not carry is read in the task file's `## Done contract`. Only then does it set the row to `done`. It does not write evidence into the status cell.
7. **The failure arm: a report that does not meet its done contract NEVER sets `done`.** The coordinating agent either relaunches that agent with what the report got wrong, or sets `failed` and writes the one-line reason into the report. Setting `done` because the sub-agent sounded finished is how a plan ships an unmet clause.
8. **A failed agent BLOCKS everything that needs it.** It is NEVER launched around, and Needs is NEVER reordered, merged, or edited to route past it — a scope change goes back to the caller.
9. **The moment a row is set to `done`, it launches everything that just became ready.**
10. **Owner checkpoints:** the moment a checkpoint's "opens when" set is all `done`, it READS that checkpoint's file (only then), FIRST verifies every fact it will state, then relays ONLY the judgment items — each with that verified fact, never a step for the owner to re-perform. A fact that does not hold is not relayed: the named agent goes through rule 7 and the gate stays unpresented. A hard checkpoint with no judgment item is relayed as the owner's stated reason and the release ask. It records the gate as pending in status.md. Only the held agents stop; everything else keeps running. On PASS it records the answer and launches what became ready; on FAIL it routes the named agent(s) through rule 7 and re-presents the checkpoint after the fix. It NEVER launches a held agent on a pending or failed gate, and NEVER answers a judgment item itself. After repeated judge FAILs it asks the owner only when the open point is a judgment, and resolves it itself — recorded in the plan's `doubts.md` — when a documented rule or the specification decides (§ Judge agents).

## Loose ends

Executors SURFACE loose ends in their reports and NEVER write a captured task themselves. ONLY the coordinating agent writes captured work, and only into the destination recorded in `workflow.md`.

**The destination is asked, never assumed.** While writing the plan, ASK the user: captured loose ends to a file (and WHICH file), or chat-only? Record the answer as one line in `workflow.md`'s coordinating-agent contract — `Loose ends: <path>` or `Loose ends: chat-only`. Under chat-only the coordinating agent surfaces captures in its own report and writes no file.

The bar is NARROW — capture ONLY:

1. a defect observable NOW,
2. an owed teardown or cleanup, or
3. something actively misleading to a future agent.

Everything else gets one `noted, not captured: <what>` line in the coordinating agent's own record and dies there. NEVER apply the capture-everything variant: it is the recorded mistake — one program captured 76 loose ends and kept 40, and the discarded half cost every reader of that list its attention.

## Escalation

- **INVESTIGATE BEFORE ASKING.** When an executor raises a question, flags a deviation, or claims a blocker, the coordinating agent FIRST dispatches a cheap READ-ONLY rogue agent to check that ONE claim against code and disk, then resolves it on that evidence. Most claims resolve there. That rogue agent is launched with `cast --rogue`, not as a plan agent.
- **A question that survives reaches the human WITH the evidence** — the claim, what the verifier found, and the options — ONLY when the open point is a judgment item (§ Owner checkpoints). When a documented rule or the specification already answers it, the coordinating agent resolves it and records the reasoning in the plan's `doubts.md`, and does not ask. A bare question hands the decision back with none of the work done.
- **The human is AFK by default.** An ask is QUEUED, and the coordinating agent continues on everything not waiting on it. NEVER block the plan on presence, and NEVER answer an owner-gated question yourself to keep moving. A point a documented rule or the specification decides is not owner-gated: resolve it and record the reasoning in the plan's `doubts.md`.

## The self-check before the plan is handed over

1. Every agent's done contract is falsifiable, and every machine-checkable clause carries its command.
2. Every task file is self-contained: an occupant holding it plus the prompt.md plus `read-first.md` needs nothing else that does not already exist.
3. Every Install command has been run, and `cast --agent <plan-folder>/agents/<plan>-<agent> -f <task-file> --dry-run` exits 0 for every agent.

7. The two-line `CLAUDE.md` and `AGENTS.md` exist in the plan folder.
8. Every checkpoint item survived the pass-condition test of § Owner checkpoints (no pass condition could be written without an evaluative word, or the right answer would differ for a different owner on the same evidence) and step 5 (a documented rule or the specification does not already answer it). The plan-review agent checks these WRITTEN blocks against the task files and never reconstructs one.
