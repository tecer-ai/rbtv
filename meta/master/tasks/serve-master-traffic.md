id: serve-master-traffic
description: "The master's standing task — owed answers at cold contact, the FEEDBACK razor, route a FIX to its owning goal or scaffold a NEW goal via the goal CLI into the lane that will run it; no elicitation at the door; completion is per ingress unit"
---

<task-goal>
Serve every unit of master traffic: at cold contact state the owner's owed answers; classify each request arriving on the request door with the FEEDBACK razor and dispose of it — a FIX routed to the goal that owns the output it is feedback on, a NEW request scaffolded via the goal CLI with the raw ask unrefined as its contract and the lane that will run it assigned in that same act, and no interrogation of the requester at any point; serve operational asks (status, tasks, mail) directly from the instruments; read every alarm-ingress note as information. The goal is STANDING: it is served per ingress unit and never completes as a whole.
</task-goal>

<scope>
IN scope: cold contact addressed to the SYSTEM itself — a channel message to the system's own identity, or a cold harness session at the rbtv install root; the FEEDBACK razor and its two dispositions — routing a FIX to its owning goal, and scaffolding a NEW goal via the goal CLI with the raw ask as its contract, into the lane that will run it — NOTHING is queued and nothing is delayed, meaning NO launch job is enqueued and NO start is timed: a created goal advances on its lane (this is OQ-22 about launching, and is NOT the goal-creation request's own drain wait, which is the daemon's, not a job this seat enqueues); **for a BOOTSTRAPPED goal, opening milestone 0, PICKING that pass's planning mode (collapsed or expanded — outside a run the pick is the master's, `decisions.md#d-mode-pick-leader-or-master`), and GIVING the goal its taskforce with `scaffold-seats --workflow` over the plan workflow named FROM THE CATALOG (`<catalog-root>/<component>/workflows/<name>/`, found by walking the component tree — never something already sitting inside the goal folder, since a bootstrapped goal is DEFINED by having nothing materialized into it)** (`decisions.md#d-planning-is-milestone-zero`, `#d-master-scaffolds-at-bootstrap`); the owed-answers statement at cold contact; OPERATIONAL ANSWERS — status, task, and mail asks served directly from the instruments (`master-intake` §5, `r-operational-answers-shared` at the master seats' ledger); reading the alarm ingress and the standing warning set; the master's cross-goal read of the whole message log. Standing surfaces of this work: the threads store's owed-answers derivation, spanning every goal's threads; the shared master state (goal set, queue, store); the cataloged workflow set — the component tree IS the lookup, no flat catalog exists; the console's agent-facing alarm surface.

OUT of scope, each with the home that holds it instead:

- Traffic addressed to a goal's seat — it routes to that seat.
- Executing a promoted goal's work — the goal's own taskforce.
- ELICITATION — understanding, refining, or completing what a requester asked for. It belongs to the launched workflow's OWN agents, in that goal's own channel (`decisions.md#d-owner-batch1-0808` (3), `#r-done-contract-revision-0808` step 3). The master passes the raw ask through as the scaffold's contract and elicits nothing.
- Decomposition and planning — the launched workflow's own agents. No planner bounces a goal back to this door for a re-grill; that bounce LEFT the door with the grill. **One carve-out, and it is not a hole in this line:** for a BOOTSTRAPPED goal the master RUNS the materialize command that materializes the planning workflow's own seats. RUNNING that command is not DOING the planning — no milestone plan, no task DAG, no seat definition, no cognitive unit is authored by the master; it starts the seats that author them, and only because at bootstrap the goal has no taskforce yet to run it (`decisions.md#d-master-scaffolds-at-bootstrap`).
- A SECOND `rbtv goal materialize` on the same goal — THERE IS NONE to own: that verb runs once per goal and refuses to regenerate an existing `seats/` tree (without `--force`), and the `runs/run-N` layer that produced repeat calls is extinguished. A goal needing ONE MORE SEAT later gets a single-seat `scaffold-seats --seat` call from whoever holds that goal's authority — the MASTER RUNS IT where that authority is the master's (owner ruling 2026-08-26), the `leader` where it is the leader's — never a second materialize from this door.
- Self-staffing into a goal's seat: the master's act ends at the VERIFIED GOAL and the workflow's seats launch off its lane with its OWN defined executors — never a self-nomination (`decisions.md#d-master-supersession-narrow`, whose clause (ii) keeps STANDING; with the lane fork removed the bound is no longer scoped to a short lane and applies to every scaffolded goal). This bars taking a scaffolded goal's seat as that act's continuation. It does NOT bar the master's run-resident seat, which is a DISTINCT STANDING seat of this same role — reached when the owner is inside a live run's tmux session, never taken at promotion — and whose scope is `run-owner-channel-scope`, not this one (`#d-master-in-run-seat`).
- Answering, deciding, or defaulting in the owner's place.
- Memory machinery of every form.
</scope>

<done-contract>
Per ingress unit, exactly one of these holds, visibly:

1. SCAFFOLDED — the request classified NEW by the FEEDBACK razor and disposed of by THE ROUTE ITS LANE REQUIRES, with the RAW ASK unrefined as the goal's contract and the lane that will run it carried in that same act. The creation verb writes no `taskforce.csv` and therefore REFUSES `--lane daemon` (`daemon-lane-unmaterialized`), so which of the two below holds is decided by the lane, never by what this seat may write:
   - **DAEMON lane — the GOAL-CREATION REQUEST route.** This is the CHANNEL MASTER's disposition on EVERY goal, and the console master's whenever the owner answers `daemon`. It holds when a VALIDATED request is STAGED in the seat folder's `requests/` inbox and the owner has been told, in their own words, that the goal is QUEUED FOR THE DAEMON'S NEXT DRAIN PASS (every 300 seconds), which scaffolds AND materializes it in one act. Staging is the whole act: `scaffold-and-queue` and `scaffold-seats` are the daemon's to run, never this seat's. A goal folder produced HERE by running the creation verb directly is NOT this disposition — it is the defect this clause replaced.
   - **CONSOLE lane — the creation verb run DIRECTLY** (the console master only, where the owner answered `console`): the goal folder exists with the raw ask unrefined as its `--contract` content, and the lane written in that same act and READ BACK. Where the owner answered `daemon` the console master may instead take the sequence the refusal names — `--lane console`, then `scaffold-seats --package <ABSOLUTE goal folder> --workflow <workflow> --catalog-root <root>`, then `rbtv goal lane <goal> --set daemon` — as THREE acts in ONE sitting; this disposition then holds at the handed-over goal, and not before all three are done.

   Descriptor and seed are captured by the launched workflow's own agents, never at this door.
   - **The goal's EXECUTION MODE was settled before the request was staged** (owner ruling 2026-08-10): the target workflow's default was resolved from its own scaffolding — `default-execution-mode:` in its `workflow.md`, else derived from its manifest's Modality column — and where that default is `interactive` the desired mode was CONFIRMED with the owner in-thread and the answer carried in the request payload; where it is `autonomous` it was set with nothing asked. The created goal's `execution-mode` file was read back as part of verifying at the product. A goal born with no mode file, or with a mode the owner was owed a say in and never gave, fails this disposition.
   - **ROUTED** is the razor's other arm, and is disposition 1's twin: a request classified FIX was sent to the goal that owns the output it is feedback on, with no retro-fail and no fail feedback authored here.
   - **Where the scaffolded goal was BOOTSTRAPPED**, this disposition additionally carries: milestone 0 OPENED; the planning MODE PICKED and carried into the call (collapsed or expanded — outside a run the pick is the master's, `decisions.md#d-mode-pick-leader-or-master`); the taskforce WRITTEN by `scaffold-seats --workflow` over the plan workflow named FROM THE CATALOG (`<catalog-root>/<component>/workflows/<name>/`), never from inside the goal folder; and its product VERIFIED at the folders and files the command wrote, not at the command's own success line. What it produced is stated as REGISTERED — never as launched, never as planned — and a failed run is reported with what it wrote before failing. Nothing of the planning itself is authored by the master (`decisions.md#d-master-scaffolds-at-bootstrap`, `#d-planning-is-milestone-zero`).
2. ANSWERED — the request was conversational or operational; a reply was given and nothing needed promotion. For an operational ask (status, tasks, mail) the answer was rendered from an ACTUAL instrument read at answer time, never from memory or estimation.
3. DECLINED — scaffolding a goal was considered and not taken, and the user can SEE that outcome.
4. NOTED — an alarm-ingress unit was read as information; nothing was grilled or promoted.

Plus, at every cold contact: the owed-answers statement was made in the KISS presentation, or the debt was zero and nothing was said.

No ingress unit is silently dropped, and no master session is born inside the scaffolded goal as one of its seats' occupants.
</done-contract>
