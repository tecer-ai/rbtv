# Output preview and verification

Use this procedure to make a CLI design reviewable before implementation and to compare the finished command with that design. A proposed screen is a specification, not evidence that the program already behaves that way.

## Write literal output

For a new interface or major redesign, produce a Markdown file containing the exact proposed terminal text for every added or changed command path. Include all help depths and applicable first-use, success, no-op, empty, missing setup, invalid value, ambiguous name, confirmation, dry-run, failure, narrow-width, and structured-output cases. For a small change, short literal examples covering its affected paths can sit in the working record. Link each screen to the documented command and an exit status; identify terminal width where layout matters. Mark output streams separately when both carry content.

Declare one synthetic fixture before the screens: resources, identifiers, selected target, configuration, counts, initial state, and any shared ownership that later examples rely on. Name each state transition and its before/after count. Make examples copyable and consistent; do not silently shift the fixture or claim a mocked write was executed. Give the file a navigation list and a coverage matrix connecting changed requirements to screens. A separate informed reviewer compares every screen with the settled decisions, existing caller contracts, and [interface contract](interface-contract.md), correcting the same specification file before approval. The Markdown author and reviewer are different people or agents for substantial work.

If the owner requested preview-first review, do not edit CLI implementation until the literal specification and required owner review are complete. For any other substantial change, pause only when an incompatible interface decision genuinely requires a choice not already authorized. Keep the approved text as the source for later rendering and verification.

## Optional visual preview

Make an interactive terminal preview only when it helps the decision or is requested. Build it with the `cli-preview` tool (`../tools/cli-preview/`, source-invoked — see its `cli-preview.md`): it renders the approved literal text deterministically through one fixed offline HTML template (fixed layout, colors, and controls — search, sidebar navigation, copy buttons); it never paraphrases, invents, or improves command output, and there is no per-review producer choice of palette or design to make. When offline use is intended, it works without network requests by construction (no external assets).

The sequence: the author runs `cli_preview.py init FOLDER` to get a template review folder, writes the approved screens into it as Markdown, and a separate informed reviewer checks that Markdown against the settled decisions (as in "Write literal output" above) — the same author/reviewer split, not a second one for the preview. Once approved, run `cli_preview.py check FOLDER`, fix every reported issue (required fields, unique screen IDs, strict-JSON examples, a help screen for each declared command), and rerun until it passes — no agent designs or reformats the page at this stage; only the Markdown changes. Then `cli_preview.py build FOLDER --out FILE` renders that validated Markdown to the offline HTML file. Its declared coverage check cannot prove the command inventory is complete or that a screen's output matches the real command — that is still verified below. The parent or owner gives final review of the built preview unless an explicit instruction says otherwise.

Whoever gives that final review checks three forms for exact parity: the approved Markdown text, the data embedded in the preview, and the rendered text in the live page. Also inspect normal and narrow layouts, scrolling, focus, and copying. Report what was checked and what was not.

## Verify the real command

Build a command-by-command test list from the coverage matrix; do not substitute a few happy paths for full help and output coverage. Test the installed entrypoint, not just source invocation, from a different working folder. Check command resolution and collisions, and distinguish current-shell `PATH` from user-level or future-shell `PATH` where those differ. The command must locate its own resources outside the source folder.

Run the actual parser at every command depth and with help before/after command tokens, global options, and positionals; include missing required arguments, `--` terminator, and a literal value that resembles help. Verify the chosen help/invalid-token policy. For every documented path, test representative accepted and rejected value classes, option interactions, context precedence, aliases, errors, standard output, standard error, exit status, text and structured output. Parse structured success and failure values from standard output, check a nonzero failure exit and no duplicate structured error on standard error, and compare documented fields. Ensure no decoration leaks into structured standard output. When authentication or raw responses exist, inject fake sentinel secrets and exercise ordinary text, structured output, progress, errors, and raw-response paths; verify the sentinels appear in neither output stream.

Inspect real terminal output at normal and narrow widths. Verify full copyable identifiers, state/type labels, ordering, pagination continuation, and readable no-color/redirection behavior. Repeat invocations to expose no-op, retry, and state-boundary errors. Test paths with spaces and platform differences relevant to the supported platforms. A formatting test should inspect what the user sees, not only a renderer's string helper.

For mutating paths, isolate the target and the command's home, configuration, environment, and shared resources. Record before/after state for a real add/change/remove lifecycle where applicable, including retry, no-op, and cleanup. Record before/after state for a dry-run or no-write guarantee. Dry-run output alone proves only what the command said; it does not prove that nothing changed or that a real write would succeed. If isolation or live access is unavailable, mark the corresponding behavior unverified.

Finally, give fresh cold reviewers the installed interface through [blind testing](blind-testing.md). Reproduce material findings and retest after correction. Completion requires the changed jobs to work through the interface, applicable checks to pass, and unresolved material limits to be named; a test report without observed result is not sufficient.
