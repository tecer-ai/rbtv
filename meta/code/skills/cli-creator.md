# CLI creator

Deliver a command that a person and an agent can discover, understand, and use for the same operations. Default terminal text must serve both. A structured mode serves programs that need stable fields. Honor the stage the user requested: design-only work stops with a reviewable specification and labels build and real-command checks planned or unverified; it does not imply approval to implement. For implementation work, scale the sequence to the change: a new interface or major redesign follows the full sequence; a small edit uses the relevant inventory, examples, and tests without staging a full redesign.

## 1. Establish the job and boundary

1. Identify the real user jobs, the current command or source interface, existing callers, target users, operating systems, installation context, state and services affected, requested scope, and an observable definition of success. A short script is preferable when no one needs a durable command across contexts. **Done when:** the jobs and boundaries explain why this interface needs to exist and what a successful invocation changes or returns.
2. Inspect existing commands, documentation, callers, and suitable runtime/parser tools before proposing new names or architecture. For an existing CLI, record the current public surface and a safe baseline. **Done when:** the command inventory and compatibility obligations are known, including scripts and agents that parse output.
3. Interview the owner about choices that materially affect behavior or presentation. Use an available interactive question tool, not a plain-chat decision question. Offer named options, consequences, and a recommendation. State low-impact defaults and work past them; do not reopen decisions already settled or ask again for authorized steps. If no question tool is available, do not treat silence as approval: defer only the dependent decision and continue independent work. **Done when:** unresolved high-impact choices have an answer or are explicitly blocked.

## 2. Observe the interface cold

For an existing CLI, run a blind usability pass **before reading implementation source to diagnose or repair its interface** when interface testing is in scope. For a proposed new CLI, blind-test realistic mock output before code where that can expose design confusion; test the installed command cold after build. A design-only request without an executable can still use a mock interface review. Do not launch reviewers when the user excludes them or reviewer capability is unavailable; mark omitted checks unverified. Read [blind testing](../capabilities/cli-ux/blind-testing.md) before setting up reviewers. Keep interface authors, source-informed verifiers, and cold users distinct.

Give cold users only the runnable or mock interface, realistic user jobs, and safe test boundaries. Do not supply design intentions, suspected defects, source, documentation, expected answers, or earlier reports. Their literal commands, output, errors, and uncertainty are evidence about discoverability. **Done when:** the baseline shows which tasks a fresh user can complete through the interface alone, which they cannot, and what remains untested.

Synthesize transcripts by separating corroborated findings, unique coverage, actual contradictions, and uncertainty. Panel agreement is usability evidence, not proof of a source-level cause. Inspect source after the blind pass to find where behavior originates; treat shared or global checks as relevant when they affect the chosen command, and label their scope. Keep decisions, corrections, and rationale in one existing working record. **Done when:** each proposed change traces to a user job, observed failure, or explicit owner requirement.

## 3. Specify the complete interface

Read [interface contract](../capabilities/cli-ux/interface-contract.md) before drafting commands and help. Inventory every group, leaf, alias, positional, option, accepted value, default, interaction, output form, failure, exit behavior, mutation, setup route, and caller. Make a finite coverage matrix for every documented path and relevant value class; mark inapplicable cases with a reason. Use pairwise or risk-based combinations where a full cross-product would add no information. **Done when:** a reviewer can choose and predict any documented invocation without inferring hidden rules.

Specify literal default text and structured output for all added or changed paths, plus applicable first-use, empty, invalid, ambiguous, narrow-terminal, and machine-readable cases. Use one declared synthetic fixture, keep counts and state transitions consistent, and label mocks as proposed output. Read [output preview and verification](../capabilities/cli-ux/output-preview.md) before producing the specification. **Done when:** the owner can review the actual words, tables, examples, and consequences before incompatible design choices enter code.

For substantial work, have one author produce the Markdown output specification and a separate informed reviewer check every changed path against the agreed decisions. If a visual preview helps or is requested, build it with the `cli-preview` tool (`../capabilities/tools/cli-preview/`): author the approved screens as its Markdown review folder, run its `check`, then its deterministic `build` — no separate HTML-authoring agent designs or reformats the page. Verify source, embedded data, and live display parity against the approved Markdown regardless. Small changes may use short approved examples inline. Pause for owner review only where a proposed incompatible design decision actually needs it, or where the owner expressly requested preview-first review; then implement the approved version. Authorization already given remains in force. **Done when:** the reviewable output contract and any required owner decision are settled.

## 4. Build the command

For a new CLI, inspect runtimes available and deployable on the target platforms, plus existing repository and software development kit constraints. Choose the least setup friction and a maintained parser that can meet the specified help behavior; reuse a suitable runtime and parser for existing code. Keep one operation implementation behind interactive, noninteractive, graphical, human, and agent controls. Noninteractive calls must never unexpectedly ask a question. Choose composable operations that meet the actual jobs: discovery, exact reads, bounded collections, and narrow writes where relevant. Do not add a language, doctor command, auth layer, raw escape hatch, or companion skill without a demonstrated need. If a raw operation is useful, it inherits the same write boundaries as named operations. **Done when:** all specified paths call the intended operations and no parallel implementation can diverge.

Choose the intended project, user, or system installation scope and packaging for supported platforms; do not silently install globally. Use a temporary installation for checks when lasting deployment is not authorized. Wire the durable entrypoint so it works from another working folder without a source-relative assumption, and check command-name collisions. When command lookup through `PATH` is intended, verify the chosen folder is on the relevant current/future shell path and that the command resolves to this entrypoint. Handle relevant configuration/auth precedence without revealing secrets. Preserve exact identifiers, pagination continuation, and stable machine-readable fields where needed. If a command or field is renamed, update its docs, scripts, tests, structured-output consumers, and agent setup before completion, or provide an explicit supported migration. **Done when:** a caller using the chosen installed command and migrated integrations reaches the new behavior.

## 5. Verify behavior and first use

Read [output preview and verification](../capabilities/cli-ux/output-preview.md) for the test procedure. Exercise actual parser help at every command depth and token position, not just a sampled top-level help screen. Compare real normal and narrow terminal output with the approved literal specification; check errors, streams, structured output, repeated calls, paths with spaces, relevant platform differences, and context/config precedence. **Done when:** observed commands and outputs match the contract, with exceptions named.

Where mutation is in scope, use an isolated disposable target and isolated home, configuration, environment, and shared state. Test add/change/remove, retry/no-op, and cleanup as applicable; prove no-write and dry-run claims by before/after evidence. A preview never proves that a real write works. For a durable command, invoke its installed entrypoint from another working folder and inspect command resolution. **Done when:** the relevant real lifecycle succeeds without changing the owner's live state, or the unverified path is explicitly reported.

Run a fresh blind pass after changes with cold reviewers and new contexts, scoped to the changed behavior. Reproduce each material finding, repair its cause, and retest; keep review rounds bounded and report unresolved material issues rather than calling the CLI complete. **Done when:** a fresh user can accomplish the agreed jobs through the interface alone and the applicable checks pass.
