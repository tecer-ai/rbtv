# Exposure — how rbtv puts things in front of agents

You are exposing a part — a new component's surface, a toolsmith task's registered capability, an optimized or ported workflow's entry — in any use case. Legality lives in two KG records (§1); the organization judgment (§3) is this page's own cargo. Which FILES exist at all is `component-anatomy.md`'s (sibling); this page decides only how what exists reaches an agent.

## 1 — Legality (by record, never from memory)

- The method vocabulary is CLOSED: **skill · command · rule · hook · sub-agent · agents.md · config · path · pool** — one `method` per row, no null, no other value (`sd-graph show "exposure method"`; the ruling: `sd-graph decision d-exposure-method-canon`; the eighth value `path` is owner-ruled 2026-08-09, core-build `decisions.md#d-tool-inventory-exposure-rows`, registry transcription pending as F-113; the ninth value `pool` is owner-ruled 2026-08-09, planning-v4 `decisions.md#D22` — the part is consumed by the drafting seat into produced workflows as a closing seat; no harness realization, never `exposes:`-authorable; registry transcription rides the F-113 queue). Per-harness realization is DERIVED through CMP-12's one map — never declared per component; `path` has NO harness realization at all (the shell is the channel — CMP-12 keeps no cell, nothing is minted beside `seat.md`). Any check you write over the manifest asserts membership in this canon, not merely that the csv parses.
- The `part-kind` vocabulary is CLOSED: **capability · reference · workflow · task · prompt · tool · plugin/MCP** — one `part-kind` per row, no null, no other value (`sd-graph show "exposure manifest"` § file schema, the `part-kind` column; the sixth value `tool` is the inventory kind minted by the same 2026-08-09 ruling as `path`, core-build `decisions.md#d-tool-inventory-exposure-rows`; the seventh value `plugin/MCP` is owner-ruled 2026-08-15, `decisions.md#d-exposure-part-kind-plugin-mcp` — an MCP server registration is a part of its OWN kind, carried by `method: config` per `#d-mcp-registration-is-config`). A `pool` row's `part-kind` is the part's OWN kind — `prompt` for the two pool seats — never `pool`, which is a METHOD, not a kind.
- **`path` IS `exposes:`-authorable — it is the CLI method, and the only member whose realization is the SANDBOX's** (owner-ruled 2026-08-10, core-build `decisions.md` § *Amendment to d-extinguishment-design-lock item 12*, minted registry-side as `d-path-exposes-authorable`; supersedes this page's earlier "never `exposes:`-authorable"). The owner's word was "CLIs"; the canon's member for a shell-reached tool is `path`, and **a `cli` method value was refused twice and is not re-proposable** (`d-exposure-method-path`; `d-tool-inventory-rbtv-cli-column` — a second mint-nothing member beside `path` says one fact two ways, and the enum is keyed on). Why the authorability changed: `path` was bounded mint-nothing when every seat's shell already reached every installed tool; the 7.607 cage measurements refuted that for CAGED seats — a daemon-launched seat instructed verbatim to check in had a writable coordination surface and NO reachable `coordinate` (not on PATH under the tmpfs HOME, its team-kit target unbound). A seat's `exposes: path:` group therefore does not mint a loader — materialize emits `<part-id> <absolute entry point>` into the generated `seat.md`'s `exposed-clis:`, and the cage binds the entry point plus the code tree it runs from read-only, both ends of any symlink. An UNCAGED seat's declaration realizes nothing, exactly as before; a seat that declares nothing gets nothing. `pool` remains never `exposes:`-authorable.
- What the manifest can and cannot express — columns, entry-point-per-method semantics, the `rbtv-cli` column: `sd-graph show "exposure manifest"`. Two of its rules get improvised wrong, so they are named here:
  - A part with NO manifest row is NOT exposed and is reached only through an entry point's own content — a sanctioned state, not a gap to fill.
  - A method-less row is NOT expressible. Precedent: three empty-`method` rows were invented, a header written defending them, and both deleted on owner correction — "CLI-invocable but no harness method" is not a state the manifest can say.

## 1b — The `write-roots` column, and the skill → CLI discovery layer (W6, owner-ruled 2026-08-14)

The manifest carries SEVEN columns; the seventh is `write-roots`, and it exists because a CLI is not only code to read — some of them must WRITE (an OAuth token refresh, a cache, a state file), and under the universal read-only workspace floor they meet `EROFS`.

- **Legal on `method=path` rows ONLY** — a write root belongs to a CLI. Cell is `;`-separated.
- **Every entry carries the DANGER MARKER `!`** — written `!<path>`. An unmarked entry is a REFUSAL, at component-lint and at materialize both. **A write grant is never inferred**: it reaches a seat only because an author typed the marker. The marker is IN-CELL and the header stays seven columns — it qualifies one entry, not the row.
- **The path takes the entry-point grammar** — component-relative, or `ws:<path-from-the-workspace-root>` — and inherits the `..` refusal, resolved in the same one reader (`materialize-seats.py#_exposure_rows`).

A seat does not name those roots. It names a SKILL, and **skills are the discovery layer**: the file a `method=skill` row's `entry-point` NAMES (not "SKILL.md" — 10 of the 11 live skill rows point somewhere else) carries a flat `exposes-cli:` list in this page's own reference grammar, naming the CLIs that skill routes to. `exposure.csv` stays the DECLARATION layer, so a ref resolving to no `method=path` row is `skill-cli-dangling` — refused at component-lint and at materialize both.

Resolution is the MATERIALIZER's: it walks seat → skills → CLIs → roots, dedupes by target (two identical binds error bwrap), refuses a name reaching two entry points, and bakes the resolved absolute roots into `seat.md` as `cli-write-roots:`. `spawn.js` only reads it, and binds it read-write through the same predicate `rw-paths` is judged by — so a CLI-derived root can no more reach `.rbtv/goals` than a declared one can. Direct `path` exposure stays usable and unchanged; the method canon stays closed at nine.

**A CLI-derived root is NEVER a pierce.** `private.json`'s deny list wins over a baked grant unconditionally (the masks are appended after the whole grant stack), and materialize REFUSES a root landing on a private entry rather than letting the seat meet a silently masked mount. Editing a `write-roots` cell reaches a live seat only through `materialize-seats.py --repass`.

## 2 — The row test (run per part before adding a row)

0. Is the part a FIRST-PARTY CLI tool — one the module itself authors and ships (a script/CLI living in the component)? YES → a row is MANDATORY, not a judgment call (owner-ruled 2026-08-09, core-build `decisions.md#d-tool-inventory-exposure-rows` + first-party scope correction): every module maintains its first-party tool inventory in `exposure.csv`. Row shape: `part-kind` = `tool`, `method` = `path`, `entry-point` = the invocable (repo-relative script path, or the installed binary name where the tool installs one), `rbtv-cli` and `description` empty — the tool self-documents via `-h`. This row is inventory plus the fact of shell-reachability; it mints NO harness scaffolding, and prompts keep citing the tool in prose (`<resources>`). It is ALSO the row a seat's `exposes: path:` binds to when a CAGED seat must actually run the tool (§ Seat-folder materialization) — the row is the prerequisite, never the grant. THIRD-PARTY CLIs a dependency manifest installs (package.json) get NO inventory rows — the manifest is their declaration and the harness-exposed surface that routes to them is their reach. Continue to step 1 only if a tool should ALSO land as harness scaffolding (rare — a real exposure decision).
1. Should an agent reach this part ON ITS OWN — its own skill, command, or rule — rather than through the component's entry surface? NO → no row; give it a routing line in the entry point's body and stop. YES → continue.
2. This is a real exposure decision: pick the ONE canonical method matching how it should be met, fill the row per the manifest record's schema, and stop.
   The method choice itself lives in `exposure-choice.md` (sibling) — read it before picking; it carries the audience × trigger table and the skill-vs-sub-agent call in full.
3. A part added LATER defaults to branch 1 — a routing line, not a row. A row appears only when the owner wants the part reachable on its own.

## 3 — Progressive disclosure (this page's own cargo)

- ONE router surface fronts the component. It answers "which path, and when" — a decision table the agent stops at on the first row that holds, never a tour of everything available.
- The router carries ONLY what the next layer cannot say for itself: the routing judgment, plus the few facts nothing self-documents (a failure mode that misreads — e.g. empty extractor output means JS-rendered, not empty page; a cleanup obligation; an environment quirk). Everything else lives where it self-documents — a CLI's `--help`, a record body, a file's own frontmatter — and the router points.
- Disclose in layers, each with its own reader: the listing line (frontmatter description — the agent scanning) → the orientation body (`component.md` — the agent deciding whether to enter) → the working surface (the exposed entry point's body — the agent working) → the detail (the tool's or record's own docs, on demand). Never collapse layers to save a file: a merge puts one reader's content in another reader's context.
- Everything exposed is an entry point an agent enters; everything else is reached THROUGH one. When in doubt, front less: a buried part can be promoted later by a real exposure decision — an over-exposed surface taxes every agent that loads it.

## Seat-folder materialization (owner-ruled 2026-08-09)

A manifest row says a part is reachable on its own; a SEAT says which of those parts must be materialized beside its `seat.md`. That declaration is the prompt file's frontmatter `exposes:` mapping (method → part-ids — grammar and rules: `file-prompt.md` § frontmatter). The materializer resolves each id against `exposure.csv`, refuses any method mismatch (the manifest stays the one home of part→method), and mints the per-harness realization per CMP-12 — thin loaders for skills/commands/sub-agents, verbatim copies + a forced-read AGENTS.md preamble for rules, config merges for hooks. Adding a manifest row does NOT by itself put anything in a seat folder; listing it in a seat's `exposes:` does.

**The `path` group is the exception to "mints a loader", not to the binding rule** (owner-ruled 2026-08-10, `d-path-exposes-authorable` — §1). It resolves and refuses exactly like the other five (same reference grammar, same `exposes-ref-dangling` / `exposes-method-mismatch` / `exposes-entry-missing` gates, same `method=path` row it must agree with), but CMP-12 has no `path` cell so nothing is written beside `seat.md`. Instead the resolved parts land in the generated `seat.md` frontmatter as `exposed-clis:` — one `<part-id> <absolute entry point>` per line — which the cage's one declaration reader consumes, binding the entry point and its code tree read-only into the seat's sandbox. It is emitted into `seat.md` and not into a sibling file on purpose: `seat.md` is read-only inside the cage, so the enabled-CLI set is not self-grantable; and it is never a `seats.csv` column, because the prompt card is its one home. A mirror-resident seat reaches a repo-resident tool with the `rbtv:` second root (`path: [rbtv:ignite/coord/coordinate]` — the 13 planning seats' live shape).

## Stop rule

An exposure need neither the canon nor the manifest can express: STOP and surface it — never invent a method, a null value, or a side-channel column.
