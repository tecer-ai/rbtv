# the prompt file — `prompts/<prompt-id>.md`

Records first: `sd-graph show "prompt file"` (its file-schema field is the layout authority) · `sd-graph show prompt`. The records rule meaning and legality; this guide rules the judgment calls. On any mismatch, the record wins.

## what it optimizes for

One readable home: the whole reusable prompt — identity to constraints — auditable in a single document, each unit individually addressable as a section.

## why it exists

Per-unit files spread one prompt across many files and directories; a human auditing one seat had to reassemble it. The whole-file layout retires that: one file per prompt, versioned by git history alone — no version-ids, no `@latest`/pins, no index, no lockfile, and no `prompts.csv` (the frontmatter IS the card; a catalog would duplicate it). `seats.csv` stays — pairing this prompt with a task into a seat.

## when one exists at all

One file per reusable prompt, in the component's `prompts/` pool. Before creating one, climb the ladder: does the pool already hold a prompt an existing seat could reuse? Two prompts whose honest personas converge are one prompt. And a job that is fully deterministic gets a tool seat, not a prompt file.

## naming the id

The id is both the file name and the `id:` field, and it MUST name the prompt's ROLE — the occupant's job as a noun: `understander`, `designer`, `drafter`, `reviewer`, `verifier`, `dod-judge`.

NEVER name a prompt after the workflow that runs it. A prompt lives in the COMPONENT's pool and any workflow in that component may pair it into a seat, so a workflow name in the id claims an ownership the model does not grant, and it goes false the moment a second workflow reuses it. The workflow code belongs to the SEAT id and nowhere else: seat `plan-understander` pairs prompt `understander` with task `understand-goal`. A collision inside the pool means the role name is too vague — sharpen it, NEVER prefix it.

## what belongs — and what never does

**Frontmatter — the card, exactly these fields:**

- `id` — the prompt's stable id; seat rows reference it.
- `description` — one line; the agent-card projection, browsed blurb-first by staffing.
- `staffing-recommendations` — harness/model/effort hints for the staffer. Hints, NEVER a binding: late binding stands; no static file names a model or harness.
- `human-interactive` — OPTIONAL (owner-ruled 2026-08-09, planning-v4 D14): `yes` declares the seat's ROLE includes talking to the human — elicitation, ratification, approval. A statement about function, never about how the session runs (headless/headed is a separate axis). Contact fires only when BOTH gates pass: this flag AND the goal's execution-mode is interactive — the mode absent means autonomous, so by default nobody pings the owner; a flagless seat can never reach the owner, by design. Every flagged seat's procedure states its autonomous fallback (park the question durably / proceed on a stated default with disclosure / block-and-queue) — interaction is an enhancement over the autonomous path, never the path. The materializer emits the flag into the generated `seat.md` (emission follows the `exposes:` precedent; rides the next team-kit window).
- `fallback` — REQUIRED iff `human-interactive: yes`, and legal only there or on a seat the manifest stamps `interactive` (owner-ruled 2026-08-09, planning-v4 D14 via D19): the seat's autonomous arm, typed — `park` (the question waits durably on the bus) · `default-and-disclose` (proceed on a stated default, disclosed) · `block-and-queue` (hold the seat, queue the question for review). ⚠ **`block-and-queue`'s hold is MECHANICAL, not a procedure the seat is trusted to follow** (owner-ruled 2026-08-10, core-build `decisions.md` § `d-block-and-queue-mechanical-hold`, settling the divergence the 7.626 build surfaced — the wording here STOOD and the engine changed to match it): a seat on this arm that asks the owner and exits is NOT `done` to the DAG — the goal's execution record publishes its outcome as `blocked`, so its dependents do not start until the owner's answer revives it and that revived session finishes. The other two arms hold nothing and are unchanged. ⚠⚠ **THE HOLD FIRES ONLY ON A *DELIVERED* ASK, AND IN AUTONOMOUS MODE THE ARM IS THE WORKAROUND** (owner-ruled 2026-08-10, `d-parked-ask-autonomous-workaround`): autonomous exists to make workflows COMPLETE, not to suppress messages, so when the goal is autonomous (or the seat is unflagged) the ask PARKS, nobody can answer it, and the engine does NOT hold — the seat runs its AUTHORED autonomous workaround per `d-s14-autonomous-dod`: derive the answer, record it with provenance in the goal's own `decisions.md`/`doubts.md`, and proceed; the parked ask and the derivation are both there for the owner on return. **So `fallback: block-and-queue` obliges the prompt's `<procedure>` to carry that workaround in its own words** — the field names the arm, the procedure carries the behaviour (the ONE HOME rule below), and a `block-and-queue` seat whose procedure only says "block on answers" has no autonomous path at all. **The workaround's step carries the literal marker `Autonomous arm —`** (owner-ruled 2026-08-11, task 7.645) — one `<procedure>` step, opening with that marker, saying what the seat derives, from what, and where it records the derivation and its provenance. `component-lint`'s `interactive-fallback` check now enforces the MARKER: a `block-and-queue` prompt whose `<procedure>` carries no such step is a finding. Its limit is accepted and deliberate — the check verifies the marker is PRESENT, never that the prose behind it is adequate; authoring the substance is still the author's duty. ONE HOME: the procedure keeps the BEHAVIOR and never restates the arm name. The typed field turns D14/D15's flag ⟺ modality ⟺ fallback correspondence into arithmetic a tool checks (`component-lint` check `interactive-fallback`).
- `exposes` — OPTIONAL (owner-ruled 2026-08-09, core-build `d-seat-exposes-frontmatter`): the seat's harness-materialized instruments, a mapping of canonical exposure method → exposure.csv part-ids. Group keys are exactly `skill` / `command` / `rule` / `hook` / `sub-agent` / `path` (never `agents.md`/`config`/`pool` — those have their own surfaces or none at all). **`path` is the SIXTH key and the CLI one** (owner-ruled 2026-08-10, core-build `decisions.md` § *Amendment to d-extinguishment-design-lock item 12* → minted registry-side as `d-path-exposes-authorable`): the owner's word for it was "CLIs", and the canon's member for a shell-reached tool is `path` — no `cli` method value exists or will (`d-exposure-method-path` and `d-tool-inventory-rbtv-cli-column` both refused the name; the manifest enum stays closed at nine and gains no second mint-nothing member). A `path:` group binds to a `method=path` manifest row exactly like every other key binds to its own method, and its realization is the SANDBOX's, never a harness's: materialize resolves each part and emits `<part-id> <absolute entry point>` into the generated `seat.md`'s `exposed-clis:`, which the cage's declaration reader binds read-only — both ends, the invocable entry point and the code tree it runs from. Nothing is minted beside `seat.md` (CMP-12 keeps no `path` cell), and an UNCAGED seat's declaration realizes nothing. A seat that must reach a CLI from inside a cage declares it here (`path: [rbtv:ignite/coord/coordinate]`); a seat that declares nothing gets nothing. **A `skill:` group can also carry WRITE grants, and you never author them here (W6, owner-ruled 2026-08-14):** a skill is the DISCOVERY layer — its entry-point file's `exposes-cli:` list names the CLIs it routes to, those CLIs' `method=path` rows declare their `write-roots`, and the materializer walks seat → skills → CLIs → roots and bakes the result into `seat.md` as `cli-write-roots:`. So a seat reaches a writing CLI by declaring the SKILL, never by naming a directory; there is no write key in this frontmatter and `rw-paths` stays the only place a seat asks for a path in its own right. Column grammar, the mandatory `!` danger marker, and the refusals are `references/exposure.md` § 1b — do not restate them in a prompt. Reference grammar by segment count: `part` = this component's `exposure.csv` · `component/part` = a sibling component, same module · `module/component/part` = another module's component (owner-ruled 2026-08-09: cross-module must exist) — resolved from this component's position in the tree, so the same grammar works on the mirror and the rbtv repo (`<tree>/<module>/<component>/`) — plus the SECOND ROOT (owner-ruled 2026-08-10, registry `d-path-ref-second-root`): an `rbtv:`-prefixed reference (`rbtv:<path-under-the-repo>/<part>`, e.g. `rbtv:ignite/coord/coordinate`) resolves against the rbtv REPO tree instead of the referencing component's own, derived by walking up for the `.rbtv/config/` DIRECTORY and reading `rbtv_path` from `rbtv.json` at that workspace root, which is how a MIRROR-resident seat reaches a repo-resident tool at all. ⚠ **`.rbtv/config/install.json` is NOT consulted** (owner-ruled 2026-08-11, IPH-6 / D33 — it was, until that ruling collapsed the two walks into one): the book's `target` was redundant with the book's own location, and requiring it meant `rbtv:` could not resolve on any workspace that had never run install2 — which is every fresh clone. **`ws:` is a DIFFERENT mechanism and not a sibling of `rbtv:`** (owner-ruled 2026-08-11, IPH-6 / D33): `rbtv:` prefixes a REFERENCE *here*, in this frontmatter, and picks which component directory a manifest is read from; `ws:` prefixes the `entry-point` COLUMN *there*, in that manifest, and picks the base a file path resolves against — the WORKSPACE root, the first ancestor holding `.rbtv/config/`. Nothing in `exposes:` ever carries a `ws:` reference. It is how a seat reaches a tool that lives in neither its own tree nor the repo — a workspace tool (`ws:3-resources/tools/stools/stools.py` is the live instance) — and it is legal on `method=path` rows only, because the installer copies every other method's entry-point out of the component and a workspace path is not inside it. An entry-point that climbs out with `..` is REFUSED at materialization on every method, prefixed or not, so the sanctioned way out cannot be bypassed by counting directories. The manifest stays the ONE home of the part→method binding — materialize REFUSES a group key that disagrees with the row's `method` column. Materialize mints the per-harness loaders beside `seat.md` (realization per the registry's CMP-12 matrix). This does NOT replace `<resources>`: conditional reads, reference files, and the JUDGMENT about a CLI (when to reach for it, its caveats, its exact invocation) stay prose there — `exposes` carries only what materialization must realize for the seat. The two halves are complementary for a CLI and neither substitutes: the prose unit says WHY and HOW, `exposes: path:` is what makes the binary REACHABLE inside a cage — prose alone left a caged seat instructed to run a tool it could not run (measured 2026-08-10, the `coordinate` gap). **Authoring duty (owner-ruled 2026-08-10, core-build `d-task-capabilities-retired`):** the task file carries NO means declaration — whoever authors or amends a prompt SHOPS the needs of every task it pairs with (via `seats.csv`) and writes them here AND describes them in `<resources>` — every `path`, `skill`, and `sub-agent` entry gets its own `<resources>` bullet of at most 280 characters on how the occupant uses it, ruled in full (with its `command`/`rule`/`hook` and `coordinate`-checkout exemptions) by declaration 2 of `references/workflow-authoring-checklist.md`; the mechanizer/resource-definer flow writes the capability requirements a toolsmith builds from. A seat may hold more than any one paired task needs (supply is a union across its tasks, plus role instruments); a paired task whose means are nowhere in the prompt is the defect. **The checkout grant is a STANDING convention (owner-ruled 2026-08-12):** every workflow-node seat's prompt declares `path: [rbtv:ignite/coord/coordinate]` — the instrument its occupant closes the seat with, advancing the DAG — and that ONE entry needs no body prose, because checkout belongs to the run protocol and never to the role. Any use of coordinate BEYOND checkout — an owner-channel ask, a fail-status query, a registration act — MUST be named in the body, in `<procedure>`, `<resources>`, or `<permissions>`. A dispatched sub-agent definition (writer, researcher, diagnoser) NEVER carries the entry: a sub-agent holds no seat and does not checkout.
- `rw-paths` — OPTIONAL: a YAML list of workspace-relative write paths (the same vocabulary as the catalog `rw-paths` column — `forg-builder`'s `.rbtv/mirror`). Absent = empty cell: the product stays in the seat folder or in-goal `goal-writes`. Occupant-facing `<permissions>` / `<scope>` Write: stay prose. A product landing outside the goal folder is this key, not `goal-writes`. Name a path that exists at launch (a parent, if the product is new).

**Body — one kind-named XML section per assembled unit, in this order:**

`<role>` → `<procedure>` → `<resources>` → `<io-spec>` → `<permissions>` → `<restrictions>` → `<constraints>`

Which sections the requirement matrix demands vs permits is ruled by the `cognitive unit` record — run `sd-graph show "cognitive unit"` and read its Requirement matrix's prompt column before authoring; as of this guide's writing, `<constraints>` and `<resources>` are the optional pair and the rest are required, but the matrix wins on any mismatch. Author each section by its own guide (`references/kind-*.md`); persona and agent type nest inside `<role>`, and input/outcome/output inside `<io-spec>`. `<resources>` has no kind guide — author it from its record (`sd-graph show resources`) and from declaration 2 of `references/workflow-authoring-checklist.md`, which rules what it must cover: one bullet per declared CLI, skill, and sub-agent. The requirement matrix marks the section optional, and that stands — but a prompt declaring any non-exempt `exposes:` entry has something to describe, so in practice it carries one. **The ethos carry is MANDATORY on every workflow-node seat's prompt (owner-ruled 2026-08-12):** its `<constraints source="references/ethos.md">` section carries the ethos block verbatim between the `<!-- ethos:start -->` and `<!-- ethos:end -->` markers, copied from its one home and never paraphrased. A dispatched sub-agent definition is EXEMPT — it is handed one narrow job, never a role that designs anything.

Never in a prompt file: task-serving units (task goal, scope, done contract — the task file's cargo) · a harness or model binding · version pins or unit references · run-instance data.

## how to write an optimal one

1. Answer the meta-question first — one line on what this prompt optimizes for. No answer → no file.
2. Author sections in order, each by its guide, each unit whole and in place inside its tag.
3. Make every line pay rent: the occupant carries this whole file on every step of its work.
4. Write direct instructions throughout — never KG citations the occupant must look up.
5. Re-read as the assembled occupant with zero memory: identity, method, means, bounds, contract — all present, nothing contradicting. Then check the frontmatter parses as YAML.
