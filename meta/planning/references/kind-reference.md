# reference — the applied kind

Record first: `sd-graph show reference`. It rules meaning and legality — applied, never executed; normative, structural, or referential — and this guide rules the judgment calls. On any mismatch, the record wins.

## what it optimizes for

ONE subject an agent loads at exactly the moment it needs it, paying for nothing else. A reference is met just-in-time, and everything it carries rides in the reader's context for the whole act that opened it.

## when one exists at all

Run `component-anatomy.md`'s existence test FIRST — it rules whether the file exists at all, and this guide rules only what goes in it once it does. A reference restating a CLI's own `--help`, a KG record body, or a sibling reference is a restatement liability: a worse copy on the day it is born, drifting from the day after.

## the one-subject rule

A reference MUST carry exactly ONE subject.

**"Micro" means one-subject, NEVER small.** A subject that genuinely needs length keeps its length: a long file on one subject obeys this rule, a short file on two breaks it. NEVER cut substance to hit a size.

There is NO limit on how many references a prompt's `<resources>` names or a component's surface exposes. Splitting is therefore free and merging is what costs — a wrong split costs one extra pointer, a wrong merge charges every reader of either half for the whole of the other.

## the split test

Split when EITHER holds:

- The description needs an "and" to say what the file covers. That "and" names two references.
- A reader reaches for a section without reading the rest. That section is its own reference.

NEVER split a section that is only meaningful after the one above it. That is a chapter of one subject, not a second subject.

## the merge test

Merge ONLY when BOTH hold: neither half is ever read alone, AND both are read at the same moment by the same reader.

A shared audience is not a shared subject. A shared folder is not a shared subject. Two references one seat holds are still two references when it reaches for them at two different moments.

## what belongs — and what never does

Belongs: the one subject whole — its rule, its judgment calls, its failure modes.

The frontmatter `description` MUST name the MOMENT the file is read, NEVER merely its contents. The reader scanning descriptions is deciding whether to open the file, and a contents blurb cannot answer that question.

Never:

- Run-specific values — the inputs, paths, and destinations of one run arrive with the seed.
- Owner-specific values — channel ids, accounts, hosts, credentials, vault paths; those are run-time configuration under `.rbtv/config/modules/<module>/<component>/`.
- A second copy of anything that already has a home. Point at the home.

## how to write an optimal one

1. Name the one subject in a single line. Two lines → two files.
2. Write the description as the moment of reading, then confirm the body serves only a reader at that moment.
3. Run the split test over the finished draft, split what it names, and stop — a chapter is not a split.
4. Re-read as a reader who opened this file for its subject and holds nothing else: every sentence states a requirement or resolves a judgment call, or it is deleted.
