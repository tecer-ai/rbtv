# Orchestration

## Purpose

The long-horizon work module — creating structured plans, executing them through tiered sub-agents, and mining long sources the orchestrator can't read directly. These components make multi-session, multi-agent work repeatable: a plan written today runs without the original conversation, and execution is delegated with per-phase review instead of done in one fragile context.

---

## Components

### `rbtv-orchestrating`

- **What**: The general orchestration capability — one skill that routes any body of multi-agent work, of any work type (code included), to the right worker; dispatches each task as a self-contained artifact with a three-file state spine; verifies every return against disk (the message is a hint, the repo is the truth); and recovers from halts, worker deaths, and return drift without losing work or improvising decisions. Shaped as a thin `SKILL.md` loader → an always-loaded `core-protocol.md` (the invariants, the situation table, and the installed-model capability summary) → JIT `cards/` opened only when their situation arises. It is the single front door for orchestration: from an all-night multi-agent build down to one minimal-ceremony dispatch to a named CLI model. Dispatch surfaces are `cast` / `cast route` / `cast api` against the catalog under `.rbtv/mirror/core/sub-agents/`; cards CALL those commands.
  - **Core protocol** (`core-protocol.md`, always loaded): the invariants every run obeys (never execute the work yourself; no dispatch without a self-contained task artifact + state spine; disk = truth, verify every return; halts are the loop, never blind-retry; evidence must be plausible; budget question at every intake; ask-the-user taxonomy; adaptive brain floor; depth cap ≤ 2), the situation table that maps each run situation to its card, and a one-line capability summary per catalog row (the routable set is recalled on demand via `cast route --catalog`, never baked).
  - **Cards** (`cards/`, opened JIT per the situation table): `intake.md` (entry door selection, spine init, the one pre-AFK question round — budget, code-backend, run mode), `routing.md` (boundedness → stakes → budget tree; the `(harness, model, effort, carrier)` selector is resolved by CALLING `cast route` — the card remains the algorithm authority on any script-vs-card divergence; pinned-role floors (conductor and final-plan reviewer pin to fable with opus fallback, re-added 2026-07-07; routing §3); topology + depth cap; sdd/research/haiku leaves; batching incl. hot-zone detection against concurrent-session in-flight files), `dispatch-wrapper.md` (header+payload packaging incl. the G1 launch-root row — every CLI worker launches with its guidance-root = the orchestrator root and the work-target passed via the model's add-dir flag, the post-run confinement diff runs in the work-target's git, and an authorized self-commit is pathspec-scoped to the allowlist with `git add -A`/bare commits forbidden (the a3e217d defect class); binding addendum incl. the conductor obligation to explicitly instruct the behavior-rule read for harnesses that do not auto-read it — codex auto-reads, kimi does not (opencode auto-reads AGENTS.md at its --dir root when present), and that read instruction must require one-file-per-call / small-batch reads, never a recursive bulk read that truncates silently mid-corpus, the unified five-field return schema, tripwire field checks — dispatches are GENERATED by the dispatch-scaffold (`orchestration/skills/orchestrating/scripts/scaffold.py`) run after scripted pre-flight gates (catalog row exists, guidance file present, output folder exists) — with hand-authoring as the named fallback on a scaffold pre-flight failure plus a run-log event), `halt-recovery.md` (Halt→Decide→Resume, the L1/L2/L3 recovery ladder, doubt-escalation chain, red-sets, precondition override, USER-EXECUTED-ONLY handover), `verification.md` (return gate, review gates with pre-flagged briefs, the cold verifier at feature boundaries, debug roles, conductor-executed exit probes, and run finalization — the exit scorecard, honest completion status, and verbatim surfacing of every Human Review block), `state.md` (the three-file spine semantics, registrar discipline, propagation, the dual-write rule; the capsule regeneration discipline — every boundary write regenerates the capsule from the template skeleton (per-row liveness + volatile-facts-once), with `stamp.py --scope conductor` refusing an accreted capsule (duplicate section header, a next-dispatch claim outside Resume Point, the next dispatch stated more than once, or a Resume Point missing the three labeled bullets); state transitions route through ONE `orchestration/skills/orchestrating/scripts/stamp.py` call — worker scope writes the three worker surfaces, conductor scope adds the run-log event (the row COMPOSED from `--event-type`/`--worker`/`--outcome`, timestamp auto) + the capsule Resume Point lockstep (`Last completed`/`Next dispatch`/`Last update` labeled fields) — instead of four hand-edits, with a stamp non-zero EXIT halting the transition; a conductor-executed plan-line task with no `{id}.task.md` by design passes `--no-task-file` to skip the absent frontmatter surface and stamp the rest (refused if a task file exists, so a missing worker task file is still caught); the context-refresh offer is a deterministic checklist row of the phase-boundary procedure, not a mid-phase self-trigger).
  - **Templates** (`templates/`): `run-log-template.md` (the append-only audit log instantiated at spine init) and `state-capsule-template.md` (the mutable, atomic-overwrite resume state).
  - **Cast surfaces** (workspace component `.rbtv/mirror/core/sub-agents/`): the live roster is the **catalog** (`cast route --catalog` / `--json`). **`cast route`** is the selector (GATE→RANK→PIN; verdict `{verdict, harness, model, effort, carrier}`). **`cast`** is conductor dispatch. **`cast api`** is the API-worker runner. Routable set = catalog ∩ availability (`cast doctor` for binaries; API-key resolution for `mode: api` rows). Cards CALL these commands; the rbtv repo keeps no router / dispatch / model-catalog code. kimi-code-cli is retired — kimi models only via opencode. Worker-mirror render lives in team-kit (`ignite/team-kit/mirror/driver/`; `install.py --mirror` / `--check` / `--uninstall` are the other callers).
  - **Install (no model-package election):** orchestration install no longer elects per-model CLI packages and does not read leftover `rbtv.json` `model_packages` / `model_variants` keys. Permission-rules sync reads the catalog. Guidance-file render is retired (`d-hard-guard-retire-model-mirror`).
  - **Installer-persisted pointers** (p2-3): `rbtv.json` carries three optional pointer fields that survive re-install via `write_state` carry-forward logic: `env_file` (API-key env path), `model_plans_file` (per-model plan-overlay YAML with context-window caps — `cast route` still reads this pointer), and `model_mirror` (mirror driver state block). Each is preserved on re-install when the caller omits the corresponding flag; `--env-file` / `--model-plans-file` flags override. Graceful skip when absent.
  - **Deterministic router**: `cast route` — the selector. The routing card's §2a selector CALLS this command; the card stays the algorithm authority (card text wins on any script-vs-card divergence, defect filed against `cast route`). Developer pointer: `orchestration/docs/routing-system.md`.
  - **Context monitor** (`orchestration/hooks/context-monitor.py`): a `PostToolUse` hook script — NOT installed into `.claude/`, read in-place from the RBTV source — that reads real context-window usage from the session transcript and emits a tiered refresh advisory during an orchestration run (self-detected from the transcript; silent in plain sessions and below 30%; window configured via `RBTV_CONTEXT_WINDOW`, default 1,000,000). `install.py` wires it into the workspace's `.claude/settings.local.json` when the orchestration module is elected and removes it on de-election (`sync_hook_entry` / `remove_hook_entry` in `admin/install/installer/orchestration.py`), identifying the rbtv-managed entry by sentinel (`rbtv:context-monitor`) OR command-path-signature — never a key alone, so it survives a Claude Code settings round-trip — and preserving hand-added hooks. It replaces the old self-guessed context estimate in the phase-boundary refresh checkpoint (`cards/state.md` §8) with the real percentage.
  - **API workers**: `cast api` shells to the runner under `.rbtv/mirror/core/sub-agents/tool/api/`. Catalog rows with `mode: api` are legal to PICK via `cast route` and illegal to LAUNCH via `cast <harness>`. Keys resolve via the `env_file` path in `rbtv.json` (OS-env first, file fallback) — never inlined in artifacts or prompts.
- **When to use**: Any work that needs coordinated dispatches — executing a multi-step plan through workers, running a goal end-to-end, a long-horizon/AFK build, multi-worker or cross-repo coordination, or dispatching a CLI model (kimi-code-cli, codex-cli, claude-code-cli, opencode). Also the front door for a single standalone dispatch to a named model ("use kimi for X"). The orchestration module rule owns the discoverability trigger bar and mid-task escalation.
- **How to invoke**: Say "orchestrate this", "run this end-to-end with workers", "use kimi-code-cli/codex-cli/claude-code-cli/opencode for X", or `rbtv-orchestrating` directly. The skill loads its core protocol and follows the situation table from there.
- **Inputs / outputs**:
  - Input: a plan (with its companion artifacts) OR a goal prompt; the run's budget answer, code-backend choice, and run mode (gathered in one pre-AFK round at intake)
  - Output: coordinated worker dispatches with per-return verification and per-boundary review/cold-verification, a three-file state spine (`run-log.md` / `state-capsule.md` / `decisions.md`) that makes the run resumable across sessions, and the delivered work itself

### `rbtv-orchestrating` (rule)

- **What**: The always-on discoverability rule for the `rbtv-orchestrating` skill (`orchestration/rules/orchestrating.md`, installed as `.claude/rules/rbtv-orchestrating.md`). It pulls orchestration-shaped work INTO the skill without the user naming it, via a balanced trigger bar: **Intake Triggers** that fire on ANY of — explicit ask, an orchestration-flagged plan, a forecast of ≥3 coordinated dispatches, multi-hour AFK intent, ≥2 worker types needed, or a **fitting single dispatch** (a self-contained unit that fits an installed + available worker beating the conductor on cost/fit — fires at minimal ceremony, not a true quick lookup); **Mid-Task Escalation** that fires while already working when context fills with work remaining, when about to dispatch the 3rd sub-agent for the same goal, or when cross-repo coordination emerges; and a **Counter-List** that NEVER fires FULL orchestration (a single dispatch needing NO worker — a direct-answer quick lookup, sub-≈30-minute tasks, and work a specialized workflow already owns — `source-mining`, wiki ingest, planning itself) so the rule is counter-shaped against eager firing (a fitting single dispatch that DOES route to a worker is the minimal-ceremony trigger above, not a counter-list exclusion). On fire, the agent announces and invokes `rbtv-orchestrating` rather than dispatching workers by hand. Enforced as a sequencing gate (invoke before any ad-hoc dispatch) plus a red-flag tripwire table against the rationalizations that skip or over-fire it.
- **When to use**: Always active once the orchestration module is installed — the agent self-detects, no user action required. It is the WHEN layer; the skill's core protocol and cards are the HOW.
- **Inputs / outputs**: Input — the task in front of the agent (at intake) and the run's growth signals (mid-task). Output — a mandatory `rbtv-orchestrating` invocation when a trigger fires; no action when only a counter-list item matches.

### `rbtv-plan-doc`

- **What**: Interactive workflow that produces a complete, self-executing plan — a main plan file, a scope document (`decisions.md`, whose entry format carries an optional one-word `compoundable` marker as the single home for harvest-worthy findings), an artifact index (`deliverables.md`), a behavior-spec + test-plan per code feature (code-work plans), and individual micro-step task files for each action. Each micro-step file contains complete execution instructions so the plan runs without the original conversation context. It is **orchestration-aware**: a plan may declare it will be orchestrated and choose DEEP pre-resolution (resolve every foreseeable doubt with the user, emitting per-task executor/reviewer pins, allowlists, validation commands, serialization order, and a hard-halt registry in the form the orchestration router consumes) or LIGHT (resolve only critical questions, leave workers latitude) — the flag does not force orchestration, and HALT discipline is mode-independent. In DEEP mode the per-task executor pin is resolved by CALLING `cast route` — the SAME selector the conductor calls at run time, so plan-time and run-time routing can never disagree. Both calls degrade gracefully on a non-orchestrated plan or a workspace without the orchestration module installed. Authoring knowledge (complexity rubric, task-file contract, spec template, dependency ordering, decisions-file discipline) is read from the shared authoring core — single source, not duplicated here. Tasks set to `human_review: required` (and every checkpoint task) instruct the executor to emit a Human Review Presentation block at completion: a list of evidence-anchored items the user should review first, plus red and yellow flags drawn from concrete criteria — never free-associated, with an explicit "None identified" affirmation when no flag triggers fire.
- **When to use**: Any multi-step task where you want a structured output you can hand off to another agent session, delegate to a teammate, or return to later. Good for projects, feature builds, operational rollouts, or anything with more than 3–4 sequential decisions.
- **How to invoke**: Say "create a plan for X" or "let's plan this out" — Claude picks up the trigger automatically. You can also say `rbtv-plan-doc` directly.
- **Inputs / outputs**:
  - Input: task description, gathered conversationally across guided steps (incl. orchestration-flag/mode and code-work detection)
  - Output: `{plan-name}-plan.md`, `decisions.md`, `deliverables.md`, `specs/{feature}-spec.md` (code-work plans), and `phase-N/pN-X.task.md` micro-step files in a folder at the confirmed output path
- **Example**: "Create a plan for migrating our CRM to HubSpot" → Claude walks through scope, phases, and task granularity, then writes all files.

### `/rbtv-source-mining`

- **What**: Processes a long source (conversation export, transcript, book chapter, long document) that the orchestrator Claude cannot read directly due to context limits. It chunks the source, dispatches sub-agents to extract decisions or concepts from each chunk, groups the results, and synthesizes them into either a **reconciled document** (updates an existing doc with session decisions + user line-comments) or a **study note**. The orchestrator never reads the source — only sub-agents do.
- **When to use**: You have a long conversation or document you want to mine for decisions, incorporate into an existing spec, or turn into study notes. Especially useful after long planning sessions where you want to update a PRD or plan with what was decided.
- **How to invoke**: `/rbtv-source-mining` — Claude asks for source path, mode (reconcile or study), and target document.
- **Inputs / outputs**:
  - Input: source file path, mode selection, target document(s) for reconcile or destination for study
  - Output (reconcile): target document(s) updated in place + a delta document per target showing what changed
  - Output (study): new study note at confirmed destination
- **Example**: `/rbtv-source-mining` → "reconcile" → point to a long strategy conversation → point to your current strategy doc → Claude mines the conversation and updates the doc with decisions made, showing a diff.

## Shared Components

### Shared Authoring Core

- **What**: A single source of artifact-authoring knowledge at `orchestration/workflows/_shared/authoring/`, consumed by BOTH the interactive `rbtv-plan-doc` workflow and orchestration intake writer agents so both doors produce identical artifact contracts. It owns: the task-file contract (zero-context self-containedness, file-operation verbs, allowlists, context budgets, owner-observable acceptance criteria, and worker binding via `cast route`), a behavior-spec + embedded test-plan template for code work, a complexity rubric (Dependencies and Decision Density widened beyond the 1–3 scale to match observed coordination/decision load) that routes a body of work to its entry door, dependency-ordering rules with shared-file serialization, and the worker-facing `decisions.md` entry discipline (decision/rationale/scope only; append-don't-rewrite; size floor on rewrites).
- **When to use**: Read by planning and intake when authoring task files, specs, and dependency-ordered plans — not invoked directly by users. It is authoring KNOWLEDGE (what an artifact must contain, how to size/order/discipline it), distinct from workflow MECHANICS (step sequencing, plan-document structure), which stay in the consuming workflow.
- **Inputs / outputs**: Input — a body of work to author artifacts for. Output — task files, specs, and orderings that satisfy one shared contract regardless of which workflow or which executor model produced or runs them.

### `teamview` (CLI)

- **What**: A responsive live dashboard CLI for multi-agent tmux team runs (`orchestration/cli/teamview/teamview.py`, python3 stdlib-only, runnable in place — not installed into `.claude/`). It RENDERS the run's `state.json` snapshot (written by `team-monitor`, the run's one raw-source sensor) and reads nothing else: the tmux session's windows and panes with agent seat names, each pane row carrying the agent's harness, model, context-window used % (colored, and RED with a trailing `!` past that seat's OWN `ctx-refresh` threshold), last-activity age and prompt-pending; plus `roster_absent` ghost rows so a seat whose pane left the room is never silently dropped; plus the coordination log's last sends (`MESSAGES`: how long ago · sender→recipient · as much text as the row holds). **The snapshot's age is ALWAYS on screen and a stale snapshot renders a red STALE warning at every layout and width**; a missing/corrupt/empty snapshot renders a loud error frame, never a blank dashboard. Four layouts chosen from the pane's own measured size every frame (full / wide-short strip / narrow-tall / tiny). Below the constant first line the WHOLE BODY renders the COMBINED view statically whenever the measured frame fits everything at once, and CYCLES every ~10s only when it does not (stateless — derived from wall clock, so `--once` shows whichever page is current): the windows/panes view — itself paged as the height needs — then the messages view, then back around. A CRITICAL pane (past its own ctx-refresh threshold, >=85% context, or awaiting approval) is PINNED into every rotation page and pins the whole cycle on its windows page — never cycled out of view; the alarm rollup (`N panes · worst ctxN% · R red · A ?`) rides the header of BOTH views. `--no-rotate` (= `--view combined`) forces one complete frame; `--view panes|messages` pins one body. The WINDOWS header carries the run's average dispatch payload (`dispatch ~N tok avg/seat`) off the snapshot's `dispatch_tokens` field, and the first line carries a system RAM+CPU readout colored by pressure so an operator spots an OOM risk at a glance. Every cue, footer and ctx VALUE degrades GRACEFULLY at narrow widths instead of a blind mid-value clip; `…` marks every text truncation and `~` is reserved for context-match uncertainty. The marker legend is OFF the dashboard (every row goes to data) and lives in `teamview interface-legend`. Reference surfaces: `--help-panes` (what each pane state and marker means, and what clears `ctx~`) and `--help-security` (teamview writes NOTHING, makes NO network call, reads NO credential, and never speaks to tmux at all — a claim `--selftest` proves with an AST walk, not a grep). `--selftest` gates every edit. Promoted 2026-07-24 from the second-brain team-kit's overview tooling.
- **⚠ The plan-limit bars are NOT here (2026-08-07)**: they moved OUT of teamview to the `acct` CLI. Accounts and their plan windows are a property of the BOX; teamview renders ONE RUN. The move took teamview's entire credential-reading, network-calling and process-scanning surface with it, so the R24 boundary's exemption list SHRANK from two named lanes to one (box CPU%) — retired, not relaxed.
- **When to use**: Watching any team-kit (or otherwise tmux-hosted) multi-agent goal execution — as the control-panel strip pane, a full-screen monitor, or a small corner pane. For plan-limit headroom before routing work, run `acct usage` instead.
- **How to invoke**: `python3 orchestration/cli/teamview/teamview.py [session] [--package <goal-folder>] [--once]` (the package resolves from `--package`, else by walking UP from the cwd, else a teaching refusal at exit 2; a positional NAME is checked against the snapshot's own `session` field; symlink onto PATH per machine as `teamview`). Full flags: `orchestration/cli/teamview/README.md`.
- **Inputs / outputs**:
  - Input: a team-kit package — the GOAL FOLDER — holding `{goal}/state.json` (goal-direct since 7.607; there is no run folder)
  - Output: a continuously refreshed terminal dashboard (or one `--once` frame). It writes no file at all.

### `ctx-monitor` (CLI)

- **What**: A per-pane agent context monitor for tmux team sessions (`orchestration/cli/ctx-monitor/ctx_monitor.py`, python3 stdlib-only, runnable in place — not installed into `.claude/`). For every pane it reports the agent running there — harness, model, context-window used %, and last activity — read from each harness's OWN session record on disk (claude transcript, codex rollout, opencode sqlite db, kimi wire log; argv `--model` and visible-TUI `N% context left` fallbacks). Local files only: no network, no credentials. Claude panes map pid→transcript EXACTLY via the session-pids records a companion statusline script persists (the workspace team-kit's `statusline-usage.py`), falling back to a cwd heuristic marked `transcript~`. This is the harness-agnostic outside-observer twin of the Claude-only PostToolUse hook `orchestration/hooks/context-monitor.py` (which advises the conductor in-session); built 2026-07-24 for teamview's per-pane columns.
- **When to use**: Auditing the context headroom of a running multi-agent team from outside its sessions — one-shot (`--json` for tooling) or as the engine behind `teamview`'s pane rows; also single-pane (`--pane`) and no-tmux (`--cwd --harness`) queries.
- **How to invoke**: `python3 orchestration/cli/ctx-monitor/ctx_monitor.py [session] [--pane %N] [--cwd DIR --harness H] [--json]`. Details: `orchestration/cli/ctx-monitor/README.md`. `--selftest` gates every edit.
- **Inputs / outputs**:
  - Input: a tmux session/pane (defaulting to the current session), or an explicit cwd+harness
  - Output: one record per pane (text table or JSON): harness, model, ctx used % + tokens/window, last-activity epoch, and the source each fact came from

## How They Fit Together

`rbtv-orchestrating` is the general front door for long-horizon, multi-agent work — it ingests a plan or a goal, routes each task to the right worker, and gates every return; the `rbtv-orchestrating` rule is the discoverability layer that pulls qualifying work through that front door (intake trigger bar + mid-task escalation + counter-list) without the user naming it; `rbtv-plan-doc` writes the plans it ingests. `/rbtv-source-mining` mines the long conversations that planning and execution produce, folding decisions back into the plan or PRD.
